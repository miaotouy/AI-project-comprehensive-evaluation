## 结论摘要

这条记录把“拼命开发研究前端即时表现力的工程化机甲，被上游模型训练的过拟合给砸得粉碎”还原为一个**模型—宿主契约错位**问题：客户端已经准备了流式解析、增量投影、HTML/JS 运行面和交互回传，但上游模型在面对“做一个能立刻显示的东西”时，可能优先激活“任务拆解—调用文件工具—写入工作区—运行测试—汇报结果”的工作流。结果不是前端没有运行时，而是模型没有把输出流当成运行时的一部分。

“工作区依赖症”在本记录中是对一种可观察行为的暂定命名，不是已经被训练数据或 RLHF 因果实验确认的诊断。附加对话能支持的事实是：对话参与者报告了模型反复调用文件或工具、倾向把代码落盘，以及在需要即时富媒体表现时出现停滞或表达收缩；至于根因，也可能包含模型路由、渠道包装、工具声明、系统提示词和客户端解析器差异。

## 系统边界与总体调用链

前端即时表现力需要一条不同于普通文本回答的链路：

```text
用户意图
  -> 模型输出内联结构或受控标记
  -> 流式解析器识别稳定前缀与半截内容
  -> 消息内预览或独立运行面增量更新
  -> HTML/CSS/JavaScript/Canvas/WebGL 等运行时呈现
  -> 用户事件、错误和状态回传宿主
  -> 消息、对象或文件按各自事实源保存
  -> 后续回合读取运行结果或源码继续迭代
```

现有调查笔记显示，VCPChat 已经具备消息流、私有标记解析、HTML 预览、Python 执行、桌面挂件和部分对象回流链路；AIO Hub 则把聊天内 HTML 预览与磁盘文件驱动的 web-canvas 工作区拆成两层。也就是说，“工程化机甲”并非纯粹想象：宿主侧确实存在承载即时表现和工作区协作的不同机制。问题出现在模型选择了哪一条入口，以及该入口能否被宿主正确解释。

## 1. 两种输出范式的冲突

| 范式 | 模型默认动作 | 宿主期待 | 可观察结果 |
| --- | --- | --- | --- |
| 工作区工程流 | 拆任务、写文件、跑测试、等待工具结果 | 文件树、编辑器、预览和持久化 | 适合项目维护，首屏表现被推迟 |
| 即时表现流 | 直接生成可解析的 HTML/SVG/脚本或结构化片段 | 流式解析、局部渲染、事件回传 | 适合“边生成边看见”，但依赖协议稳定性 |

两者都可以被称为“写代码”，但事实源和成功标准不同。工作区流把文件写入视为主要成果；即时表现流把当前输出过程本身视为交互媒介。模型若只学会前一种成功标准，就会把后者误译成“先创建一个项目文件”，从而绕过已经存在的消息内运行面。

## 2. 为什么前端工程会显得像被击碎

前端运行时通常由多个相互配合的部件组成：流式边界处理、代码块识别、预览容器、脚本隔离、资源依赖、事件桥和持久化。每个部件单独工作，并不等于系统能获得即时表现力；它还需要模型持续输出宿主能消费的中间状态。

因此，模型一旦转向文件工具，破坏的是整条链路的**入口选择**：

1. 流中不再出现可供即时解析的目标片段，渲染器只能等待工具结果或完整文件。
2. 首屏从“输出即呈现”退化为“工具完成后再预览”，动画、节奏和中间状态丢失。
3. 如果模型继续在“应当直接输出”与“必须先落盘”之间切换，宿主看到的可能是空白、半成品、重复写入或长时间等待。
4. 用户会把这种体验归因于前端运行时失效，但静态证据只能说明模型—协议—渲染链路没有对齐，不能单独证明某一端是唯一故障源。

## 3. 附加对话提供的证据

附加对话把以下内容作为实测或群体观察提出：

- 某些模型在富媒体任务中没有直接输出 SVG、HTML 或动画代码，而是反复调用 `vcptoolcall`、`FileOperator` 等工具。
- “鹈鹕骑车”被作为检查模型是否仍能直接完成 SVG 动画表达的探针；这一探针的存在说明讨论者把“是否立即产生可视结果”当作模型能力维度，而不仅是代码正确性。
- 对话将模型在工作区环境中的谨慎、反复确认和工具依赖，与即时渲染场景中的表达收缩联系起来，并提出“工作区依赖症”“即时表达通道被锁死”等解释性概念。

这些是附加材料中的报告和解释，不是本轮独立复现实验。对话中的模型名称、渠道状态和降级路由也没有在本记录中视为已确认事实。

## 4. 与现有项目调查的交点

- VCPChat 的调查显示，消息正文仍是原始文本事实源，渲染器会在流式过程中识别特殊标记并把部分内容投影为 HTML 预览、工具卡或其他宿主表面；桌面挂件和 Scriptorium 才拥有更完整的独立对象或协作语义。见 [VCPChat 生成式输出与运行时调查笔记](VCPChat-生成式输出与运行时调查笔记.md) 的“协议处理”“对象模型”“表现类型、依赖与运行环境”。
- AIO Hub 的调查显示，聊天内 HTML 预览与 web-canvas 文件工作区是并列层次：前者偏即时展示，后者偏文件事实源、Git 版本和 Agent 协作。模型如果始终选择后者，并不代表前者不存在，只代表当前请求没有走到即时投影入口。见 [AIO Hub 生成式输出与运行时调查笔记](AIO-Hub-生成式输出与运行时调查笔记.md) 的“聊天输出”“画布对象模型”和“聊天流式”。

由此可以得到一个较窄的判断：前端客户端已经把“消息是文本”和“消息可以成为运行面”同时工程化，但上游模型的行为策略可能把二者重新压扁为“代码必须先成为工作区文件”。这解释了为什么宿主能力越丰富，错位发生时的落差反而越明显。

## 5. 设计取舍与已确认边界

- 即时流适合快速反馈、动画节奏和探索性原型，但依赖半截内容可解析、脚本安全和资源可用性。
- 工作区流适合多文件工程、测试、版本和长期维护，但天然牺牲部分首屏即时性。
- “模型能写出可运行项目”不等于“模型能把输出当作正在运行的媒介”；两者应作为不同能力维度记录。
- “客户端支持流式渲染”只能确认宿主提供了承载路径，不能推出上游模型一定会选择该协议。
- 本记录没有把模型行为归因于单一训练方法，也没有把具体客户端、渠道或模型版本判定为项目级缺陷。

## 未验证事项

1. 在相同模型、相同提示词下，分别关闭工作区工具和保留工作区工具，是否会显著改变输出入口。
2. 直接 API、官方客户端和中转渠道之间，是否存在模型版本、路由或系统提示词差异。
3. 让宿主明确声明“直接输出可运行片段”与“写入工作区”的边界后，模型是否能稳定保持即时流。
4. 流式 HTML/SVG/Three.js 在半截标签、脚本尚未闭合、依赖未加载时的实际渲染行为。
5. 工具调用结果、运行时错误和用户交互是否能回流到同一对象，从而让模型在下一回合按对象身份而不是重新创建文件继续维护。
