# 十九个生成式输出与运行时横向对比

> 对比对象：AIO Hub、AstrBot、Chatbox、Cherry Studio、DeepChat、DeepSeek Harness、Dify、Hermes Agent、Jan、LobeHub、Manifold Desktop、NextChat、Open WebUI、OpenCode、Pi、Risuai、SillyTavern、VCPChat、VCPToolBox
>
> 对比更新日期：2026-08-28
>
> 依据：同目录 18 份源码调查笔记及其记录的代码快照；未运行跨项目 benchmark，也不把产品宣传语当作实现证据
>
> 对比方法：沿“触发/协议 -> 对象与事实源 -> 增量更新 -> 投影/运行 -> 交互与编辑 -> 持久化 -> 模型回流 -> 生命周期治理”主链比较；结论保留“已确认、静态推断、未验证”边界
>
> 对比范围：输出对象模型、触发与输出协议、增量更新、投影表面、表现与运行环境、编辑与协作、能力桥与执行位置、持久化与版本、模型回流、生命周期与性能；普通 Markdown 与消息渲染类内容留在消息渲染器类目
>
> 文档定位：实现学习与跨项目横向比较，不作为整改方案或安全审计报告

## 结论摘要

这 19 个项目并没有实现同一种“Artifact”。同一个词可能指消息内临时 iframe、工具产出的文件、文档工作区，或可寻址的工作流执行记录。横向比较最重要的不是给项目排总名次，而是先判断输出在产品中究竟是回答、工作过程、文件、可编辑文档，还是可运行应用。

1. **真正的对象模型仍然少见。** 大多数项目把消息文本、parts 或 blocks 作为事实源，Artifact 只是从消息内容派生的投影。LobeHub 的文档、OpenCode 的真实文件、Cherry Studio 的 Agent 工作区、AIO Hub 的 web-canvas，以及 VCPChat 的桌面挂件拥有独立对象身份；AIO canvas 已按项目区分派生状态并回传预览错误，但审批候选和运行实例仍不持久，也没有 revision 或环境级持续调度。
2. **G3 执行能力不等于 G4 可编辑工作区。** AIO Hub、Chatbox、DeepChat、Jan、NextChat、Cherry、Open WebUI、VCPChat 等都能让 HTML/代码实际运行，但其中多数不能让用户和模型围绕同一对象进行定向编辑、版本管理和恢复。AIO 的消息 HTML/SVG 代码块可执行 JavaScript、表单和 Canvas 小应用，Action Button 可触发预定义聊天动作；它属于 iframe 型可执行消息，不能因宿主 SDK 弱于 VCPChat 就从 G3 样本中漏掉。执行环境与对象生命周期必须分开计分。
3. **工作区路线的事实源最清楚，但事实源清楚不等于协作事务完整。** OpenCode 直接以文件系统、ToolPart、SQLite 会话和影子 Git 快照组成闭环；Cherry 的磁盘 workspace 通过文件树、编辑器、冲突检测回流到下一轮；AIO 的 canvas 以物理项目和 Git 为真相源，审批候选先进入内存覆盖层，当前项目外部变更也会触发刷新。它仍没有 revision、CRDT 或冲突合并，候选层也不能跨重启恢复。
4. **消息派生路线的优势是低接入成本。** Chatbox、Jan、NextChat、LobeHub、DeepChat、Open WebUI 等可以从一条消息中探测 HTML/标签并显示 Artifact，不必建立新的对象表。代价是对象身份通常由消息位置或内容派生，编辑、分享、跨会话恢复和多投影同步很难做完整。
5. **结构化协议比自由文本更适合长期演进。** Cherry/Chatbox/Jan 的 typed parts、DeepChat 的 blocks、LobeHub 的 flow、OpenCode 的事件与 ToolPart 都把工具、推理、文件和正文分开。AIO 当前接入的 VCP 文本协议、VCPChat、VCPToolBox 的私有文本协议兼容面更宽；其中 AIO 的工具调用表示位于可替换的 `ToolCallingProtocol` 抽象下，但当前只实现 VCP。对这些文本协议而言，标记嵌套、半截流、后处理顺序和回放一致性会成为隐式契约。
6. **稳定区优化是可执行内容的分水岭。** AIO 的 stable/pending AST + Patch、VCPChat 的 stable block + morphdom、LobeHub 的尾块缓存和 OpenCode 的分块/Worker 方案，会限制重算范围并保留运行时状态。仅做 30 FPS 或 rAF 节流（如 NextChat、SillyTavern 的累计全文重渲染）只能控制频率，不能消除长回复增长成本。
7. **安全边界随运行强度急剧变化。** Chatbox、Jan、LobeHub、NextChat 的不透明源 iframe 相对克制；Open WebUI 还提供 CSP 注入和导航拦截，但配置可放宽。Cherry、DeepChat、AIO 的 HTML 分支允许 `allow-same-origin` 与脚本，VCPChat 更直接在主页面执行脚本；这类能力不能按普通 Markdown 的信任模型处理。
8. **VCPToolBox 应被看作运行时供给层。** 它有工具进程、MediaRenderer、AICodeWorker、文件和事件记录，却没有最终用户消息表面。把它与 VCPChat 的桌面挂件或 Open WebUI 的代码解释器直接比较，会把“执行调度”和“输出投影”混成一层。
9. **没有脱离场景的总冠军。** 通用桌面聊天适合采用结构化 parts + 低权限 Artifact；编码 Agent 更适合以文件/Git 为事实源；自由生成小应用要单独设计 runtime SDK、权限档位和资源回收；角色卡生态则必须把字符串、HTML/CSS 和扩展事件视为兼容契约。
10. **模型输出没有 artifact 对象，会话事件日志是唯一事实源。** DeepSeek Harness 的原始形态是闭合的 StreamChunk 七变体协议（block-start、text/reasoning/tool-call-delta、block-end、usage、finish）；BlockAssembler 是唯一折叠器，agent-loop 把每条 chunk 先落 assistant/chunk 事件再喂给折叠器，block-end 是权威整块、max-tokens 时丢弃未完成 tool-call，随后冻结出带 usage 与 sourceEventSeqs 的 assistant/message 落为表面节点。输出对象有四类身份：消息、工具调用配对、磁盘文件（spill 与 sha256 内容寻址附件）、仅进程内存活的终端会话。持久化默认 JSONL（zstd 帧，注释声称体积约 -60%）或 SQLite。能力总评 G1（富静态结果），终端 PTY 是 G5 活对象的局部形态。
11. **媒体类 G1 对象可以在消息正文之外获得独立身份。** Risuai 的输出以消息文本为绝对主体（G0），唯一有独立对象身份的是 inlay 媒体资产（G1）：UUID 寻址、独立 IndexedDB 存储、image/video/audio/signature 四类，经 `{{inlay::id}}` 占位嵌入消息。回流是宿主代取式半闭环——提示构建时宿主把图片与签名解析回注模型上下文，模型自身没有资产寻址能力；它提供了“媒体对象如何在无执行面的文本聊天里获得身份并参与下一轮”的对照样本。

VCPChat 的 Scriptorium 已形成另一条 G4 级的局部链路：源码作为文档事实源，Agent 可读取文档和视觉上下文并提交完整 source PR，人工审阅后才返回 applied、rejected、conflict 或 failed。它比消息内预览多了对象、审阅与可追溯编辑记录，但未见 CRDT 或自动三方合并。VCPToolBox 的鼠标主题生成仍应保留在 G1 文件交付：CUR/ANI、预览、源 HTML 与安装脚本被打包为 ZIP，没有主题 ID 或版本链。

## 输出对象与事实源

### 1. 消息派生对象：便宜、直观，但身份脆弱

Jan、NextChat、Chatbox、DeepChat、LobeHub 的 Artifact，以及 AstrBot 的 GenUI、Hermes 的桌面 artifact，主要都是从消息正文、parts 或 blocks 在渲染期推导出来。对象可以拥有局部 React/Vue key 或内存注册表，却不等于拥有跨会话稳定 ID、独立版本和事实源。

这条路线适合“模型回答后立即预览”：协议接入简单，历史恢复只需重新渲染消息，删除消息即可删除投影。它不适合直接承诺对象级协作，因为以下问题尚未自动得到答案：

- 用户编辑写回消息全文时，如何保留对象身份和其他 part 的边界；
- 同一 Artifact 同时出现在消息、侧栏和分享链接时，谁是权威版本；
- 流式过程中对象尚未闭合，重载、切换会话和重新生成如何收口；
- 模型下一轮如何查询“第几个对象”而不是重新扫描一段文本。

NextChat 的内容 md5 分享链接、LobeHub 的 Artifact 派生 ID、Cherry 的临时 Artifact ID 都不能替代对象数据库中的稳定身份。它们能定位一次投影，却不自动提供版本、权限或协作语义。

### 2. 文件/文档事实源：编辑、恢复和回流更可靠

OpenCode、Cherry Studio Agent workspace、AIO web-canvas、LobeHub 文档和 Pi/Chatbox/Hermes 的文件工具链把真正的源放在文件系统、数据库文档或 Git 快照中。消息只负责记录“谁在什么时候修改了什么”，而不是承担完整源码。

其中 OpenCode 的边界最清楚：工具调用落 SQLite `Part`，文件系统是真实工作区，影子 Git 记录回合快照，模型通过 `read/glob/grep` 再次读取。Cherry 将这一模式包装成文件树、代码编辑器、自动保存和冲突检测；AIO 提供独立预览窗与 Git 提交，并把预览错误经窗口总线回传主窗口 Agent。LobeHub 的 Lexical 文档则把 diff、锁和 Page-Agent 修改置于文档对象层。

文件事实源也有代价：它要求项目路径、权限、删除、迁移和外部编辑都被纳入生命周期；“模型生成了一个漂亮的消息卡片”不再是完整功能，用户需要理解文件、分支和恢复状态。对编码 Agent、长项目和需要跨会话维护的应用，这是合理代价。

### 3. 活对象：少数项目把运行状态也当作对象

VCPChat 的桌面挂件最接近 G5：拥有独立 ID、文件持久化、重载、模型创建/替换/查询和能力桥。AIO canvas、LobeHub 文档、OpenCode 文件和 Cherry workspace 具备 G5 的若干条件，但它们的“活”主要来自文件/文档状态，不是任意脚本在桌面持续运行；AIO 的错误回流已经静态贯通，运行实例和审批候选仍不持久，因此仍只计 G4。

Open WebUI 的 Pyodide 文件系统和代码解释器 output item 是会话级活对象，能执行、编辑和保存；不过跨会话对象保证、版本语义和多投影同步仍有限。不要因为某个 iframe 能运行定时器，就把它称为 G5：运行实例可被销毁、源码可能只存在于消息文本，模型也可能完全无法观察其状态。

## 增量生成、更新与最终化

增量能力应拆成三项：更新频率、每次重算范围、已创建节点/运行实例是否保留。下表只比较生成式输出与运行时相关的主路径。

| 类型 | 项目 | 主要策略 | 长回复/活对象影响 |
|---|---|---|---|
| 稳定前缀或尾部 patch | AIO Hub、VCPChat | stable/pending AST 或 stable block；尾部 Patch/morphdom；最终用权威全文收口 | 可保留焦点、DOM、动画和已完成节点；解析/协议复杂度高 |
| 分块或 token 增量 | LobeHub、OpenCode、Open WebUI、Hermes、DeepSeek Harness | block cache、Worker token、TextToken 复用、网关合批与分段定稿；DeepSeek 以 BlockAssembler 逐 token 装配、block-end 权威整块替换、chunk 运行打包 | 重算范围较小；需要处理 supersede、完成事件和高度缓存；DeepSeek 无 diff 应用层，超大输出经 TextRetainer 尾窗与 spill 两级处理 |
| typed part 流 | Cherry、DeepChat、Jan、Chatbox | parts/blocks 先流入，再由 Markdown 子渲染器处理；部分有 overlay 或 batch | 业务状态稳定；单个 text part 仍可能累计重解析，需实测阈值 |
| 节流但累计全文 | NextChat、SillyTavern、Pi、Risuai | rAF/30 FPS/帧节流；每帧仍处理当前累计文本或整条组件；Risuai 三档性能模式控制后处理与刷新时机，strong 档先纯文本渲染、流结束后再后处理 | 频率受控但成本随正文增长；运行时 DOM 状态较难保留 |
| 直接重放 | AstrBot、Manifold Desktop | 前端或 WebView 以累计文本重渲染；Manifold 无节流且整块 `innerHTML` 替换 | 最简单但长回复、状态保持和安全边界最弱 |
| 非统一多面 | Hermes、VCPToolBox | 事件/工具层合批，具体投影各自收口；VCPToolBox 只转发 | 协议必须携带完成、错误和最终文本，否则各消费者会分叉 |

可复用的工程结论：

1. 先把 token 合帧或批处理，再缩小不稳定尾部；只有节流而不缩小重算范围，收益会随回复长度下降。
2. 最终帧应沿用相同对象/part 身份，避免选择、焦点、滚动位置和脚本状态无故被销毁。
3. 流式期间可以使用简化解析，但结束时应以完整原文或最终事件权威重放，并验证流式/最终输出一致。
4. 持久化频率不应跟随 token 频率；UI overlay、历史事实源和运行状态应分开写入。
5. 对可执行应用，源码 revision 与运行实例生命周期要分离：源码可 patch，运行域可冻结/重载，不能每个 token 都创建新 iframe。

## 投影表面与运行时强度

### 消息内预览

消息内预览的优点是上下文连续：Artifact 与触发它的回答同屏，用户不必管理新对象。Jan、NextChat、Chatbox、LobeHub、DeepChat、AstrBot 都采用这一形态的某种变体。它通常以“从代码围栏或标签探测 -> 卡片 -> iframe/代码视图”实现，适合一次性结果和轻量交互。

缺点是消息列表承担了运行时生命周期。窗口化会卸载对象，流式重渲染会清除定时器和组件状态，删除或编辑消息会隐式改变运行实例。若运行内容拥有真实副作用，必须像 VCPChat 一样增加可见性激活、暂停和资源登记，或像 Open WebUI/Jan 一样将其放入可重建的沙箱。

### 侧栏、工作区与独立窗口

Cherry 的 Artifact webview 与文件 pane、DeepChat 的 Workspace、LobeHub 的 Portal 文档、Hermes 的预览侧栏、AIO 的 web-canvas 把源码/预览从消息列表中分离。这样可以提供更大的编辑空间、稳定的尺寸和更清晰的保存动作，但也引入多视图同步：消息正文、侧栏源码、磁盘文件和运行实例可能是四份状态。AIO 是一个反例：工具页只有项目/Monaco，运行预览在独立 WebView，当前同步仅覆盖 active ID 与文件变更通知，不覆盖错误和 Git 状态。

最稳的事实源顺序是“磁盘/文档 -> 编辑器 -> 预览”，消息只做引用或事件记录。若仍以消息正文为源，应明确保存动作是全文重写、revision 追加还是临时投影；Cherry 的聊天 Artifact 属于前者，DeepChat 的 Artifact 仍主要依附消息文本。

### 桌面与外部环境

OpenCode、Pi、Cherry Agent workspace、AIO canvas、Hermes 文件链把生成式输出带入本机工作环境。其价值在于能使用真实文件、Git、LSP、终端和外部工具；其风险在于执行位置已经离开浏览器沙箱，权限审批、工作目录、子进程回收和错误回流必须成为运行时契约。

VCPToolBox 的 stdio/in-process/WebSocket 节点、MediaRenderer 和 AICodeWorker 是这一层的供给能力。它本身不决定 UI 如何展示、用户是否能编辑或对象能否恢复；这些语义由 VCPChat、Open WebUI 或其他消费者补齐。

## 编辑、版本与模型回流

| 闭环类型 | 代表项目 | 已确认能力 | 主要缺口 |
|---|---|---|---|
| 消息全文重写 | Cherry Artifact、VCPChat 普通消息、AIO 聊天、SillyTavern、Risuai | 用户可改正文、重新生成、重新解析 | 对象 ID、局部冲突、版本和多投影同步弱；Risuai 的 reroll 为内存级版本替换，刷新即失 |
| 文件定向修改 | OpenCode、Cherry workspace、AIO canvas、Pi、Chatbox、Hermes、DeepSeek Harness | read/list/search -> write/edit/patch；部分带 diff/Git；AIO 用不落盘覆盖层预览候选，批准后单次写盘；DeepSeek 以 read/grep 定位 spill 文件、终端按会话 id 定向发送/读取/关闭 | 细粒度 revision、跨客户端锁、运行状态与源码同步不一；AIO 候选层不持久且没有并发冲突合并；DeepSeek 用户不可编辑输出，无 diff 应用层与对象版本，终端会话不持久化 |
| 文档协作 | LobeHub | DB 文档、快照、diff 节点接受/拒绝、编辑锁、Page-Agent | 仍需核实跨设备协作、离线恢复和大型文档性能 |
| 运行对象版本 | Hermes artifact、VCPChat 挂件、Open WebUI output | 重建或切换版本、下载/保存、会话级 output | 多数对象不可被模型列表查询；版本不是统一对象协议 |
| 只读 Artifact | DeepChat、Jan、NextChat、LobeHub Artifact、AstrBot GenUI | 预览、重载、下载或交互 | 无用户编辑写回，无对象级模型维护 |
| 无闭环 | Manifold Desktop | 只有当前 DOM；会话也未可靠落盘 | 保存、恢复、回流均缺失 |

“模型可读取文件”不代表“模型知道某个 Artifact 的状态”。完整回流至少需要：对象列表/稳定 ID、源码或结构读取、运行状态/错误、定向 patch 目标、更新后的事实源，以及下一轮上下文中的版本/冲突信息。当前只有 VCPChat 挂件、OpenCode 文件和部分工作区路线接近这一闭环。

## 能力与安全边界

### 普通正文、声明式组件和代码 Artifact 应分开

普通 Markdown 只需文本、链接、媒体和少量声明式组件；工具、推理、审批、错误和附件最好以 typed part、block 或注册表表达。把它们塞回 Markdown 私有标记，会让渲染器同时承担协议解析、容错、排序和安全清洗。

HTML/JS Artifact 是另一类 sink。下列经验具有跨项目一致性：

- 不可信 `srcdoc` 默认不应同时拥有 `allow-scripts` 与 `allow-same-origin`；Chatbox、Jan、LobeHub、NextChat 的默认隔离更清楚。
- iframe 不能替代宿主安全配置。Cherry、DeepChat 和 AIO 聊天 HTML 的 same-origin 分支，还需结合 webview sandbox、context isolation、CSP、preload 和 IPC sender 校验判断实际边界。AIO canvas 已改为仅 `allow-scripts` 的 opaque origin，并注入专用 CSP、校验消息 source/origin；但其 CSP 仍允许 HTTP(S)、WebSocket、外部 frame 与 asset 资源，不是断网沙箱。
- Open WebUI 的 `injectCsp`、导航拦截、Pyodide/外部终端分域是可参考的拆分方式，但配置项可放宽，不能把默认值当成所有部署的保证。
- VCPChat 主页面脚本和宽能力 widget bridge 属于有意选择的高信任运行时；它适合自由生成应用，不应被当作通用聊天 Markdown 默认方案。
- Manifold 的裸 `innerHTML`、无 sanitizer、无清晰保存收口是下限样本；这不是“轻量架构”的必要代价。

### 本机进程与能力桥

OpenCode、Pi、Chatbox、Cherry、Hermes、AIO、DeepChat 的本机执行都落在 Agent 工具或工作区边界，而不是浏览器 Artifact 本身。必须分别确认：工作目录白名单、命令/工具审批、子进程超时和回收、网络权限、密钥注入、日志回流、后台任务和用户取消。AIO canvas 会校验画布 ID并拒绝绝对路径、盘符、NUL、空段、`.` 与 `..`，再把规范化相对路径拼入项目根目录；符号链接和 Tauri 文件系统特殊路径仍需运行验证。

VCPChat widgetFS/musicAPI/proxy bridge、MCP App 的 `postMessage`/JSON-RPC、Open WebUI 的 Terminal 服务器都说明了同一事实：桥接 API 的方法列表就是运行时权限模型。脚本被放进 iframe 并不会自动限制它能调用的宿主动作；能力应按方法、会话、对象和用户批准拆分，并在执行端再次校验。

## 架构分型

### 1. Parts-first：Chatbox、Cherry Studio、Jan、DeepChat

```text
stream event -> typed part/block -> layout/projection -> Markdown 叶子或工具组件
```

优点是工具、推理、错误、附件和 Artifact 边界清晰，适合自动测试和逐步扩展。Chatbox 路径最短；Cherry 增加了 overlay、registry、文件 pane；Jan 直接承接 AI SDK parts 并用 harden；DeepChat 是 blocks-first 但用正文标签桥接 Artifact/MCP，正则顺序仍是隐式协议。

### 2. Flow/document-first：LobeHub、OpenCode、AIO Hub

LobeHub 先将扁平消息编译成 conversation-flow、AssistantGroup 和文档投影；OpenCode 以事件、ToolPart、SQLite 和影子 Git 组织真实工作区；AIO 在聊天中用 AST，在 canvas 中用文件/Git。三者共同点是先组织工作过程或资产，再决定如何投影，而不是把一段字符串直接塞给 UI。

### 3. String/DOM-first：SillyTavern、VCPChat、Manifold Desktop

字符串路线保留了社区内容、HTML/CSS、宏和扩展兼容性。SillyTavern 将兼容性放在首位，VCPChat 把它推成可执行消息运行时；Manifold 则没有形成可维护的对象和安全契约，适合作为下限对照。三者不能因都使用字符串就视为同一成熟度。

### 4. Event gateway / multi-surface：Hermes Agent、OpenCode、VCPToolBox

Hermes 用 Python 网关向 TUI、桌面、Web 和消息平台发送事件；OpenCode 用服务端 part 事件被 Web/TUI 分别消费；VCPToolBox 负责协议转发和插件执行，最终投影交给外部前端。共同要求是事件必须携带稳定 ID、完成/错误状态、最终文本和可回放信息。

### 5. Token/component runtime：Open WebUI、Pi

Open WebUI 从 marked token 树进入 Svelte 组件，并把代码执行、Notebook 与 Artifact 分成不同运行域；Pi 从 Agent 事件进入终端组件树，Markdown 只生成 ANSI 行。二者都避免把模型 HTML 直接写入主页面，但目标不同：前者是浏览器托管工作区，后者是终端 Agent。

### 6. 平台适配器自治：AstrBot

AstrBot 的上游事实源是 MessageChain，下游 Telegram、LINE、QQ、WebChat 等平台各自决定切块、Markdown、附件和流式策略。它证明了“统一消息语义 + 平台自治投影”适合多 IM 分发，却不提供一个统一的 Artifact 运行时。

### DeepSeek Harness

DeepSeek Harness 属于会话事件日志事实源路线：模型输出的原始形态是闭合的 StreamChunk 七变体流协议（block-start、text/reasoning/tool-call-delta、block-end、usage、finish），agent-loop 把每条 chunk 先落 assistant/chunk 事件再喂给唯一折叠器 BlockAssembler，block-end 携带权威整块，冻结出带 usage 与 sourceEventSeqs 的 assistant/message 落为表面节点；工具结果遵循“规范 JSON 值 + 纯投影渲染”契约，value 只在进程内存在。输出对象分四类身份：消息、工具调用配对、磁盘文件（spill 与 sha256 内容寻址附件）、仅进程内存活的终端会话。持久化默认 JSONL（zstd 帧）或 SQLite。模型回流为每次请求全量派生，经 read/grep 定位 spill 文件、按终端会话 id 定向维护。能力总评 G1，终端 PTY 是 G5 活对象的局部形态。

### Risuai

Risuai 与 SillyTavern 同为角色扮演聊天，走 String/DOM-first：模型自由文本是唯一内容通道，宿主用正则识别 `<ImgGen>`、`<Emotion>` 等标记。输出以消息正文为事实源（G0），唯一获得独立身份的对象是 inlay 媒体资产（G1）——UUID 寻址、独立 IndexedDB 存储、image/video/audio/signature 四类，经 `{{inlay::id}}` 占位嵌入消息，模型可经文本标记或 Gemini 原生媒体返回驱动其生成。模型输出无执行面（eval/new Function 仅在插件系统，iframe 只承载插件 UI 与 YouTube 嵌入），无工作区、画布或桌面挂件。编辑是消息全文覆盖，reroll 为内存级版本替换不落盘；inlay 资产不随主库备份、drive 同步或冷存储迁移。回流是宿主代取式半闭环：提示构建时宿主把图片与签名回注模型上下文，模型自身无资产寻址能力。

## 长会话、资源治理与性能

| 策略 | 项目 | 适用条件 | 注意事项 |
|---|---|---|---|
| 虚拟列表/窗口化 | Chatbox、Cherry、LobeHub、OpenCode | 普通文本和声明式组件 | 高度测量、滚动锚定、流式尾部和对象恢复需要专门测试 |
| `content-visibility`/预算 | AIO、Open WebUI、Hermes 桌面 | 需要保留组件身份但跳过离屏绘制 | JS watcher、定时器和 iframe 仍可能存活；Safari/配置差异需处理 |
| 自定义终端虚拟化 | Hermes TUI、Pi | 行级输出、无 DOM 运行时 | 单条消息更新仍可能重建组件；不能直接类比 GUI |
| 分页/截断 | NextChat、SillyTavern、DeepSeek Harness | 普通聊天、实现成本优先；超长工具结果与 shell 输出 | 超长单消息仍可能昂贵；活动 Artifact 不应被盲目卸载；DeepSeek 以 TextRetainer 只留前缀与单块尾窗、超长结果整体 spill 落盘只给 head/tail 预览，终端/作业持续占用直至关闭 |
| 渐进全量 DOM | VCPChat | 消息本身拥有动画、媒体和脚本副作用 | 必须暂停不可见资源、登记 Worker/Audio/WebGL/timer，并定义恢复语义 |
| 无专门策略 | AstrBot、DeepChat、Jan、Manifold、Risuai | 短会话或当前证据未发现；Risuai inlay 无引用计数/自动回收，blob URL 页面级缓存未 revoke | 长会话性能和资源上限未验证 |

活动运行时的回收至少应覆盖 iframe/WebView、Worker、timer、WebGL、AudioContext、媒体流、WebSocket、子进程和临时文件。仅从 DOM 中移除节点不能证明这些资源已释放；同样，保存源码也不能证明运行状态可以恢复。Open WebUI、AIO、VCPChat 对这些问题分别提供了不同程度的实现，调查笔记仍有若干未运行验证项，不能据此宣布无泄漏。

## 测试与已确认边界

### 证据较强的项目

- **Cherry Studio**：parts、流式 overlay、Artifact 安全和 workspace 相关的自动测试与生产组件证据较完整。
- **AIO Hub**：聊天 renderer 有 AST、Patch、测试台和人工可视化设施；web-canvas 专项测试覆盖路径校验、审批候选覆盖层、HTML/CSS/JS 候选内联、拒绝语义、批量审批和单次正式执行。真实窗口、watcher、CSP、错误回流与 Git 恢复仍没有完整 E2E。
- **OpenCode**：事件、Markdown 分块、工具渲染和虚拟列表有单元/组件测试；没有 UI 渲染基准和通用 Artifact 安全面。
- **Hermes Agent / Pi**：TUI Markdown、流式组件和工具组件测试较多；跨面一致性、终端性能与文件活对象恢复仍不是同一套自动 oracle。

### 静态确认较多、运行验证较少的项目

DeepChat、Jan、LobeHub、Open WebUI、Chatbox、NextChat、AstrBot、SillyTavern、VCPChat、VCPToolBox 的调查主要来自源码与配置静态阅读。尤其需要实测：半截标签/转义、流式与最终一致性、iframe origin/CSP、模型脚本能见范围、保存恢复、错误回流、长会话性能和资源回收。

### 已确认的下限或缺口

- Manifold Desktop：消息不可靠落盘，助手流文本不进入下一轮上下文；裸 `innerHTML` 且无 sanitizer/专用 runtime。
- Jan/NextChat/DeepChat 的 Artifact：执行能力存在，但对象编辑、版本和模型寻址通道不完整。
- AIO/VCPChat：能力面广，但聊天字符串、协议标记、运行时和跨平台路径的耦合使验证成本显著上升。AIO canvas 的旧闭环断点已有对应机制补齐；当前边界集中在候选层不持久、无 revision/冲突合并、单当前画布 watcher，以及真实多窗口/WebView 行为未经 E2E。
- VCPToolBox：执行器和产物记录不等于用户可操作对象；必须由消费者提供对象投影与编辑语义。

|---|---|---|---|

| 编码 Agent / 项目维护 | OpenCode、Cherry workspace；AIO canvas 提供 Physical-First + 候选覆盖层参照 | 文件/Git 事实源 + 基于 revision 的工具审批 + diff/回滚 + 预览隔离；DeepSeek Harness 的会话事件日志事实源、检查点屏障与 spill 溢出策略可作参考 | 只把源码塞进消息 Markdown；把瞬时预览层误当成可恢复 revision |

| AI 运行时供给层 | VCPToolBox | 插件 job、能力桥、产物事件与前端对象协议分层 | 把服务端执行记录当成最终 UI 对象 |

## 推荐的组合架构

若新项目同时需要结构化聊天、可运行 Artifact 和长期项目维护，建议采用两个事实域、三个对象层：

```text
模型/工具事件
  -> 顶层 part IR（prose / reasoning / tool / file / app / media）
  -> 消息投影（稳定 ID、流式尾部、可折叠状态）
  -> app runtime（独立 realm、revision、能力桥、运行状态）

file/document part
  -> workspace（物理文件或文档 DB）
  -> diff / version / lock / rollback
  -> read / patch / error 回流模型上下文
```

### 结构化边界

旧 VCP 或标签协议可以保留兼容 adapter，但只在入口处编译一次为顶层 part；后续 renderer、流式和交互不再反复扫描原始字符串。`app` part 只描述文档源、资源、revision 和权限档位，不把任意 JavaScript 翻译成大量业务 AST。

### 运行域与能力档位

| 档位 | 默认能力 | 适用对象 |
|---|---|---|
| `prose` | Markdown、媒体、声明式组件；不执行模型脚本 | 普通回答、工具结果、引用 |
| `active` | 独立 realm 内脚本、Canvas/WebGL、可选网络；无宿主原生 API | 可交互 Artifact、图表、小应用 |
| `trusted` | 版本化 runtime SDK，可请求文件、工具、会话事件和持久化；每项仍由宿主校验 | 用户明确创建的 Agent 工作区/挂件 |

脚本不应直接取得 Electron/Tauri 完整 preload、任意文件系统或密钥对象。即使产品选择 VCPChat 级自由度，也应让桥接方法成为稳定契约，并由宿主负责对象身份、权限、可见性、持久化和资源回收。

### 流式、保存与恢复

`prose` 使用 stable/pending AST 或尾部 block；`app` 在边界稳定后创建一个 runtime，后续以 revision 更新同一实例。保存采用低频快照或文件写入，结束事件包含最终源码/状态/错误；重载时先恢复源码与对象元数据，再决定是否恢复运行状态。长列表卸载普通消息，活动 app 进入最近使用池、冻结快照或 `serializeState()/restoreState()`，不能静默丢失交互状态。

## 最终判断

如果只需要稳定聊天和少量交互，Cherry Studio、Chatbox、Jan、NextChat 的低权限 Artifact 经验足够；如果核心是 Agent 工作过程，LobeHub 的 flow/registry 和 Cherry 的 parts/overlay 更值得借鉴；如果核心是代码与项目，OpenCode、Cherry workspace 的闭环证据更强。AIO canvas 的 Physical-First、候选覆盖层、外部文件监听和独立项目 Git 也提供了可复查样本，但 revision、冲突合并与完整窗口 E2E 仍不在当前能力内。

如果目标是“模型可以生成一个持续运行的小应用”，VCPChat 的能力目标最完整，DeepChat/NextChat 提供较轻量的 iframe 入口；AIO 提供项目文件、独立预览和错误回流，静态代码已经形成“修改 -> 预览 -> 报错 -> 再修改”链，但真实窗口时序和 WebView 行为尚未端到端验证。VCPChat 的桌面挂件是本样本中最接近 G5 的机制，同时也是最需要显式权限和资源治理的机制。

横向上最稳定的共识是：**先确定事实源和对象身份，再选择运行时；先区分普通正文、工具、文件和 app，再谈 Markdown 或 Artifact；先定义流式最终一致性和回收，再谈“实时”。** 结构化 parts、文件/Git 工作区和独立 runtime realm 可以组合成一套可迁移底座；自由文本协议仍可作为兼容入口，但不应继续承担全部对象、权限和生命周期语义。
