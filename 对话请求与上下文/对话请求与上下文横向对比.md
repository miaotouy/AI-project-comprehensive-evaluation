# 对话请求与上下文横向对比

> 对比对象：AIO Hub、AstrBot、Chatbox、Cherry Studio、Codex、DeepChat、DeepSeek Harness、Dify、Hermes Agent、Jan、LobeHub、Manifold Desktop、NextChat、Open WebUI、OpenClaw、OpenCode、OpenOcta、Pi、RikkaHub、Risuai、SillyTavern、VCPChat、VCPMobile、VCPToolBox
>
> 对比更新日期：2026-11-05
>
> 依据：文末来源表的 24 篇单项目笔记，并结合相邻会话与工具专题；采用截至 2026-11-05 的静态证据，调查日期与代码版本按各篇元数据区分，未做运行验证
>
> 对比方法：按 SDK/主链归属、消息构建、流式持久化、中断层级、任务并发等共同维度逐项对照；未被单项目笔记共同覆盖的项单独标注范围
>
> 对比范围：SDK 使用与聊天主链、消息构建与上下文拼装、流式持久化、中断与取消、执行层技术债；会话数据语义在会话与消息管理横向对比，界面工作流在 Chat UI 横向对比
>
> 文档定位：实现学习与跨项目横向比较，不作为整改方案

## 结论摘要

- **"使用 SDK"限定在消息生成和流式组装的主链**，UI 框架与可选插件另属其他层。同为 OpenAI-compatible 请求的项目可能各自接入不同 SDK；SDK 选型实际在决定"谁是消息的规范拥有者、标准化发生在哪一层、Agent 是否被视为普通消息的扩展、短期接入速度与长期语义控制的交换、故障应归因到哪里"。
- **只比较"是否有上下文"不足以区分实现**：客户端应用、主进程 runtime、Agent 后端、Web 服务和请求编排网关都可能负责最终输入的一部分。Manifold Desktop 的历史数组没有回写 assistant 流，因此第二轮请求仍缺少上一轮回复。
- **"UI 立刻刷新"和"完成态落盘"的时序，各项目并非都实现了两层缓冲**：从数据库 block、WebSocket delta 到纯 DOM 更新覆盖了多种形态；SillyTavern 与 Manifold Desktop 没有独立的流式缓冲层。
- **中断/取消生成至少分三层**：按钮停止、任务取消和请求中止不是同一层。VCPChat 仍是"同一产品两条路径不对称"证据最完整的案例；中断表逐项列出全部对比对象，未追至中断层的项目明确标为“未调查/无法确认”，不能从按钮存在推断请求已被中止。
- **客户端会话与服务端插件历史并存（VCPToolBox）**：它在单次请求内重写输入，客户端持有会话导航；OneRing 另存跨请求消息及回合，HTTP 完成和异步入库时点分开。
- **DeepSeek Harness 从会话日志派生模型历史**：v4 有 system、developer、user、assistant 与 tool 五类表面消息，请求头保存配置和工具，模型尝试各有耐久收口。压缩、图像卸载与结果 spill 是可选扩展；spill 按文本与图像的估算 Token 留存，恢复材料不可用时保留原内容。调用适配与循环编排保持分层（[来源](<./DeepSeek-Harness-对话请求与上下文调查笔记.md>)）。
- **Risuai 以"累计全文块 + 整段替换"表达流式状态，半截流也会落盘**：Provider 流把每块的累计全文放进单一键，消费端整段替换并按 125ms 定时器 + requestAnimationFrame 合帧；而流式占位消息在请求前就写入会话，全局保存循环 500ms 防抖持续落盘，因此半截消息也会随保存写入磁盘，与"流结束才落定"的实现不同。流长度由空闲超时约束；保存走块级增量编码，非响应式键值单独放进 `kv:<namespace>` 块。
- **Risuai 的并发是"无任务对象的全局单任务"**：没有独立的取消令牌、任务注册表或队列对象，`doingChat` 锁与 UI 检查直接拒绝新的发送；群聊成员在发送入口内按 talkness 排序逐个串行生成。停止只发生在本地消费层，桌面端网络请求无取消命令，继续到完成或 240 秒超时。
- **OpenClaw 把一次可见对话拆成"ACK 前准入"与"ACK 后 detached dispatch"两段**：`chat.send` 在 ACK 前同步确认身份、幂等、附件与取消边界并写 pending dedupe，ACK 只承诺稳定 run id；用户 turn 随后交给脱离 RPC 生命周期的 dispatch，经 auto-reply 管线进入嵌入式 Agent 运行器，assistant turn 由运行器直接写回 transcript，Gateway 只投影 live reply，非 Agent 回复与媒体补写另走 finalization 避免重复 assistant 行。上下文来源分层（transcript 恢复 + workspace/skills/memory + 可选 Context Engine），预算分"只记录状态的预检"与"实际压缩恢复"两层。

- **路径级排队与请求中止分属两层**：AIO Hub 将等待生成的消息持久化为 queued 节点，目标路径空闲后才按模式继续；它保证同一路径有序、分支可并行，取消由独立的取消协议承担。Chatbox 的 Work Mode 队列把待处理条目（最多 20 条）写入 localStorage 跨刷新保留，steering 消息先持久化为 `steered` 用户消息再进入当前生成的后续 step，取消同样走请求中止层。VCPChat 通过 bridge 和 coordinator 回收旧 surface 的流投影，主要解决事件交付与最终化顺序，远端 interrupt 仍由网关协议承担。
- **没有独立消息表时，"日志是否承载过程"决定压缩能否回放（Codex / OpenOcta）**：Codex 把模型项与协议事件一并写进 rollout，压缩以 `Compacted` 记录重写后的替代历史，恢复时可以重建；OpenOcta 只追加回合结果——用户行、每轮 assistant 行、工具结果行，取消时再补快照，运行中摘要写到独立转录文件、不回流会话。两者的权威历史都在文件里，差别在前者是"可回放的过程日志"，后者是"结果日志"。
- **同会话并发取决于准入与运行时生命周期（Codex / OpenOcta）**：Codex 在 turn 提交判定处把新输入并入当前轮或拒绝；OpenOcta 的网关请求先等待旧运行时，首段 30 秒超时后删除池映射，旧运行尚未释放时可另建实例。后者的抢占标记作用于池映射的删除与实例重建，旧轮是否真正中断取决于运行时释放时机；同键严格串行也存在边界；聊天页的客户端排队是独立层。

- **生成主链从界面层移向可独立调度的一层（Chatbox / Pi / OpenCode）**：Chatbox 的编排与流式增量处理进入 `packages/chatbox-core`，生成任务、阶段推进与 chunk 状态机分成三个模块，渲染端只保留组合根；Pi 的 durable 链以提交记录、phase 与 checkpoint 取代常驻 lane，提交先落盘再执行，重启从 checkpoint 恢复，未结算工具按安全重放策略处理；OpenCode 的 Runner 逐轮推进，每步用 `Outcome` 标记完成、输出上限、压缩、恢复、重试与续写。
- **RikkaHub 把请求组装、循环与收尾拆到三处**：`ChatRequestFactory` 负责上下文与工具装配，`AgentLoop` 负责步骤循环与审批，`finishGeneration` 把完成、取消、失败的回合统一写回；压缩改为插入检查点而非替换历史。
- **日志投影口径在细化（DeepSeek Harness / Codex）**：DSH 的 v4 投影把工具结果作为 tool 角色消息，循环把工具调度交给 `ctx.tools.execute()` 的执行器接缝；Codex 的压缩记录带窗口 id，`for_prompt` 按模型模态剥离不支持的图片与音频。
- **恢复与流控按层拆分（VCPMobile / Risuai）**：VCPMobile 分三层恢复——进程内重连、重启读活动记录、被系统回收后用离线完成文件补交终态，WebSocket 另有独立活动策略控制心跳与重连退避；Risuai 把固定总时长改为空闲超时，保存格式用 `kv:<namespace>` 块承载非响应式键值，只在命名空间变化时重编码。

## 项目概览

### DeepSeek Harness

请求历史从 v4 日志的五类表面消息派生，系统提示也先协调到表面；每步固定模型选择后才准备请求，后置请求改写只调整控制项。实时 chunk 在结束时内嵌于成功消息或非表面 attempt，工具调度经执行器接缝完成。压缩与 spill 为可选扩展，spill 以文本和图像的估算 Token 合算，基座默认约 12500 Token。其取舍是让请求可从事实日志解释，同时承担投影与插件组合的边界（[来源](<DeepSeek-Harness-对话请求与上下文调查笔记.md>)）。

### Risuai

一次生成由统一入口 `sendChat` 驱动，没有独立任务对象：运行状态是全局锁、阶段进度与调用方中止信号的组合，任务权威记录是写回消息的 `generationInfo`。上下文按提示词模板卡片逐项预检 token 装入分组桶、再按卡片顺序拼装；预算以全局 `maxContext` 为上限，启用记忆时由四套记忆引擎之一截断或摘要，否则从头部整条删除。Provider 交接在统一的 `requestChatData` 分发层完成，各 Provider 独立解析 SSE 并把累计全文放进单一键的流式块，消费端整段替换并按 125ms 定时器 + requestAnimationFrame 合帧。流式占位消息在请求前写入会话，500ms 防抖的全局保存循环持续落盘，因此半截流也会被保存；停止只发生在本地消费层，桌面端网络请求无取消命令，继续到完成或 240 秒超时。并发为全局单任务：`doingChat` 锁直接拒绝新发送，群聊成员按 talkness 排序串行生成。

### OpenClaw

一次可见对话的主链是 Gateway `chat.send`：请求先规范化并解析会话，准入阶段写 pending dedupe、占用同会话运行槽并注册 abort owner，ACK 前同步确认身份、幂等、附件与取消边界；ACK 后把 turn 交给脱离 RPC 生命周期的 dispatch，经 reply dispatch 进入嵌入式 Agent 运行器。attempt 从 per-agent SQLite 恢复 active branch，按历史 sanitize → 预算预检 → Context Engine assemble（可选）→ system prompt 组装 → 工具目录构建 → AgentSession.prompt 的顺序进入 Agent Core 的工具/回合循环；assistant 由运行器经 SessionManager 写回同一 transcript，Gateway 只把实时 chat/agent 事件投影给订阅面。模型请求只在 Gateway 所在主机发起，各聊天表面与外部消息渠道不直连 Provider；普通 attempt 与非 OpenClaw harness/plugin 的交接由 backend 选择接管。

### RikkaHub

一次生成仍由 `ChatService` 编排：每会话对应内存中的会话对象，输入先入队列由调度器串行取出，同一会话不并行、不同会话各自并行。请求侧集中到 `ChatRequestFactory`——合成 system 消息（生效系统提示、记忆目录、各工具系统提示）、按条数做滞回截断并对齐工具对、再穿过输入变换管道，最后交给 `ai/agent/AgentLoop` 的步骤循环；循环把工具结果写回助手消息 parts，审批未决时以事件挂起，默认步数上限 256。压缩不再替换历史，而是插入一条检查点消息并记录最近上下文 token，旧消息保留。收尾统一走 `finishGeneration`：完成、取消、失败三种结束都会把内存态写回会话，等待审批与步数耗尽各自有结束原因；流式增量只更新内存态，取消经协程传播到 Provider 的 `callbackFlow`。

### Codex

一次生成从 turn/start 进入 app-server，转换为核心的 turn 提交 Op，由单一判定点决定"开始新轮、并入当前轮或拒绝"。上下文不是拼成一条 system prompt 后直接发请求：先把世界状态按固定顺序（工具声明、模型指令、token 预算、AGENTS 与权限、模式、环境、工具命名空间、多 Agent 与目录）作为片段写入历史，首轮全量、后续只写与上一基线的差异；base instructions 另走请求的独立字段。压缩是重写历史——摘要加真实用户消息形成替代序列，初始上下文重新插到最后一个真实用户消息之前，并以 Compacted 记录落盘，旧历史只是不再可见。同线程严格串行，一次采样结束时统一等待在途工具，轮末 flush 之后才结束本轮。每步选搜索提供方并据此收窄目录，线程所有者只排斥另一提供方，同提供方调用可共享预留；压缩落盘的 `Compacted` 记录携带窗口 id，`for_prompt` 再按模型模态剥离不支持的图片与音频。

### OpenOcta

一次生成由 WebSocket 方法调用交给后台运行，进度以 chat 事件推送。模型输入来自运行时系统提示、员工覆盖与当前转录；本轮文本先写入转录，网关未水化历史时，下层仍会按路径补读，无法读取且没有可用消息则可能终止回合。预算按模型窗口，清理与摘要在运行时执行，摘要不回流会话 JSONL。

网关再次发送会先等待旧池条目，首段 30 秒超时后删除映射并允许另建 Runtime；旧实例可继续运行至释放锁，因此池内互斥只约束同一条目。显式取消分 TurnLoop 停止与上下文取消两层，聊天页内存排队与网关直接发送的并发行为应分别理解。

## SDK 使用与聊天主链

| 项目 | 主链中的 SDK / 协议封装 | 对会话与消息模型的影响 |
| --- | --- | --- |
| AIO Hub | 自研 LLM Core、VCP 文本协议与可重放流源 | `ChatSessionDetail` 和树形消息节点由应用定义，流式状态由 AST/Patch 体系承接 |
| AstrBot | Python 自研事件总线、九阶段流水线与 Agent runner | OpenAI 格式历史只是持久化载体；会话顺序、唤醒、follow-up 和压缩语义由 AstrBot 流水线控制 |
| Chatbox | 调用层使用 Vercel AI SDK；编排与流式增量处理迁入 `packages/chatbox-core`（生成任务、阶段推进、chunk 状态机三个模块） | SDK 归一化 Provider 流，生成主链与流式状态机归 core 包，渲染端只保留组合根；历史、分支和持久化仍是应用自己的 Session 模型 |
| Cherry Studio | Vercel AI SDK `UIMessage` / `readUIMessageStream`；Agent 会话另走 Claude Code SDK | `UIMessage.parts` 是普通聊天的结构化消息契约，Agent Session 有独立持久化路径 |
| Codex | 不用 OpenAI SDK：经 `codex-api`/`codex-client` 构造 Responses 请求，WebSocket 优先、失败回退 HTTP，一次 turn 复用同一客户端以保留粘性路由 | 历史是 rollout 日志的投影，恢复时从日志重建；增量工具模式下工具声明与 base instructions 改由历史区块提供，压缩与世界状态也必须能随日志回放 |
| DeepChat | main process 内的自研 Session/Agent runtime 与 typed IPC | transcript、assistant blocks、pending input 和 Provider 流由主进程统一管理，renderer 只维护投影与缓存；另有无头 CLI 控制平面与 renderer 共用同一主进程 runtime 和审批 broker |
| DeepSeek Harness | 插件化自研循环与可替换 LLM 适配层；Web 经类型化 Remote 调宿主 | v4 日志五类表面消息派生历史；系统提示表面化，请求头保存配置/工具；每次成功或失败尝试均有耐久收口，客户端重放投影 |
| Dify | service API + `AppGenerateService` 按 AppMode 分派，公开聊天消费 SSE | Conversation/Message、workflow run 与 task ID 由模式专属 generator/runtime 创建；浏览器只维护临时树与事件投影 |
| Hermes Agent | Python `AIAgent` + JSON-RPC/WebSocket 桌面协议 | 后端 SQLite 是真相源；桌面按 stored session id 与 lineage root 匹配会话，压缩轮转后 root 标识保持稳定 |
| Jan | Vercel AI SDK `useChat` + 自研 `CustomChatTransport` | UI message、ThreadMessage 和文件/SQLite 持久化模型之间显式转换，transport 掌管上下文和 Provider 参数 |
| LobeHub | 自研 ModelRuntime、消息 Store 与 `conversation-flow`；`packages/mecha` 提供 client agent 与 Gateway 共用的上下文工程内核 | Provider 调用与 DB 消息分层；展示路径由 flow 从消息记录重建；发送入口集中在全局 `conversationLifecycle.ts`（局部 `sendMessage.ts` 只剩前置检查与转发），`/compact` 与 `/goal` 命令经 Command Bus 处理；Gateway 事件按内部 Promise 串行处理以保证顺序，实验开关 `enableGatewayMux` 按 owner 复用同一 Gateway 连接 |
| Manifold Desktop | WebView2 `postMessage` + C++ Provider 流式桥 | 前端 `messages[]` 与 C++ 会话文件 API 未接通，assistant 流只更新 DOM，未形成完整会话模型 |
| NextChat | Zustand 会话状态 + 自研 Provider adapter/SSE 回调 | 单一 `ChatSession[]` 同时承载消息、Mask、摘要、工具状态和流式占位，没有服务端 conversation runtime |
| Open WebUI | FastAPI 中间件/Provider 适配 + Socket.IO 事件协议 | 服务端同时维护 history JSON 与消息行，约 25 类事件统一承载内容、状态、任务和工具交互 |
| OpenCode | 服务端 `SessionPrompt`/`SessionProcessor`/`SessionRunner` + Vercel AI SDK `streamText`；SSE 事件协议 | SQLite 是权威源，`message.updated`/`message.part.updated`/`message.part.delta` 事件经 SSE 广播，App 以 16ms 批量 flush 投影到 Solid store，TUI 同协议订阅；Runner 逐轮推进，步骤结果用 `Outcome` 枚举区分完成、输出上限、压缩、恢复、重试与续写 |
| OpenOcta | 自研 WebSocket 网关 + Eino 运行时编排；模型工厂按 provider 分派 Anthropic Messages 或 OpenAI 兼容适配器（内置 25 家条目） | 会话不是内存对象，每轮从 JSONL 水化；消息拼装、落盘与广播顺序由网关 handler 统一控制，摘要与主体历史分文件 |
| Pi | 自研 `AgentSession` + `agent-loop`，Provider 调用走 `packages/ai` 统一流接口；另有 `durable` 链处理提交、phase 与 checkpoint | JSONL 会话树由应用定义；durable 链把输入拆成接纳与执行两层，每个 phase 结束存 checkpoint，重启从最后 checkpoint 恢复；默认 coding-agent 仍走 `AgentSession.prompt()` |
| RikkaHub | 自研 `ChatService` 编排，请求组装在 `ChatRequestFactory`、步骤循环在 `ai/agent/AgentLoop`、重试策略在 `Retry`；Provider 是无状态接口，走自研 SSE 解码（OpenAI、Google、Claude、ChatGPT、Grok 五类，OpenAI 兼容再分 Chat Completions 与 Responses） | 消息模型由 `ai` 模块的 `UIMessage`/parts 定义；会话状态与生成 Job 归 `ChatService`，`finishGeneration` 统一写回完成/取消/失败三种结束，Provider 只做协议适配、不持有会话 |
| Risuai | 自研统一入口 `sendChat`，无独立任务对象；Provider 交接在 `requestChatDataMain` 的 LLMFormat 分发 | 消息模型由应用定义，任务权威记录 `generationInfo` 写回消息；各 Provider 独立解析协议，Rust 端只做字节转发 |
| SillyTavern | Provider 专属请求分支和浏览器/后端 `fetch` | `chat[]` 与 JSONL 格式不依赖统一消息 SDK，兼容语义由本地字段与扩展维持 |
| VCPChat | 自定义 VCP IPC/文本协议，单次 `fetch` 到网关 | Topic `history.json` 保存原始消息和上下文，VCP 标记在客户端解释 |
| VCPMobile | Rust 应用服务、VCP payload 与 SSE Channel | SQLite 消息与活动请求记录为本地事实源；前端仅维护流式投影 |
| VCPToolBox | 自研请求预处理与 VCP 工具递归 | 客户端拥有导航和分支，OneRing 可另存插件消息/回合历史；HTTP 完成与异步入库分开 |
| OpenClaw | 自研 Gateway 协议 + 自研 Agent Core / embedded-agent-runner；无通用消息 SDK，Provider 走自研 transport/stream（非 OpenClaw harness 由 `runAgentHarnessAttempt` 接管） | assistant turn 已由运行器写入带 `parentId` 的 transcript，Gateway 只做 live reply 投影；非 Agent 回复、媒体补写与 abort partial 走专门 finalization 路径，会话/消息模型由应用定义 |

### SDK/自研边界意味着什么

上表描述的是代码事实，下面只做基于这些事实的设计推断。这里的"意味着"不是项目作者的明示动机；它表示这种边界通常会把哪些责任放在应用内，以及会带来什么代价。

| 项目 | 更像是在做的设计决策 | 换来的能力 | 主动承担的成本 |
| --- | --- | --- | --- |
| AIO Hub | 把消息协议、会话树和可重放流作为产品主链，自研完整实现 | AST/Patch、VCP 文本协议、树形会话和流式恢复可以共享一套语义；第三方 Provider 位于适配层 | 需要自行维护协议、错误语义、流式边界和兼容层；外部 SDK 的新能力不会自动进入主链 |
| AstrBot | 把跨 IM 平台的消息处理建模为事件流水线，不承担桌面聊天页面职责 | 九阶段管线、UMO 锁、follow-up 严格序和插件阶段可以独立演进，适合多平台群聊与机器人场景 | 事件任务全局无背压；洋葱式异步生成器增加异常栈和收尾时序的理解成本 |
| Chatbox | 只在 Provider/流式调用层借力，产品数据模型仍由应用拥有 | 以较低成本统一多 Provider 的流事件，同时保留 `Session`、`Thread`、`Fork` 和 `contentParts` 这些产品语义；替换 Provider 不必改写会话存储 | SDK 的输出要映射到自定义消息模型，形成"SDK 契约 + 应用契约"两层边界；工具调用、压缩和分支越复杂，适配代码越多 |
| Cherry Studio | 普通聊天和 Agent 采用不同 SDK，按交互复杂度拆分协议 | 普通聊天可直接使用 `UIMessage.parts` 的结构化流；Claude Code SDK 可以单独承载 Agent 的工具、审批和执行生命周期，不必把 Agent 事件硬塞进普通消息 | 两条主链和两套持久化语义需要明确转换边界；跨模式复制、搜索、恢复和 UI 展示容易出现不一致 |
| Codex | 把模型项与协议事件写进同一条本地日志，再用 SQLite 投影加速列表与分页 | 可整文件回放、可直接用文本工具检索、恢复时同时重建模型输入与 UI 历史 | 需要维护投影表、迁移子系统与回退时的指针切换；日志只增不减，检索和列表都依赖扫描或旁路索引 |
| DeepChat | 让主进程拥有 session、transcript、Agent 和 Provider runtime | pending input、工具交互、流式 block、搜索和持久化能共享一个有序 transcript；renderer 可专注窗口化展示 | main/renderer 间的 revision、cursor 和 IPC 事件顺序成为额外一致性边界，崩溃恢复与乱序行为仍需运行验证 |
| DeepSeek Harness | 把请求组装、历史派生与能力扩展全部放在自研事件运行时，SDK 与协议适配只留在最外层 | 上下文、compaction、spill 等能力以插件/瀑布形式挂接而不改主链；请求头与消息可重放、可从日志重建，"模型可见即已落盘"降低状态同步面 | 事件日志只增不减，定价需重放折叠；可选 seam 的组合正确性依赖 base 组合与瀑布注册顺序，能力需自行挂载才生效 |
| Hermes Agent | 让跨界面的 Python Agent 后端作为权威状态源 | CLI/TUI/桌面复用同一会话与工具能力，lineage root 可跨压缩轮转稳定引用会话 | 会话句柄（sid）与持久 session id 两类身份需要翻译，压缩轮转后按 lineage root 重锚；前端本地定稿与后端中断检查处在不同层 |
| Jan | 用 AI SDK 承接流式 UI，用自研 transport 保留本地模型和上下文控制 | 桌面/移动端共享前端逻辑，仍能注入本地 Provider 参数、附件清洗、压缩和树形版本 | UI 消息、持久化消息和 Provider 请求存在多次转换；桌面 JSONL 每次整文件重写，未完成回合不恢复 |
| LobeHub | 将 Provider SDK 留在适配层，自建 ModelRuntime、Store 和 flow | 可以把模型调用、权限、工具执行、消息持久化和展示投影按自己的运行时编排；适合把 Agent 过程记录为可观察流程 | 需要长期维护 Provider 适配和运行时抽象；transcript 副本与单向镜像需要维护作用域身份、翻页窗口和引用稳定性 |
| Manifold Desktop | 保持前端与 C++ Provider 桥尽量薄 | 请求链短，前端标签页可直接驱动 Provider 流 | 会话存储 API 没有接入正常聊天主链，导致回复不回写上下文、多标签共享广播和重命名覆盖等基础一致性缺口 |
| NextChat | 把会话、摘要、工具和请求编排集中在一个客户端 store | 部署简单，IndexedDB/localStorage 即可保存完整本地状态，Provider adapter 可在同一状态机内处理工具回注 | 单 store 承担较多职责；token 估算、摘要质量、多端同步和工具结果复用都有各自的未验证边界 |
| Open WebUI | 把聊天建模为服务端协同系统，而非单机状态容器 | 权限、分享、归档、多模型、任务取消、工具交互和跨实例事件可以统一落在后端 | history JSON 与消息表双写需要持续对账；Socket.IO 事件协议和大型前端状态机扩大了状态组合面 |
| SillyTavern | 优先保证 Provider 和社区扩展的开放兼容，不设统一消息 SDK | 可以容纳 text-completion、OpenAI messages 及大量非标准字段，扩展可直接介入请求、正则、World Info 和存储格式 | 请求分支、字段语义和生命周期由本地约定拼接，类型保证弱；新增 Provider 往往意味着新增分支，长期容易产生行为差异和回归面 |
| VCPChat | 把客户端定位为 VCP 协议的呈现与交互端，把编排能力放到网关 | 客户端可以保持较薄，Topic 历史保存原始消息，网关和客户端可相对独立演进；VCP 标记可作为扩展协议承载工具/群聊能力 | 协议契约主要靠约定和客户端解释，标准 SDK 的互操作性、类型校验和错误归因较弱；网关行为不透明时，客户端难以单独诊断完整请求链 |
| VCPToolBox | 将请求级编排与客户端会话导航分离 | 一次请求内完成协议桥接、预算与工具递归；OneRing 可补充长期插件历史 | 客户端历史、插件记录和 HTTP 结算有各自提交时点，需分别解释恢复边界 |
| OpenCode | 把会话、消息、工具状态和事件流全部放在服务端运行时，Web/TUI/CLI 只是同协议的客户端 | SQLite 权威 + 事件广播，多前端共享同一会话语义；发送、中断、重试、压缩都在服务端闭环 | 前端必须消费 SSE 事件投影，协议版本（v1/V2 协商）影响客户端复杂度；本地纯离线场景仍依赖本地 server 进程 |
| OpenOcta | 文件保存转录，池化 Runtime 持有执行态 | 数据布局直观，可从转录重新水化 | 池配置捕获、旧 Runtime 驱逐与索引无锁读改写是独立一致性边界；崩溃损失范围未运行验证 |
| Pi | 把消息协议、工具循环和会话持久化全部放在本地 Agent 运行时，交互模式只是 I/O 层 | CLI/TUI/print 共享同一 AgentSession；事件驱动 + 单 agent 循环语义统一 | 需要自维护流式事件、压缩、重试与终端渲染；多会话并行生成不在设计内 |
| RikkaHub | 把会话状态、内存队列与 Step 循环放在应用层运行时，`ai` 模块只做无状态协议适配 | 会话内存态、工具审批与多 Provider 协议可各自演进；替换 Provider 不改会话模型，截断点在一段轮次内不动以稳定请求前缀 | 需自维护 SSE 解码、流式合并、条数截断/手动压缩与重试；停止只到协程取消，底层网络是否即时中断未验证 |
| Risuai | 把一次生成的请求编排、消息构建与记忆预算全部放在自研 TS 主链，Provider 只做独立协议分支 | 模板卡片分桶、四套记忆引擎与角色兼容共享同一编排；任务记录写回消息，不需要单独的任务状态同步 | 没有任务对象，并发只能靠全局锁拒绝而不排队；桌面端停止命令到不了网络层，只能中止本地读取，服务端继续跑完或超时 |
| OpenClaw | 把请求准入、运行身份、工具循环与 transcript 持久化集中在本地 Gateway/Agent runtime，自有聊天表面与外部消息渠道都只是输入/显示面 | 多个表面（Web/TUI/原生/渠道）共享同一会话语义、幂等与恢复；模型请求只在 Gateway 所在主机发起，Provider 差异留在 transport/harness 层 | 每类输入都要消费同一事件、幂等与断线恢复协议；ACK 后 detached dispatch 使终态 cleanup 落在请求生命周期之外，普通消息与渠道消息的入口形态需要两套适配 |

### 横向看，SDK 选型实际在决定什么

1. **谁是消息的规范拥有者。** Chatbox、Cherry Studio、Jan 把 SDK 当作调用层契约，Session/Topic/Thread 仍由应用定义；AIO Hub、LobeHub、DeepChat 把规范放在自研运行时；Hermes Agent、Open WebUI 放在独立后端；SillyTavern 和 VCPChat 则依靠原始消息与扩展字段/协议标记。这个边界影响历史数据能否脱离当前 Provider 解释，也影响接入新 Provider 时只需增加适配器，还是要增加一套请求分支。
2. **标准化发生在哪一层。** 调用层标准化（Chatbox、Cherry Studio、Jan）主要处理 Provider 流差异；主进程/运行时标准化（LobeHub、AIO Hub、DeepChat）还统一工具、上下文和展示投影；AstrBot、Hermes Agent、Open WebUI 分别把这类职责放在事件流水线、Agent 会话后端和协同服务中；VCPToolBox 统一请求编排，客户端导航与 OneRing 插件历史分别持有。仅看依赖中是否出现 SDK，无法判断系统的标准化范围，比较时要先区分所在层级。
3. **Agent 是否被视为普通消息的扩展。** Cherry Studio 选择单独的 Claude Code SDK；DeepChat 把 Agent turn、pending input 和工具交互变成主进程 transcript 的一部分；Hermes Agent 让子代理本身成为真实子会话；LobeHub/AIO Hub 在自研运行时中统一承接；SillyTavern/VCPChat 则通过字段或协议标记扩展。它们对审批、工具步骤、恢复状态和子会话可见性的表达能力并不相同。
4. **短期接入速度与长期语义控制的交换。** 成熟 SDK 可以减少 Provider 适配工作，但项目需要接受其事件模型和升级节奏；自研主链可以按产品语义设计消息树、流式落盘和工具循环，同时承担兼容性、测试和迁移责任。SillyTavern 的多分支兼容、AIO Hub 的协议一致性，分别体现了这两种取向。
5. **故障应归因到哪里。** SDK 边界清晰时，可以把 Provider 错误与应用状态错误分层定位；协议/网关自研较多时，错误可能发生在消息重写、标记解释或递归工具循环中。排查这类问题需要同时保留原始请求、转换后请求和执行快照，否则很难定位模型输出偏差的具体环节。

评估 Chat 应用的 SDK 使用情况时，应比较五件事：**规范消息由谁定义、流式事件在哪里归一化、工具和 Agent 生命周期由谁承接、会话数据能否脱离当前 Provider 恢复，以及失败时能否观察到每次转换。** 这些问题比依赖名称更能解释架构取向。

## 消息构建：历史如何转换为模型输入

| 项目 | 进入构建器的历史 | 注入、裁剪与最终模型输入 |
| --- | --- | --- |
| AIO Hub | 目标叶子到根的有效路径；启用摘要遮罩原消息，保留工具原角色供编译定位 | 11 个可配置处理器依次完成历史、异步结果、正则、转写、世界书、预设、Recall、变量、预算、格式化与附件处理。预设组合正文先编译再展开宏，历史锚点避开工具调用/结果区间；自动工具定义与运行环境、自动 Recall 可动静分离，显式布局保留。虚拟文本附件和本地媒体投影到请求副本，原资产与权威消息树保留；真实缓存收益需上游 usage 验证 |
| AstrBot | 当前 conversation 的 OpenAI 格式历史；群聊还可取 UMO 环形原始消息 | 压缩字段（`overflow_strategy` 默认 `llm_compress`、`max_turns`、`keep_recent_ratio`）来自 Local runner 的 `agent_runner.config` 档案，普通聊天、cron 调度台与压缩子任务可用不同默认值；先轮次截断，再在 82% token 阈值触发摘要或按轮截断，仍超限时折半；persona、知识库结果和群聊 `<system_reminder>` 另行注入；图片在模型调用前经统一的 `prepare_request_images` 阶段按最长边与 JPEG 质量转换 |
| Chatbox | 目标 assistant 之前的当前 Session/Thread 消息 | `buildContext` 处理压缩点、附件与最大上下文消息数；知识库、网页浏览和 Agent Mode 注册为工具，随后注入 system instructions 并转换为模型消息 |
| Cherry Studio | `getPathToNode(anchor)` 的路径；最近 `data-clear` 之前的消息被舍弃 | 先按上下文窗口生成或复用持久化压缩摘要，再由 AI SDK 将 UI parts 转为模型消息；多模型时同一用户消息可派生多份独立请求 |
| Codex | 当前线程在内存中维护的历史（恢复时由 rollout 回放重建），加上本轮新写入的世界状态差异 | 世界状态按固定顺序分 8 类区块装配，首轮全量、后续只写差异；base instructions 走请求独立字段，增量工具模式下工具也走历史；超限时压缩重写历史，保留摘要与真实用户消息，不保留工具输出 |
| DeepChat | transcript 中从 summary cursor 开始的完整 turns；重试/恢复按 `orderSeq` 截到目标 assistant | system、skills、tools、checkpoint、memory 和 directives 组成 leading messages；Agent memory 在生成前自动检索注入，查询 embedding 带熔断器（失败则降级不注入），注入按 persona、working、query recall 三条 lane 的硬 token 预算先保底再按优先级扩展，后台维护做冲突合并并以 tombstone 防同一事实被重复提取；超预算先移除 memory/directives，再保留完整尾部 turns，固定内容仍超限则报错 |
| DeepSeek Harness | 日志表面五类消息；失败尝试只记证据、不进模型历史 | 每步先确定模型路由，再协调系统提示、上下文与工具；请求改写不能再换路由或 effort。压缩与图像卸载按可选扩展接入，日志保持原始事实 |
| Hermes Agent | SQLite/内存历史与压缩轮转后的当前 lineage 上下文 | `build_turn_context` 恢复系统提示、做预飞行压缩、注入记忆/插件上下文和运行期说明；轮转可更换 session id 但保留 lineage |
| Jan | 普通 Chat 取 Thread 活动路径；Cowork 另有前端持有的工作历史 | Chat transport 清洗附件并按模型预算压缩/裁剪；Cowork 的 200000 Token 总量按每次 request 重置，compact 只改模型消息投影；两个表面分别理解 |
| LobeHub | 当前 `ConversationContext` 的 display messages，发送前排除仅本地消息 | 输入区把文件、技能、工具和选择区编码为 metadata 或运行上下文；最终预算与 provider payload 由 client agent/Gateway runtime 决定，本次未逐 provider 展开 |
| Manifold Desktop | 当前标签页内的整个 `messages[]` | 只追加 system prompt 后经 WebView2 发给 C++；assistant 流未回写数组，因此第二轮缺少上一轮 assistant，上下文链实际不完整 |
| NextChat | 当前 session 中从 `clearContextIndex` 起的非错误消息 | 顺序为 system prompt → `memoryPrompt` → Mask context → 受消息数/token 估算限制的近期历史 → 当前 user；工具/MCP 结果再进入同一状态机 |
| Open WebUI | 持久会话从 DB/history 加载，临时会话由前端携带 | 服务端管线注入能力并重跑 request Filter；native 可延迟工具 schema，通过检索与分派器调用。审批恢复复用助手身份，持久决议/认领事务提交后才执行外部工具 |
| SillyTavern | `chat[]` 过滤掉普通 system 消息后得到 `coreChat` | 先应用正则和附件内容，再经过 interceptor、World Info 和 API 分支格式化，产出 text-completion prompt 或 OpenAI messages；不同后端没有统一 payload |
| VCPChat | 群聊已核实为内存 `groupHistory` 的当前快照；单聊最终请求组装未在本次笔记逐步展开 | 群聊按成员串行构建各自上下文，下一位成员会看到上一位刚落盘的回复；群聊与单聊分属不同构建链，本行记录的范围只到群聊这条链 |
| VCPMobile | 同一 Topic 的轻量历史，跳过渲染缓存、保留附件提取文本 | Agent 配置、移动端 system prompt、时间/发言者信息、附件与 Tarven 规则组装为 VCP payload；本地未找到 token 预算或摘要压缩 |
| VCPToolBox | 调用方提交的线性 `messages`；Responses、Anthropic、Gemini 请求先桥接成该格式 | 请求级管线依次做字符预算裁剪、Tavern 注入、模型路由、变量/Agent/Toolbox 展开、多模态与 RAG/Timeline/OneRing/折叠预处理、Detector 和角色拆分；工具循环再追加 assistant 正文与 user `VCP_TOOL_PAYLOAD`。客户端会话外置，OneRing 另存插件历史；预处理实质改写模型输入 |
| Pi | 当前分支、压缩检查点与最新 context_edit 共同投影历史 | 编辑可替换或排除目标内容，工具结果独立回注；steer 等助手/工具批次边界再注入，followUp 在自然收尾前排空 |
| RikkaHub | 当前分支不含 system 的消息列表；会话有固定 `ConversationConfig` 后按配置的模型与开关取历史 | 先按 `contextMessageLimit` 做条数口径的滞回截断并对齐工具对，再前置一条合成 system 消息（生效系统提示 + 记忆目录与核心文件正文 + 各工具系统提示），最后穿过输入变换管道；压缩是插入检查点消息，旧消息保留，无 token 预算触发的自动压缩 |
| Risuai | 当前聊天尾部反向收集的消息，跳过 `disabled` 项；记忆路径下为所选引擎的截断或摘要结果 | 提示词模板卡片逐项预检 token 装入分组桶、再按卡片顺序拼装；预算以全局 `maxContext` 为上限，无记忆时从头部整条删除；拼装后还有只清空可移除消息的 token 重检，多模态附件在逐条处理时替换为 base64 |
| OpenCode | 从 SQLite 重读的全量历史（`MessageV2.toModelMessagesEffect`） | system 拼装：agent.prompt ?? provider 风格 → env/AGENTS.md 指令/MCP 指令/skills → user.system；media 从 tool result 抽离为独立 user 消息；溢出按 `model.limit.input - 20k` 检测，compaction 重排为 [compaction-user, summary-assistant, tail, continue-user]，压缩请求把选中历史**文本序列化**拼进 summary 请求（不再逐消息转 AI SDK 消息，也不做 stripMedia 媒体剥离） |
| OpenOcta | JSONL 尾部历史；网关关闭水化后，下层仍可能读盘 | 系统提示在 Runtime 创建时捕获，员工覆盖；运行时按模型窗口清理/摘要，摘要不回流会话 JSONL |
| OpenClaw | 当前 active branch 的 SQLite transcript（attempt 恢复后 sanitize/replay validation）；raw model run 只保留 probe prompt | 顺序为历史清理 → 可选 Context Engine assemble（legacy 则透传）→ prompt assembly 加入 inbound/runtime/hook/steering context → LLM boundary 投影时间/发送者 → `convertToLlm`；预算预检只分类压力路线、不直接压缩，溢出/阈值/超时恢复时才实际 compact，工具结果另有字符上限与迟到媒体护栏 |

**结论**：只比较"是否有上下文"不足以区分实现。客户端应用、主进程 runtime、Agent 后端、Web 服务和请求编排网关都可能负责最终输入的一部分。Manifold Desktop 的历史数组没有回写 assistant 流，因此第二轮请求仍缺少上一轮回复。比较具体行为时，应同时标注构建位置、历史真相源、压缩顺序、工具注入层和未覆盖边界。

## 流式生成：渲染状态如何进入持久化层

各项目都要处理"UI 立刻刷新"和"完成态落盘"的时序，但并非都实现了两层缓冲（渲染侧的 DOM 更新细节见消息渲染器横向对比）：

- **AIO Hub**：渲染走独立可重放流源与 RAF 节流，节点正文按定时器节流写回（默认 2 秒或增量保存间隔）；reasoning 直接刷新元数据，完成时强制排空。一个服务端 VCP 响应可拆成连续助手/工具节点，段切换时迁移排队子树，所有段关联同一请求快照；服务端工具结果先遮蔽，再检查本地工具请求。崩溃后已落盘的生成节点在加载时按有无内容结算为 complete/error 并回写，真实崩溃恢复未实测（[AIO 请求笔记](<AIO-Hub-对话请求与上下文调查笔记.md>) 第 5 节）。
- **Chatbox**：`updateStreamingCache`（只写 react-query 缓存）与 `persistStreamingMessage`（写 IndexedDB）分开；`shouldPersistStreamingChunk` 规定 tool-call 立即落盘，其余按 2000ms 定时。代码注释给出的原因是 tool-call 可能长时间等待审批，延迟落盘会在刷新时丢失待批准状态。落盘时用 `mergeCachedGeneratingMessages` 防止旧快照覆盖生成中的消息。
- **Cherry Studio**：数据流分为三层：DB 历史（SWR 缓存）、`useExecutionOverlay` 中尚未落库的流式增量，以及 `useStableMessagePartsLayers` 合并前两者后得到的 `historyPartsByMessageId`/`partsByMessageId`。渲染时再按 `firstLiveGroupIndex` 把同批消息分成已封存历史和 live 两段，分别使用不同的 memo 策略。
- **LobeHub**：transcript 层作为消息副本唯一写入者，局部会话 Store 只做单向镜像，解析集中在 lens。Gateway 事件按 Promise 队列串行消费并另做高频缓冲，避免工具占位、增量与终态刷新越过；镜像与静态展示分别稳定引用（[来源](<../会话与消息管理/LobeHub-会话与消息管理调查笔记.md>)）。
- **SillyTavern**：没有独立的流式缓冲层，`StreamingProcessor` 直接修改 `chat[messageId].mes` 和 DOM `innerHTML`，渲染状态与持久化数组耦合较紧。DOM 引用经 `#checkDomElements()` 懒加载缓存后，如果流式期间执行 `redisplayChat` 整段重绘，旧引用会指向已脱离文档树的节点；后续写入不报错，也不会显示。笔记确认了这条代码路径，尚未做运行时复现。
- **VCPChat**：`streamManager.finalizeStreamedMessage` 统一收尾，1 秒防抖存盘；群聊消息因 `saveHistoryForContext` 对 `isGroupMessage` 直接 return，不走这条路径，由 `groupchat.js` 单独写盘。是否落盘由消息类型决定，而不是由节流参数决定。
- **AstrBot**：LLM 阶段以 `AsyncGenerator` 挂起流水线，让 Respond 阶段先发送结果，再回到生成器执行历史保存等收尾；顺序性来自 UMO 锁与 follow-up 队列，不是浏览器 UI 缓存。
- **DeepChat**：assistant 先以 pending 行与 block 占位，完整流按绑定窗口定向发送，其他窗口接收轻量活动和版本状态，终态同步正文、搜索及 Tape。摘要状态与 Tape anchor 同事务 CAS；失败或摘要过大仍可只推进边界并保留旧摘要，取消不提交该结果。来源见[请求笔记](<./DeepChat-对话请求与上下文调查笔记.md>)。
- **DeepSeek Harness**：chunk 只作实时帧，结束时将紧凑原始流和 usage 内嵌于成功助手消息；失败、取消和重试尝试以非表面 attempt 收口。请求历史从耐久表面派生，请求头另保存配置和工具，没有逐 chunk 独立日志（[来源](<DeepSeek-Harness-对话请求与上下文调查笔记.md>)）。
- **Codex**：事件逐条处理并即时转发，core 与 app-server 之间本次未找到批量合并或节流层；只有项完成时才把完整项写入历史，工具调用写入后立即派发、统一在该响应流结束时等待；中断轮会额外写一条中断标记，先 flush 再发 `TurnAborted`。
- **Hermes Agent**：delta 经 WebSocket 投影到桌面节流队列，终态再触发版本仲裁和列表刷新。Agent 可在工具进展与轮末增量 flush；规范网关另有耐久输入账本和执行代际，消息持久化与受理恢复分层（[来源](<Hermes-Agent-对话请求与上下文调查笔记.md>)）。
- **Jan**：AI SDK `experimental_throttle: 50` 只节流 UI，`useMessages` 另做乐观写与异步持久化；`resume:false` 明确不恢复未完成流。
- **NextChat**：assistant 占位从一开始就在 Zustand session 内，SSE `onUpdate` 原地改 content，`onFinish` 清掉 `streaming`。状态存储和 UI 共用同一对象，没有独立 transcript 层。
- **Open WebUI**：Provider 流先在后端按 chunk 数量聚合，再通过 Socket.IO 发约定事件；`update_db=True` 的 emitter 可按事件类型追加或覆盖消息行，前端按 `delta/output/done` 更新 history 投影。
- **Manifold Desktop**：chunk 只更新 DOM 与 `streamingText`，连前端 `messages[]` 都不回写。这属于完成态尚未回到会话状态的断链，渲染层与持久化层在此没有衔接。
- **Pi**：流式状态与持久化同源——`message_update` 携带完整 partial 消息驱动 TUI 重建，`message_end` 才落盘；无独立的流式缓冲层。TUI 以 `requestRender` 帧节流合并刷新；abort/error 以 stopReason 持久化，下次恢复可见。
- **RikkaHub**：增量只更新内存态，不逐 chunk 落库；回合结束时由 `finishGeneration` 统一把内存态写回会话，完成、取消、失败三种结束都走这条路径，因此取消或失败时已生成的部分同样落库。管道本身不节流，SSE 以 `Channel.UNLIMITED` 缓冲并把每个 chunk 直接向下游转发。
- **Risuai**：流式占位消息在请求前写入会话（`chatId = generationId`），500ms 防抖的全局保存循环对任何消息改动整库编码写盘，因此半截流也会落盘，没有"流结束后一次性落定"阶段；Provider 流把累计全文放进单一键的块，消费端整段替换消息文本，按 125ms 定时器 + requestAnimationFrame 合并写回。流长度由空闲超时约束，没有固定总时长上限；保存格式按块增量编码，非响应式键值单独放进 `kv:<namespace>` 块。
- **VCPMobile**：用户消息先落 SQLite；SSE 经 Tauri Channel 进入流 store，aurora 的稳定块、尾部文本和 AST diff 用 requestAnimationFrame 合并。终态在单一事务中写正文、渲染缓存、FTS 与 Topic 聚合，活动请求记录随后删除；若客户端在生成期间被系统回收，则用离线完成文件补交终态，只有 SQLite 提交成功后才消费该文件。
- **OpenCode**：分三层频率——reasoning/text 的 delta 经 `updatePartDelta` 发 `message.part.delta` 增量事件，`text-end` 才完整落库，tool part 状态迁移即时落库；App 端 `part_text_accum_delta` 累积增量、`message.part.updated` 完整替换，SSE 16ms 批量 flush + delta 拼接。即 UI 更新频率 > 事件频率 > 落库频率，三层明确分离。
- **OpenOcta**：每轮助手完成后先追加文件再广播，工具结果等待对应调用轮写入后补齐，取消补半截快照。前端按会话分桶保存后台运行态；重连只清当前字段，后台映射若错过终态仍可能恢复旧快照（[来源](<../Chat UI/OpenOcta-ChatUI调查笔记.md>)）。
- **OpenClaw**：assistant 文本先在 Agent Core 内存消息与 SessionManager 中推进，`message_end` 由运行器持久化；embedded subscriber 把消息事件转回复 payload 与 agent 事件，Gateway `server-chat` 以 75ms pacing 向订阅面投影 `chat` delta——payload 携带完整 assistant 文本，客户端既可追加 delta，也可在 replace/恢复场景用完整快照。Gateway 的 live reply 与运行器写回的 transcript 是两条最终化路径（非 Agent 回复、媒体补写与 abort partial 另走专门分支），UI 投影频率与 transcript 提交不在同一层。

## 中断/取消生成：按钮停止、任务取消和请求中止不是同一层

| Chatbox | 未调查 | 本类目单项目笔记未覆盖中断层级，无法确认 |
| Cherry Studio | 已确认接入 AI SDK 请求信号的 `AbortController` | 实际网络取消效果未运行验证 |

| Open WebUI | 前端按 chat/task 停止；本地 `task.cancel()`，Redis 模式广播 stop | Redis 只负责把取消命令路由到实际持有任务的实例，任务本身不迁移 |
| VCPChat | 群聊有本地 `AbortController`；单聊只通知远端 `/v1/interrupt` | 单聊本地读取循环不受控且无客户端超时；未被引用的 `vcpClient.js` 才包含本地 abort 与 300 秒超时 |

| VCPToolBox | 中断端点按请求/消息 id 定位活动请求，再 abort 上游控制器并结算响应 | 当前 pending 回合可标 aborted，预处理已写历史不整体回滚；真实外部工具停止未运行验证 |

| RikkaHub | `stopGeneration()` 先暂停消息队列（等待中的回复置错），再逆序取消会话活跃 Job 并逐个 `join()`，最后把未执行工具以取消错误补全 | 取消经协程传播到 Provider 的 `callbackFlow`，收尾由 `finishGeneration` 落库并调用 `eventSource.cancel()`；底层 OkHttp 连接是否同步中断未运行验证。重试由请求侧 `retryPolicy()` 判定，并在判定前以 `ensureActive()` 防止把取消误判为网络抖动重放 |
| Risuai | 本地消费层：UI 的 `AbortController` 中止 fetch 与流 reader，返回 false 保留半截消息 | Tauri 桌面端 `streamed_fetch` 无取消命令，网络请求继续到服务端结束或 240 秒超时；导出的 `abortChat` store 从未被 set，实际停止走调用方自己的控制器 |
| SillyTavern | 未调查 | 本类目单项目笔记未覆盖中断层级，无法确认 |
| OpenCode | `POST /session/:id/abort` → `SessionRunState.cancel` → 中断 Runner fiber | `Effect.onInterrupt` 走 `halt(AbortError)`，`cleanup` 把未完成 tool part 标 `"Tool execution aborted"` + `interrupted:true`；重试为进程内 `Effect.retry`（5xx/429/超时/网络错误，上限 5 次、指数退避 2s 起带 0.25 随机抖动），前端无独立手动重试端点 |
| OpenOcta | 两层：`TurnAbort` 立即终止 TurnLoop，ctx 取消让流循环退出；入口是 `/stop`、`chat.abort`（带 runId 或不带 runId 中止整个会话） | runId 与会话键不匹配时只记警告仍允许停止；abort 响应可能先于 `aborted` 事件，前端先本地清运行态；新消息的抢占标记受获取 Runtime 前的等待与驱逐影响，不能保证触达旧运行 |
| OpenClaw | Gateway `chat.abort` 按 run id 定位 active controller、queued followup 或 worker inference；写 abort marker、关闭 active projection、保留终态持久化所有权后 abort controller，attempt 转发到 Agent Core 并中断 compaction | 中断会留下 aborted/interrupted 的 transcript 证据供后续恢复；ACK 后仍排队的 turn 经 `chatQueuedTurns` cancel identity 取消；timeout 与用户 abort 共用 run abort owner 但记录不同 phase；真实 Provider/断线下的取消时序未运行验证 |

VCPChat 仍是"同一产品两条路径不对称"证据最完整的案例。Hermes 的规范输入受理与 legacy 本地定稿需分开，Manifold 的回调式 stop token 与 Open WebUI 的跨实例任务取消也处在不同层级。Codex 与 OpenOcta 都已追到任务取消层，但前者是"取消令牌 + abort 任务句柄"，后者是"TurnLoop 立即停 + ctx 取消"，网络请求是否真正中止都未验证。表中“未调查/无法确认”仅说明本类目单项目笔记没有追至该层，各项目的中断能力需按该项目源码另作确认。

## 请求级编排与客户端历史的边界

VCPToolBox 不提供最终用户聊天主界面，但仍负责消息构建。它把调用方提交的历史归一化为 OpenAI `messages`，在首次请求前完成裁剪、注入和预处理；模型输出 VCP 工具标记后，再把 assistant 正文和工具结果 user payload 追加到内存上下文并递归请求。`FinalContextViewer` 只捕获首次上游 fetch 前的最近 5 份内存快照，不包含后续工具递归消息，也不是会话数据库。

AdminPanel-Vue 是独立进程（监听 `PORT+1`），与聊天主链物理解耦；OpenWebUISub 是运行在第三方聊天页面里的浏览器脚本，靠 `MutationObserver` 扫描 AI 回复文本里的协议标记字符串渲染成卡片。给模型的工具结果使用 `<!-- VCP_TOOL_PAYLOAD -->` user 消息，给前端的可见结果由 `vcpInfoHandler.js` 另行写入 SSE/最终 JSON；前者进入模型输入，后者只面向界面显示。完整证据链见 `VCPToolBox-对话请求与上下文调查笔记.md` 的"消息构建调查"。

## 执行层技术债（有具体代码证据支撑的）

- **AIO Hub**：后台压缩的配置和触发 Token 统计仍可能读取前台状态；摘要模型优先显式摘要绑定、其次目标路径最近助手的请求绑定，再回退 Agent，因此模型错位并非必然。多会话误触发、取消与提交边界、崩溃后生成节点修复均未运行复现。
- **Chatbox**：`throttleWriteSessionAtom.ts` 的 `createSessionAtom`/`WriteQueue` 与实际生效实现使用相同的 2000ms 参数，却从未被调用，属于疑似死代码。
- **AstrBot**：事件队列没有全局并发上限；follow-up 与流式并行的完整时序未实测。
- **DeepChat**：IPC revision/cursor 在网络中断、快速切换会话时的行为未运行验证。
- **DeepSeek Harness**：token-meter 启发式定价（每 4 字符 1 token）与 Provider 真实计费可能不一致；压缩触发、溢出重试与 KV cache 复用收益未做真实模型端到端验证。
- **Hermes Agent**：桌面侧本地定稿与后端 `interrupt_requested` 检查不是同一动作，CLI/gateway 以外的运行行为未实测。
- **NextChat**：摘要没有质量校验。
- **Open WebUI**：多模型、工具、Socket.IO 事件和后台标题/标签/追问任务共享同一大状态机；跨实例取消依赖 Redis pubsub，未迁移任务队列。
- **Pi**：上下文 token 估算为启发式，与 Provider 计费可能不一致。
- **RikkaHub**：截断只按消息条数、不做 token 估算；压缩改插检查点，旧消息仍会随会话增长；完成、取消、失败都经 `finishGeneration` 落库，但跨进程重启后的半截回复可见性未运行验证。
- **Risuai**：导出但从未使用的 `abortChat` store、`/multisend` 命令会撞上全局锁直接返回 false、IGP 子请求把返回对象直接拼进消息文本（静态看会拼出 `[object Object]`）三个可疑点均未运行验证。
- **OpenCode**：`message.part.delta` 的累计通道 `part_text_accum_delta` 与 `produce` 就地追加在断线重连/事件乱序下的正确性未实测。
- **OpenClaw**：legacy Context Engine 的 assemble 只做透传，上下文预算与 provider-boundary 预检仍在 runner 中；预算预检只分类不直接执行压缩，压缩/溢出恢复是否与静态路径一致未实测；ACK 后 detached dispatch 使终态 cleanup 落在 RPC 生命周期之外，restart-safe 恢复依赖 HMAC fingerprint/restart claim。
- **Codex**：上下文超限时只标记并报错，压缩请求自身也会从最旧项逐条丢弃重试；压缩后缓存命中率、`BodyAfterPrefix` 作用域的收益与长上下文截断行为未实测；工具并发度与等待顺序对端到端延迟的影响未实测。
- **OpenOcta**：运行中摘要写在独立转录文件、不回流会话，换设备或重开会话看不到摘要痕迹；摘要中间件与 `sessions.compact` 的行级截断互不共享状态；系统提示覆盖会把内置安全段一起换掉；联网搜索在代码中恒为关闭。

## 设计取舍与已确认边界

- **压缩的运行任务与提交分离（AIO Hub）**：同会话复用运行中的 Promise，发送前等待已有任务，摘要与 Token 计算完成并通过取消检查后才改树；原消息保留，连续压缩合并旧摘要（[AIO 请求笔记](<AIO-Hub-对话请求与上下文调查笔记.md>) 第 3 节）。
- **构建预览与实发证据分离（AIO Hub）**：上下文预览按当前配置重建，不启动转写，变量处理仍可写共享元数据；实发快照在协议适配后捕获，有独立持久化与容量上限。两者与可恢复会话分开解释；完整历史请求以可恢复会话为准，诊断记录只覆盖容量上限内的请求体投影与来源映射（[AIO 请求笔记](<AIO-Hub-对话请求与上下文调查笔记.md>) 第 9.8 节；[上下文编译笔记](<../上下文编译与提示词工程/AIO-Hub-上下文编译与提示词工程调查笔记.md>) 第 5 节）。
- **流式三层频率是参考形态**：OpenCode 明确做到 UI 更新频率 > 事件频率 > 落库频率三层分离；多数项目是两层（UI 缓存 + 节流落盘）或一层（SillyTavern、Manifold Desktop）。
- **中断语义必须按层级验证**：按钮存在不能证明请求被中止；评估停止能力时，需要继续追到请求或任务控制层。
- **VCPToolBox 的编排是"请求级"的**：上下文裁剪是字符数估算而非严格 token 预算，工具循环上限默认 5。
- **模型历史与流式证据分层（DeepSeek Harness）**：下一步历史只消费已准入的耐久表面，实时 chunk 可以先展示、再于尝试结束时合并落盘。成功消息与失败尝试分别收口，重试仍在同一开放 turn/step 内进行。
- **RikkaHub 以条数口径截断并用内存队列表达并发**：截断按滞回/阶梯式推进，保留条数落在 `[limit*0.5, limit)` 且截断点在一段轮次内不动，用于稳定请求前缀；压缩改为插入检查点消息，token 预算不参与触发判断。同一会话的并发以消息队列表达——再次发送即入队等待本轮结束，steer 与替换当前生成的能力在 RikkaHub 中尚缺；停止沿协程取消传播到 Provider 的 `callbackFlow`，底层网络是否即时中断未验证。
- **Risuai 的停止语义只覆盖本地读取，并发用全局锁表达**：`doingChat` 锁与 UI 检查直接拒绝新发送，不排队、不替换；群聊成员在发送入口内按 talkness 排序串行生成。停止按钮的 `AbortController` 只中止本地 fetch 与流 reader，桌面端 `streamed_fetch` 没有取消命令，网络请求继续到完成或 240 秒超时。
- **ACK 与 detached dispatch 分离（OpenClaw）**：Gateway 把"接受请求"与"完成运行"分开——ACK 前同步确认身份、幂等、附件与取消边界并写 pending dedupe，ACK 后 dispatch 继续持有运行准入、transcript persistence 与终态 cleanup；"已收到 ACK"表示请求已被受理并进入 dispatch，canonical history 的写入由 dispatch 在终态完成；未确定的交付停在各聊天表面的待确认状态，等待明确结果。另一个取舍是 transcript prompt 与 model prompt 分流：用户 turn 尽量持久化 bare 文本，动态 inbound/hook 与时间/发送者投影只在模型边界加入。
- **同会话锁的作用域决定并发保证（Codex / OpenOcta）**：Codex 的活动轮准入决定新输入并入或拒绝；OpenOcta 的互斥锁属于池条目，超时驱逐映射后可以出现同键新旧实例并存。比较再次发送时，需要区分客户端排队、网关等待、实例内抢占与显式取消，不能从一把锁推导整个会话始终单任务。
- **压缩是否可回放（Codex / OpenOcta）**：Codex 把压缩后的替代历史写成 `Compacted` 记录，恢复时可重建当前历史，旧历史只是不再可见；OpenOcta 的运行中摘要写在独立转录文件、不回流会话，`sessions.compact` 只是行级截断。差别在于前者在会话日志里留下可回放的压缩记录，后者的摘要痕迹根本不出现在会话文件里。
- **类目边界**：本对比只回答执行语义；工具循环内部机制在 Agent 工具类目，Provider/渠道解析在 LLM 渠道管理类目，流式 DOM 更新在消息渲染器横向对比。

## 未验证事项

- AIO Hub：网络级停止、压缩取消与提交竞态、多会话后台配置/阈值依赖、实发快照与上游缓存 usage 对照均未运行验证；预览的变量元数据写回边界已按静态路径确认。
- DeepChat 的崩溃恢复与乱序行为、NextChat 的 Provider 级取消效果、Jan 的底层网络 abort 均未运行验证。
- SillyTavern 隐藏消息是否真的被排除出 prompt 构建未核实。
- VCPChat 单聊最终请求组装未逐步展开。
- LobeHub 各 Provider 的最终预算与 payload 未逐 provider 展开。
- DeepSeek Harness 未运行交互会话：压缩触发、溢出重试、KV cache 复用收益与 token 估算偏差需真实模型端到端验证；time-context/tmux-context/session-reference 的运行行为未实测。
- Risuai 桌面端停止后的网络请求继续时长与窗口关闭后 Rust 请求的存活行为、`/multisend` 与 IGP 两个静态可疑点、多选生成流式路径只消费第一个 choice 键的显示行为均未实测。
- VCPMobile 的取消是否使远端推理停止、SSE 取消与终态事件的真实排序、以及并行单 Agent 请求的服务端策略未运行验证。
- OpenClaw：未运行真实 `chat.send`、Provider stream、工具循环、渠道投递或 Control UI 重连场景；context overflow、自动压缩、Context Engine 降级、压缩后 continuation、restart-safe retry、session/global lane 并发容量与 abort 时序均为静态推断。
- RikkaHub：未运行应用。停止后 `eventSource.cancel()` 是否即时中断底层网络请求、管道外 UI 对高频 chunk 的渲染节流频率、检查点压缩后的实际 token 占用、五类 Provider 分支的逐字段映射，以及 `finishGeneration` 落库后跨进程重启的可见性，均未验证。
- Codex：中断的实际网络效果与工具进程终止、压缩后缓存命中率、`BodyAfterPrefix` 作用域收益、工具并发对延迟的影响、守护进程重启恢复在"输入已写、响应未完成"组合下的行为均未运行验证。
- OpenOcta：首段 30 秒等待及驱逐后新旧 Runtime 并存时的事件和写盘顺序、显式停止的实际网络效果、`stopReason` 多次覆盖顺序、讯飞图片理解路由、摘要与大上下文模型组合的阈值行为、审批中断后刷新页面再恢复、大附件与单行 32MB 上限的相互作用均未运行验证。
