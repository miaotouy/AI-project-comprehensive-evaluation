# 会话与消息管理横向对比

> 对比对象：AIO Hub、AstrBot、Chatbox、Cherry Studio、Codex、DeepChat、DeepSeek Harness、Dify、Hermes Agent、Jan、LobeHub、Manifold Desktop、NextChat、Open WebUI、OpenClaw、OpenCode、OpenOcta、Pi、SillyTavern、RikkaHub、Risuai、VCPChat、VCPMobile、VCPToolBox
>
> 对比更新日期：2026-11-05
>
> 依据：文末来源索引的 24 篇单项目笔记，并结合请求与 Chat UI 专题；采用截至 2026-11-05 的静态证据，调查日期与代码快照按各篇元数据区分，未做运行验证
>
> 对比方法：按会话单位、消息事实源、存储模型、分支模型、索引与搜索粒度、异常恢复等共同维度逐项对照；未被单项目笔记共同覆盖的项单独标注范围
>
> 对比范围：会话单位与存储模型、分支语义、索引与搜索（数据侧）、数据层技术债；发送执行与流式在对话请求与上下文横向对比，界面工作流在 Chat UI 横向对比
>
> 文档定位：实现学习与跨项目横向比较，不作为整改方案

## 结论摘要

- **"会话主体"是各项目对会话主链的命名，同一术语在不同项目里可能指不同层级**：Session 在多数项目是顶层会话，唯独在 AstrBot 是账号级容器；Topic 在 Cherry Studio 是顶层、在 VCPChat 是二级单位；Thread 在 Jan 是顶层、在 Chatbox 是 Session 内历史区间、在 LobeHub 是消息级话题线。
- **存储介质与提交语义分开比较**：Cherry Studio、DeepChat、Hermes Agent、Open WebUI、AstrBot、OpenClaw 使用数据库；Chatbox 采用平台行树（桌面/Web 为 IndexedDB、移动端为 SQLite），NextChat 保存 IndexedDB 对象。文件项目还分整份覆盖与逐事件追加，Codex 则以 JSONL 为事实源、SQLite 为投影。单凭介质无法判断并发或恢复保证。
- **"分支"不是一回事**：至少包括消息树切换（Cherry Studio）、树+兄弟记忆（AIO Hub）、同一行树的多种产品语义（Chatbox）、多模型兄弟组（LobeHub/Cherry 多模型）、独立文件/候选数组（SillyTavern）、父子树+兄弟版本（Jan）、有序 transcript 上的 fork（DeepChat）、会话复制与 lineage（Hermes/NextChat）、服务端回溯重建（Open WebUI）、指针分支（Pi）、删除式回退+复制式 fork（OpenCode）。
- **搜索的索引、命中粒度和跳转是三件事**：Chatbox 与 DeepChat 已确认能从数据层命中并定位具体消息；VCPMobile 的消息终结事务维护本地 FTS，全局搜索支持跨 Topic 命中并跳转消息；LobeHub、Hermes Agent 有数据库或搜索文档基础但定位链路证据不齐；Jan、AIO Hub、Manifold Desktop 主要返回会话级结果，Open WebUI 全局入口另有消息级命中。三项条件需分别验证，VCPMobile 已具有持久化消息索引、跨会话命中和消息锚点跳转的完整静态链。
- **DeepSeek Harness 以追加日志保存会话事实**：v4 的五类表面消息派生模型历史，系统提示也在表面内；流式证据内嵌于成功消息或失败尝试，每次模型调用各有耐久收口。JSONL 写句柄承担批量追加与屏障，跨进程排他由平台内核原语实现；旧格式先在内存迁移，写打开才发布新代文件。fork、resume 与人类 transcript 各从日志派生（[来源](<./DeepSeek-Harness-会话与消息管理调查笔记.md>)）。
- **Risuai 的会话内嵌于角色对象、落盘是整库单文件**：无独立会话集合，`chatPage` 下标即当前会话指针；内存 `DBState.db` 是唯一事实源，块级增量编码 + 500ms 防抖整库覆写，每次保存另写备份（保留 20 份）。分支是复制整份会话并截断 + `branchedfrom` 注释回链（父会话无记录），分支导航由消息内容哈希前缀树实时计算；Reroll 是纯内存候选、不落盘。消息内容搜索本次未找到。
- **VCPMobile 的 Topic 与消息以 SQLite 为事实源**：Topic 归属于 Agent 或 Group，消息按时间戳与 ID 线性排序；终结事务更新渲染缓存和 FTS，编辑或重新生成以截断后续历史表达，不产生树或候选版本。全局搜索已接通跨 Topic 查询与消息锚点跳转，短词和长词采用不同匹配路径。
- **OpenClaw 把“可寻址会话”与“可轮换消息树代际”拆成两层**：逻辑会话以 `sessionKey` 寻址、`session_nodes.entry_json` 保存会话记录，`current_session_id` 指向当前 transcript generation，一个逻辑会话可保留多个 `session_windows`；per-agent SQLite 的 `transcript_events` 是原始事件源，活动路径与 FTS5 是从事件派生的可重建投影。reset、rewind、branch switch 与 restart recovery 都以新增 generation、leaf control 或 successor 轮换当前 `sessionId`，不改写原事件，旧窗口由归档与回收处置，删除默认 archive-then-delete。列表搜索不扫正文，正文搜索走 per-agent FTS5（仅活动路径 user/assistant 文本），索引 dirty 时返回 `indexing` 并后台 reconcile。

- **流投影回收与持久化模型分属两个层面**：VCPChat 以仓库、历史写入权威和 surface 投影分层，并用 conversation key 与 generation 拒绝已撤离 surface 的迟到事件；普通单聊仍以本地历史文件为事实源，没有因此获得事务、文件锁或版本合并。AIO Hub 的队列标记则已持久化在消息节点上，使同一路径串行、分支并行的调度语义可以跨界面状态复查。
- **同为"追加式 JSONL、无消息表"，索引与恢复路径决定成本（Codex / OpenOcta）**：Codex 把 SQLite 当可丢弃的投影，列表与分页读库、恢复回放 rollout，回退另建文件后切指针；OpenOcta 只有 `sessions.json` 索引与每会话一份转录，列表、预览、成本统计都要重读文件。两者都不改写历史行，也都没有消息级编辑或消息树。

## 项目概览

### DeepSeek Harness

会话事实保存在追加式 v4 JSONL，模型历史从五类表面消息派生，失败尝试只保存审计证据。每会话串行写链与耐久屏障约束写入，跨进程依靠写者声明及内核租约排他。旧格式读取时在内存迁移，写打开才发布新代文件；fork 复制前缀，resume 从日志恢复。其一致性成本集中在投影重建、旧代文件保留和崩溃收口（[来源](<DeepSeek-Harness-会话与消息管理调查笔记.md>)）。

### Risuai

会话内嵌于角色，主存档按块编码后整份拼装，remote 角色、冷归档及资源另有外置后端。分支复制会话并截断，以单向注释回链；reroll 未选候选只在内存。插件存储采用冷索引和大值条目，API 完成、索引指针发布与主存档写出是不同提交时点；窗口互斥和多用户同步也各有合并边界（[来源](<Risuai-会话与消息管理调查笔记.md>)）。

### OpenClaw

OpenClaw 把会话建模为“逻辑会话节点 + 可轮换 transcript generation + 追加型事件树”：逻辑会话以 `sessionKey` 寻址、`session_nodes.entry_json` 保存会话记录，`current_session_id` 指向当前 transcript，一个逻辑会话可保留多个 `session_windows`。per-agent SQLite 的 `transcript_events` 按 session window 的递增 seq 保存完整事件 JSON，是原始事件源；活动路径与 FTS5 是同一事实源上的可重建投影，无法从新增行安全推出路径时置 dirty 后整树重建。reset、rewind、branch switch 与 restart recovery 都通过新增 generation、leaf control 或 successor 表达，不改写原事件，删除默认 archive-then-delete；消息级通用就地编辑或按消息删除的面向用户 RPC 本次未找到。

### RikkaHub

会话归属助手，同时保存模型与工具选择的会话级配置。Room 按节点保存候选数组，选择整数决定活动版本，用户重新生成则截断后续节点。流式只改内存，完成、取消和失败均统一保存；全文检索使用独立 FTS5 投影，主表提交与索引维护分层，因此需要索引重建路径（[来源](<RikkaHub-会话与消息管理调查笔记.md>)）。

### Codex

Codex 的会话单位是线程（ThreadId，UUIDv7），历史以一条追加式 rollout 日志保存，没有消息表结构：会话头、模型项、轮次上下文、世界状态、压缩检查点、token 用量与协议事件共 13 类记录写进同一个 JSONL 文件（可选 zstd）。权威源是这个文件；SQLite 里的线程表与轮次/项投影、外加一份独立的名称索引，都是可重建的索引。文件由单写者后台任务串行写、轮末 flush，回退则基于保留前缀另建一个 rollout 文件并一次性切换数据库指针，旧文件保留。没有消息树：分支用 `thread/fork` 新建线程并继承边界，附属线程隐藏于普通列表但被父线程拥有，因此父线程不可删。列表可读 SQLite 或用 rollout 头部补齐元数据，分页直接读投影表；全文搜索用 ripgrep 扫 JSONL，消息级编辑/删除端点与 SQL 全文索引本次都未找到。

### OpenOcta

OpenOcta 没有数据库，会话事实源是两层文件：每个 agent 一份 sessions.json 索引，加每个会话一份 `<sessionId>.jsonl` 追加日志。会话键是带语义的命名空间（agent、custom、渠道、员工、cron 等前缀），条目里的 UUID 才决定转录文件名，所以多个键可以指向同一份文件。写入按回合进行：用户消息在请求前落盘，assistant 每轮结束追加一行，工具结果单独成行，取消时补写半截快照；索引则是整文件读改写、没有锁，并发修改以后写覆盖先写收场。消息树没有读写路径——parentId 虽写进每一行，读取只按文件顺序取尾部若干条。`/new`、`/reset` 等重置入口换新 sessionId 与新文件；会话压缩只是按行截断并另留 `.bak` 备份，消息级编辑、重试与分支本次都未找到。

| Pi | Session；两套会话栈：coding-agent 的 `SessionManager`（v3 JSONL 会话树）与 `packages/durable`（不可变 entry + commit） | coding-agent 每会话一个 `.jsonl`（条目带 `id/parentId` 形成树，`leafId` 指针标记当前位置）；durable 的存储后端可在 Memory、JSONL、SQLite、IndexedDB 间替换 | 追加型：`message_end` 落盘，首条 user 或 assistant 即建文件并写缓存条目、之后逐条 append，失败回滚内存索引与 leaf；durable 以 commit 为单位先落存储再对外发布，进程中断后重开存储可 `resume()`；p2 建在 durable 之上，CLI/TUI 仍用 `SessionManager` |
| OpenClaw | 逻辑 Session（`sessionKey` 寻址）→ 当前 transcript generation（`current_session_id`），可保留多个 window | agent store 双引擎：默认 SQLite，可切换 PostgreSQL（五类 store family 各自可选、一个 Gateway 可混用）；表结构 `session_nodes.entry_json` + `session_windows` + `transcript_events` | 事件级追加 + 同步事务；活动路径/FTS 同事务前向更新或置 dirty 重建；reset/rewind/branch/recovery 轮换 generation 并保留旧窗口，schema 版本 40 |

### 术语层级：同一个词在不同项目里指不同位置的容器

- **Session 在多数项目里是顶层会话**（AIO Hub、Chatbox、DeepChat、Hermes Agent、NextChat 的 `ChatSession`、Pi、OpenCode），**唯独在 AstrBot 里是账号级容器**：session 由 UMO 标识，其下可切换多个 conversation，conversation 才是"具体对话"。
- **Topic 在 Cherry Studio 是顶层**（消息树本体），**在 VCPChat 是 Agent/AgentGroup 下的二级单位**；LobeHub 则是 Agent → Topic 两级，thread 再作为消息级子维度参与 `messageMapKey`（带 `threadId` 的消息不进主干树）。
- **Thread 在 Jan 是顶层会话**（每 thread 一个目录），**在 Chatbox 是 Session 内的历史区间**（其上还能叠加 Fork 分支），**在 LobeHub 是消息级话题线**——同一词横跨三个层级。
- **Chat 在 Open WebUI 是顶层会话**（history JSON + 消息表双写）；OpenCode 的 Session 内部严格三层（session → message → part）；SillyTavern 不用这类词，会话就是"聊天文件（chat[]）"；Manifold Desktop 的 Chat tab 尚未接通会话持久化。
- **DeepSeek Harness 的 Session 是顶层会话，且会话本体就是事件日志**：无独立消息表，消息历史从日志派生；子 agent 会话只是 header 上的 `origin: 'subagent'` 与 delegationDepth 展示元数据，不是可继续的独立会话。
- **Risuai 的顶层容器是角色，会话内嵌其中**：会话（Chat）是角色对象 `chats[]` 数组里的元素，`chatPage` 下标决定当前会话，无独立会话集合；群聊是与角色同级的群聊对象。顶层都不是会话本身——这与 AstrBot 的账号级容器、VCPChat 的二级 Topic 相似，区别是 Risuai 的会话随角色对象整体导入导出。
- **VCPMobile 的 Topic 是 Agent 或 Group 下的会话**：消息在 Topic 内线性排列；选择状态和分页窗口在前端投影，SQLite 是事实源。这与 VCPChat 的二级 Topic 同名但存储和并发边界不同。
- 会话内还能再派生**子会话**：Open WebUI 的内部子代理占独立会话行、DeepChat 的 subagent session 是独立可读 transcript、Hermes Agent 的子代理是真实子会话——这与 AstrBot/VCPChat 那种"父级角色容器 + 下级对话"是两种不同的层级结构。
- **OpenClaw 的"逻辑会话"是持续寻址层，Session/window/transcript 是身份与代际层**：同一 `sessionKey` 可轮换多个 `sessionId`（每代 transcript 各占一个 window），事件按代际独立成树，用户面对的是"一个可寻址会话的多代历史"——与 Cherry/VCPChat 把 Topic 当作静态顶层、DeepSeek Harness 的"会话即日志"都不同，它显式拆开了"持续寻址单元"与"消息树代际"。
- **Codex 的 Thread 是顶层会话，但会话本体就是日志文件**：线程 id 同时是会话 id 与 rollout 文件名主干；回退另起一个 rollout id 而线程 id 不变，因此"一个线程"可以对应多个物理历史文件。消息只是日志里的记录类型，没有独立的消息容器或活动路径指针。
- **OpenOcta 把"会话键"和"文件身份"分成两层**：键是带命名空间的字符串，决定 agent、运行时池分片与前端订阅；sessionId 才是 UUID 与转录文件名。键可以没有索引条目而退化成派生 id，同一份文件也可能被多个键指向，命名比 Codex 的"id 即文件"多一层间接。

命名取向粗略分两类：**用户语义词**（Topic、Conversation、Chat——Cherry Studio、VCPChat、Open WebUI、AstrBot 的二级单位）偏"一段话题/对话"；**实现语义词**（Session、Thread——AIO Hub、Jan、DeepChat、Pi、OpenCode、Chatbox）偏"一条会话记录"。比较时基准应是"该词在自己项目里处于哪一层、内部还能不能再挂子容器或分支"，而不是名称本身。

### 存储实现分组与一致性代价

Cherry Studio、DeepChat、Hermes Agent、Open WebUI、AstrBot、OpenClaw 使用数据库行或事务；Chatbox 使用平台行树，NextChat 使用 IndexedDB；AIO Hub、Jan 桌面端、SillyTavern、VCPChat 仍有整文件/整对象写入路径，Risuai 的整库覆写也属这一组（块级增量只限定重编码范围，写入仍是整文件），Manifold Desktop 的存储 API 尚未接入正常聊天。介质本身不保证一致性：Open WebUI 需要对齐两份数据，Hermes Agent 需要翻译会话句柄与持久 session id 两套身份，Jan 虽有文件锁仍按 O(消息数) 重写。

DeepSeek Harness 现在是纯追加型 JSONL：每会话一个目录、默认 zstd 帧压缩，写侧由 `SessionHandle` 串行 append，跨进程写以 writer claim 加 kernel lease 排斥；原 JSONL/SQLite 双后端互换已收窄为仅 JSONL，SQLite 会话后端移除。与整份覆写型文件项目不同，追加型写入的每轮成本不随消息数增长，代价落在读取时的全量解析与日志体积。

Codex 与 OpenOcta 都落在追加型文件这一组，分别是本组两种索引取向的上限：Codex 把 SQLite 投影当可丢弃的加速层，列表、分页与轮次/项定位读库，恢复靠回放日志，回退时切一次指针；OpenOcta 没有投影，每轮上下文、列表、预览与成本统计都重读转录，索引读写也不加锁。前者承担投影与迁移两套子系统，后者承担 O(文件) 读取与后写覆盖前写的丢更新风险。

## "分支"不是一回事：消息树、版本、复制和轮转链

这批项目里的"分支"至少包括消息树切换、消息版本、会话复制、文件截断另存、压缩轮转链和多模型并列，不能统一称作"消息树切换"：

1. **真树 + 指针跳转（Cherry Studio）**：持久层是 DB 树（`parentId` 外键 + CHECK 约束保证虚拟根不变式）；切分支时更新 `topic.active_node_id`，渲染再反向 walk 拼出路径。分支草稿以**持久化空叶子**保存：`POST /messages/:id/branches` 经 `MessageService.reserveBranch` 落一条空的 successful user 行，awaiting-input 状态由结构派生。`buildTopicMessageFlowLiveState` 现在只叠加"流式中尚未持久化的消息"临时节点，分支图 = 持久化树（含空分支叶子）+ 流式 overlay。
2. **树 + 兄弟记忆（AIO Hub）**：父子关系与上次选择指针构成应用层树，分支导航在兄弟间循环并恢复所选后续路径。重试（含切换模型）新建助手兄弟节点；续写助手时新建带原内容前缀的兄弟节点，续写用户时创建空助手子节点。未提升新会话草稿另存文件，恢复时重建根与当前角色开场白，属于会话身份与输入恢复机制。
3. **同一行树的多种产品语义（Chatbox）**：Thread 是树中的历史路径，Fork 是同父兄弟加激活子节点，summary 是普通摘要行；列表置顶另存元信息。领域服务将操作提交为行命令，旧数组对象保留兼容投影；thread 可转成独立会话（[来源](<Chatbox-会话与消息管理调查笔记.md>)）。
4. **多模型兄弟组（LobeHub / Cherry Studio 多模型场景）**：多模型 mention 场景下，N 个模型各自产出一条 assistant 消息，共享同一个 `siblingsGroupId`，属于并列结果，不是二选一分支；LobeHub 的 `BranchResolver` 处理的是重新生成后的候选选择，用 `metadata.activeBranchIndex` 存在父消息上，子消息本身不记录激活状态。
5. **独立文件/候选数组，无树（SillyTavern）**：Branch 把 `chat[]` 截断到某条消息后另存为新文件并跳转，Checkpoint 只另存不跳转。两者共享截断函数，但 `extra.bookmark_link` 是单值、`extra.branches` 是数组，记录关系的方式不同。单条消息的候选回复放在 `swipes` 数组中；Branch 可以先选定某个 swipe 再截断。VCPChat 的 Topic 之间没有消息级分支，多个 Topic 是并列历史。
6. **父子树 + 兄弟版本（Jan）**：`parentId` 形成活动路径，`makeSibling` 为编辑或重新生成创建同父新版本，`activeRootId`/版本导航选择可见路径；Continue 则原地续写，不产生新分支。媒体消息编辑回退为纯文本，是版本语义中的明确损失边界。
7. **有序 transcript 上的 fork（DeepChat）**：`SessionTurn` 支持 fork/retry/edit，但上下文恢复主要按 `orderSeq` 截取完整 turn，并非每次都沿 `parentId` 回溯。它更接近"从 transcript 某点复制出新 session/turn"，与 Cherry Studio 按 `parentId` 邻接关系组织的 DB 树是两种分支模型。
8. **会话复制与 lineage（Hermes Agent、NextChat）**：Hermes `session.branch` 复制历史并建立 parent/lineage 关系，压缩轮转也会生成新 session id；NextChat 则深拷贝整个 Session，只换会话 id，消息 id 和摘要游标等内部字段保留。二者都是会话级派生，但 Hermes 需要保持跨轮转 lineage，NextChat 只是本地独立副本。Hermes 分支与压缩轮转现在都**携带标题**（标题带 derived < llm < user 的 provenance，`/title` 永不被自动标题覆盖），不再对每个 fork/轮转把 `xxx #N` 重编号。
9. **服务端回溯重建（Open WebUI）**：消息本身由 `parentId`/`childrenIds` 构成树；`POST /{id}/fork` 用 `build_fork_history` 从目标节点沿父链重建一个新 Chat。多模型的 `modelIdx` 并列列序与 fork 是另一套正交关系。
10. **指针分支与投影编辑（Pi）**：导航先改内存 leaf，下一追加才记录新父链，单独导航退出不保存位置；还可复制根到叶路径成独立文件。context_edit 在当前分支替换或排除目标的模型内容，原条目仍保留，投影同时考虑压缩和最新编辑（[来源](<Pi-会话与消息管理调查笔记.md>)）。
11. **删除式回退 + 复制式 fork（OpenCode）**：`revert` 记录回退点（含 git snapshot）并回滚文件，再次 prompt 前**删除目标之后的所有消息**——改的是原消息树而非新建节点；真正的分支是 `POST /session/:id/fork`，新建会话并复制截至某消息的全部消息/parts（parentID 重映射）。多模型/多候选不产生消息级兄弟节点，也没有草稿态覆盖层。
12. **日志前缀复制（DeepSeek Harness）**：普通 fork 复制含指定边界的事件前缀，以种子标记及精确继承长度记录来源范围，不填写普通父会话字段。合法开放 turn 边界会补合成 closers，分支成为独立会话；它与 Pi 移动活动叶子指针的方式不同（[来源](<DeepSeek-Harness-会话与消息管理调查笔记.md>)）。
13. **复制会话 + 注释回链（Risuai）**：分支按钮深拷贝整个会话、把消息截断到分叉点，尾部插入一条 `branchedfrom` 回链注释（含源会话与源消息 id），再作为新会话跳到列表头；父会话不记录子分支。分支导航视图由 `getChatBranches` 对消息内容哈希做前缀树实时计算，不读取任何分支元数据——文本改动会改变树形。这条复制会话分支会持久化；Reroll/swipe 没有持久化候选，只是独立的内存候选。
14. **线性截断重发（VCPMobile）**：编辑用户消息或重新生成助手消息时，删除指定时间之后的记录，再从保留的用户消息启动下一轮；本次未找到树、兄弟版本或复制会话式分支。
15. **轮换 generation + leaf control（OpenClaw）**：rewind、fork、branch switch 共用一套 message cut——rewind 与 branch switch 保留原逻辑 key 并新建 transcript generation、复制原始事件后追加或移动 leaf control（rewind 停在指定 user 消息前，switch 指向另一 branch tip），fork 另建 dashboard 逻辑会话并记录 `forkSource` 与父 key；非活动路径目标、非 user message、非 branch tip 或已有活动工作时被拒绝。原事件通常保留，旧 generation 由归档与 disk-budget 回收，删除式回退（OpenCode 的 revert）与纯 leaf 指针移动（Pi）都不同于它。另有一层 checkpoint branch/restore：branch 写新 key、restore 保持原 key 但替换当前 `sessionId`。
16. **同一线程换物理文件 + 新线程继承前缀（Codex）**：回退指定"某轮之前"，先停掉活线程，再基于保留前缀生成新的不可变 rollout 文件，SQLite 指针一次性切到新文件，旧文件保留；分支是 thread/fork 新建线程，边界可取"含该轮"或"不含该轮"，可携带父线程的历史基址做引用而非复制。附属线程隐藏于普通列表但被父线程拥有，父线程因此不可删。它与 Pi 的 leaf 指针、OpenClaw 的 generation 轮换都不同：一条路径是"同线程换文件"，另一条是"新线程继承前缀"。
17. **换 sessionId 的新文件（OpenOcta）**：`/new`、`/reset` 与 `sessions.reset` 保留标题、渠道、聊天类型与两个生成级别，换新 UUID 与新转录文件并中止在飞运行，旧文件留在磁盘；`sessions.compact` 在超过 400 行时归档原文件并重写尾部。本次未找到消息级编辑、重试、重新生成与会话复制/分支入口，因此没有可比较的"分支"语义，只有"重开一段历史"。

AstrBot 的多个 conversation 是同一 UMO 下可切换的独立对话，不是消息分支；Manifold Desktop 未形成可持久化的正常会话主链，本次也没有可比较的分支机制。

## 索引、搜索粒度与定位标识

比较搜索能力时，要区分索引对象、结果粒度和 UI 跳转（搜索入口与跳转工作流见 Chat UI 横向对比）：

- **AIO Hub**：跨会话搜索由 Rust 全量遍历文件系统并用正则预过滤，没有持久化索引，只能定位到会话。会话内搜索是独立的前端线性扫描，仅覆盖当前活动路径，无法命中隐藏分支。两套搜索没有衔接，跨会话结果不能直接跳到具体消息。
- **Cherry Studio**：搜索使用 `document.createTreeWalker` 遍历已渲染的 DOM 文本节点，没有查询消息数据模型。消息列表由 `virtua` 虚拟化，窗口外消息未挂载到 DOM，因此不会进入搜索范围。这是 DOM 搜索与虚拟列表组合后的范围限制。
- **VCPChat**：`searchTopicsByContent` 只对字符串类型的 `message.content` 做 `includes` 匹配，多模态数组（`[{type:'text',...}]`）会被跳过，形成明确的搜索盲区。当前 HEAD 另有旁路的 VCP-CDS 影子镜像（Rust 聊天数据服务，SQLite 完整镜像 + Tantivy 全文派生索引），但只供 DeepMemo 记忆检索与 VCPMobileSync 消费，**未接入**话题搜索路径。
- **Chatbox**：搜索候选由 `@chatbox/core` 的 `SessionSearchService` 从行存储分页读取，匹配规则在 `native-session-search.ts`，扫描当前消息与历史 Thread，返回命中的具体消息，点击结果后调用 `scrollToMessage` 定位。实现仍是数据层分页扫描，没有使用 DOM 搜索或持久化倒排索引。
- **LobeHub**：服务端 `TopicModel.queryByKeyword` 用 BM25 同时匹配 Topic 标题和消息内容，但返回的是 Topic 列表，不直接定位到具体消息。另有 `message.searchMessages` 后端查询端点，但本次未找到聊天 UI 对该端点的调用，因此不能把它等同于用户可见的消息定位搜索。
- **SillyTavern**：本次仍未找到聊天内容检索 UI；现有 `search` 相关代码集中在端点/扩展和 slash command 语义，搜索范围限于这些代码位置。
- **Risuai**：本次未找到消息内容搜索——检查了全部 UI 组件与 `src/ts` 的 search/filter 入口，未发现对会话消息数组做关键词检索的 UI 或工具函数；MCP 只提供按 offset/count 分页读取当前会话的聊天历史接口，无内容检索。
- **DeepChat**：两层搜索均已确认。跨会话全文搜索把完成/错误消息写入 `deepchat_search_documents`，SQLite FTS5 虚拟表带三个触发器同步，查询用 bm25 或 `LIKE` 回退，命中直接定位到消息（message_id）并可滚动到目标行；搜索同时经 MCP 服务 `conversationSearchServer` 暴露给模型工具与设置页。
- **Hermes Agent**：SQLite `state.db` 带会话搜索 mixin/FTS，会话列表与搜索在 SQL 中完成，前端只取必要字段；笔记确认了后端索引路径，但未把桌面命中跳转逐项展开。
- **Jan**：`useThreads` 用 Fzf 懒建索引，SearchDialog 展示并导航 Thread；这是会话列表搜索，不是消息正文命中后定位。
- **Manifold Desktop**：逐个读取 session JSON，对整份 dump 做不区分大小写子串匹配，无索引和结果上限；而正常聊天未保存，搜索 API 也可能搜不到刚聊过的内容。
- **Open WebUI**：会话列表搜索返回 Chat；工作区全局搜索另聚合标题和消息内容，命中带消息 id 和片段。数据侧查询展开 history JSON，没有据此确认持久化全文索引，UI 跳转另见 Chat UI 专题（[来源](<Open-WebUI-会话与消息管理调查笔记.md>)）。
- **NextChat / AstrBot**：本次单项目笔记没有把聊天内容搜索作为完整链路展开；不能据会话列表或管理页入口推断存在消息级检索。
- **Pi**：CLI/TUI 选择器扫描会话，结果为会话级，无消息索引；p2 搜索插件另用 SQLite FTS5，不能将它视为 coding-agent 已接入的能力（[来源](<Pi-会话与消息管理调查笔记.md>)）。
- **Codex**：没有 SQL 全文索引，`threads` 表只有普通列与 B-tree 索引。全局搜索先用 ripgrep 以固定字符串扫描 rollout 目录（无 ripgrep 时退化为进程内扫描），结果按线程分页并附片段；线程内定位基于分页投影项做子串匹配，返回字符区间和绑定线程、搜索词与下一个投影序号的游标。因此"命中到具体消息"只在分页历史线程内成立，跨会话搜索的粒度仍是线程文件。
- **OpenCode**：仅会话标题 `LIKE` 搜索，结果定位到会话；**消息内容全文搜索本次未找到实现**。消息分页用游标（base64url {id,time}），App timeline 向上加载。
- **OpenOcta**：搜索只覆盖元数据——显示名、label、subject、sessionId 与会话键都是大小写不敏感子串匹配；**消息内容全文检索本次未找到**，检索 search/query/FTS/index 只见到上述元数据匹配、`sessions.preview` 的尾部预览，以及一个仅被测试引用的历史检索函数。列表是合并各 agent 索引后全量过滤排序，预览另读文件末 64KB。
- **DeepSeek Harness**：live-preferred 的逻辑语料层 `session-query` 提供精确读取（会话、表面、事件、标题）与关系追踪，事件读取复用核心表面折叠，把每个事件标记为 current/shadowed/log-only 三类；唯一全文实现是 `session-query-sqlite`——FTS5 配合 `unicode61` 分词，查询按字面短语转义（MATCH 语法当数据），跨会话结果按最强命中事件分组，返回带 snippet 的分页（不透明 branded cursor，generation 变化即失效）。索引是派生的独立数据库，TEMP 表放 live 行、持久表放已落库行，revision 对比后只增量检查新变更日志；`openAt: never` 可整体关闭搜索。命中粒度是事件（消息级），但用户可见的 UI 跳转链路本次未确认（属 Chat UI 类目）。
- **VCPMobile**：全局搜索跨 Topic 查询本地消息 FTS，并支持所有者、角色、发言者和时间过滤；短词回退参数化子串查询。结果带完整消息身份，点击先确认记录仍存在，再打开锚点窗口。时间排序支持游标分页，相关度排序不提供游标翻页（[来源](<VCPMobile-会话与消息管理调查笔记.md>)）。
- **OpenClaw**：列表搜索只匹配显示名、label、key、sessionId、category 及可解析的模型字段，不扫描正文；正文搜索走 `sessions.search`——per-agent SQLite FTS5，只索引活动路径中 user/assistant 消息的可读文本块，回退/分支文本、工具结果与图片不成为普通命中，查询词按空白分词并 AND 组合，命中带 message id（消息级）。FTS 是随 transcript 维护的派生索引，dirty 时旧行被排除并返回 `indexing`，由后台 reconcile 重建后才作为可靠结果返回。

**结论**：Chatbox 的数据扫描、DeepChat 的 FTS 和 VCPMobile 的跨 Topic FTS 均已追到消息定位链；其中 Chatbox 没有持久倒排索引。Open WebUI 全局搜索另返回消息身份，LobeHub 和 OpenClaw 需分开看查询粒度与 UI 交接。会话级结果、消息级命中、全文索引和跳转入口是四项独立证据，不能彼此代替。

## 数据层技术债（有具体代码证据支撑的）

- **AIO Hub**：跨会话搜索无索引，延迟会随数据量线性增长（静态推断，未实测）；会话与索引虽有原子写、revision 和锁，跨实例仍未发现内容合并机制。删除转入回收目录并写 tombstone，当前聊天模块未找到恢复入口；撤销栈仅在运行时保留。
- **Chatbox**：消息已改为平台行树，会话列表元数据也由两套平台实现（桌面/Web 用 IndexedDB、移动端用 SQLite），IndexedDB 那套仍不做 version 升级、只做加法式演进；侧栏"生成中/回复完成未读"指示仍是内存态（`sessionActivityStore` + `generation-runtime`），不写 `SessionMetaRecord`、不落盘，重启即清空；meta 行损坏或缺失时可由会话头与消息行重建列表，读不出的会话以仅元数据的 `recoveryArchived` 记录保留（正常完整写入会清除该标记），归档另带一次性 Undo toast。
- **Cherry Studio**：删除 Topic 不主动清理磁盘文件（附件经 `chat_message_file_ref` 引用计数 + FileManager 策略化 GC 回收，旧 `TopicService.ts:316` 的 TODO 已随 file-manager 治理移除，回收时机未运行验证）；`docs/references/chat/message-tree.md` 的 Flow canvas "forward reference" 说法已随文档更新删除，并新增 "Persisted awaiting-input branches" 一节描述空分支叶子语义。
- **LobeHub**：`doctor/diagnose.ts` 用于检测和修复读取器无法完整渲染的消息树；`reconcileAssistantToolLinks` 用于修复乐观更新在 step 边界丢失工具引用的问题；另有 `#writeThroughMessageCache`（`query.ts:302-330`）处理本地分桶 key 与服务端缓存 key 不同构时的写缓存跳过。
- **AstrBot**：会话切换/新建的 SharedPreferences 有 60 秒防抖，进程崩溃可能丢失这段时间内的选择状态。
- **DeepChat**：SQLite 加密配置、事务隔离、崩溃恢复和 IPC revision/cursor 在网络中断、快速切换会话时的行为未运行验证；搜索文档、Tape 和 transcript 的完整迁移链也未全部追踪；pending input 队列按会话计活动上限 10，达到上限即拒绝新入队。
- **Hermes Agent**：legacy 句柄与持久身份需要翻译，压缩后还需 lineage 重锚；规范网关则以输入账本和执行代际处理受理与恢复，不能套用旧桥的自动续跑语义。
- **Jan**：桌面 `messages.jsonl` 每次整文件重写，长会话每轮 I/O 随消息数增长；`resume:false` 不恢复未完成回合；编辑消息会丢失媒体 content，分支树迁移完整性未验证。
- **Manifold Desktop**：正常聊天没有调用 `SAVE_SESSION`，assistant 不回写 `messages[]`；`CHAT_CHUNK`/`CHAT_DONE` 无会话标识导致多标签广播串扰，重命名整文件覆盖会清空既有消息。
- **NextChat**：WebDAV 合并时间戳实现可疑但未执行多设备复现。
- **Open WebUI**：普通消息读改写与审批结算采用不同并发保证。审批、人工提问及工具认领在事务内读改 output 并双写，提交认领后才调用外部工具；普通消息仍依赖快照/行表对齐。数据库事务与外部副作用的恰好一次执行分开判断（[来源](<Open-WebUI-会话与消息管理调查笔记.md>)）。
- **SillyTavern**：`chat_metadata.integrity` 用于检测多标签页并发写覆盖；`swipe()` 失败时会自动恢复，恢复失败后强制整页重载。
- **Risuai**：整库覆写每轮成本随库体积增长，块级增量只限定重编码范围、写入量不减；每次保存都产生整库备份（保留 20 份），磁盘占用随保存频率增长；reroll 候选纯内存、重启即失，回退只靠复制会话；分支父会话不记录子分支，导航依赖单向回链注释；多窗口是后到者刷新、无字段级合并。
- **VCPChat**：群聊历史写盘没有文件锁，存在并发覆盖丢消息的可能，尚未构造场景验证；未读自动判定以"用户是否参与"为边界——`countUnreadMessages` 过滤系统消息与 `isThinking` 占位后，**只要历史中出现任何用户消息就返回 0，否则返回全部 assistant 消息数**；持久化标记另带 `unreadSource` 来源（手动标记保留、Agent/TopicSponsor 旧标记在用户参与后由前端主动清除）。
- **Pi**：coding-agent 默认仍读写 v3 JSONL，追加型文件随会话持续增长、恢复时全量读入；durable 的 Memory/JSONL/SQLite/IndexedDB 后端与 coding-agent 是独立会话栈，p2 采用前者。
- **OpenCode**：无消息内容全文索引（仅标题搜索）；启动迁移把 v1 会话表结构转换为 v2，运行时以 `session_v2`/`session_message`/`session_part` 单轨承载；客户端读取 HTTP 快照并用事件流增量更新，投影与事件发布分离。
- **DeepSeek Harness**：JSONL 顺序媒体 `readFrom` 每次全量解析后再跳过，长会话读取成本随日志增长（压缩率未实测）；追加型日志只增不减，体积靠 zstd 帧缓解；跨进程写由 writer claim 加 kernel lease 排斥（同一后端实例内的多写者仍靠 revision token 检测变更、不仲裁）；无会话删除 API——workspace 的登记删除与归档只移除分组索引，日志与文件保留。
- **OpenClaw**：活动路径与 FTS 是从 transcript 事件派生的投影，前向推断失败时需整树重建（dirty reconcile）；schema 版本已到 40，并按能力拆出多组特性版本常量，升级时旧搜索派生结构会被丢弃重建；SQLite 与 PostgreSQL 共用同一 store 契约，引擎差异落在连接、schema 准入与提交通知的适配层；事件与归档追加增长，archive 发布失败依赖 pending row 与重试；列表/历史/FTS reconcile 与归档 worker 的规模性能未运行验证。
- **Codex**：回退保留全部旧 rollout 文件，磁盘占用不随回退下降；文件扫描版列表有 10000 个文件的硬上限并返回 `reached_scan_cap`；SQLite 与 rollout 在崩溃窗口内的不一致、Legacy → Paginated 迁移回滚、压缩同胞文件与附属线程的组合均未故障注入；名称索引是独立追加文件，因此改名不重写历史，但也多一份要同步的状态。
- **OpenOcta**：`sessions.json` 的读—改—写没有锁，并发 patch 或 touch 会以后写覆盖先写，消息追加本身不受影响；压缩按行而非按回合，可能把一条消息切成两半且不重算 token 快照；附件以 base64 同时写入文件和消息块，转录随图片体积增长；单行超过 32MB 会整行解析失败被丢弃；删除接口返回的 `archived` 实际列出的是已永久删除的路径。

## 设计取舍与已确认边界

- **会话主体命名不能按名字直接对齐**：比较基准应是"该词在自己项目里处于哪一层、内部还能不能再挂子容器或分支"。
- **文件级存储项目共享一致性问题**：整份读写（SillyTavern、VCPChat、Jan 桌面端、AIO Hub）在长会话下 I/O 与解析成本随长度线性增长；数据库行项目则要处理双写对齐（Open WebUI）或身份翻译（Hermes Agent）。AIO Hub 的协调器、原子替换、revision 与 tombstone 约束旧写，正常启动只按文件名增量核对索引，损坏会话隔离、索引后台恢复；这些约束与搜索索引、内容合并分别处理。
- **客户端会话与插件历史可以并存**：VCPToolBox 的客户端仍提交完整历史并拥有导航与分支，OneRing 另有跨重启的消息与回合记录。其 HTTP 完成和异步提交分属不同边界，不能据客户端所有权推导服务端无持久化（[来源](<VCPToolBox-会话与消息管理调查笔记.md>)）。
- **嵌入式会话与外置存储并存（Risuai）**：普通会话随角色进入主存档，冷数据和 remote 角色由引用连接。插件冷索引独立批量刷新，主数据库另行保存；失败保留旧指针并重试，页面隐藏仅 best-effort flush，强制退出的耐久性未验证。
- **分支与回退分离（Risuai）**：分支靠复制会话实现，回退也只能靠分支或复制——消息编辑删除没有版本历史或 undo；reroll 是内存候选、不落盘，与 SillyTavern 的 swipes 数组字段形成对照。
- **多窗口不合并（Risuai）**：BroadcastChannel 互斥让后到标签页刷新，多用户实时同步是会话级整对象覆盖，都没有字段级冲突解决。
- **AIO Hub 将历史、诊断和运行态分开保存**：实发快照按会话独立写文件，最多 10 次尝试、单尝试 1 MiB、单会话 4 MiB，清空 epoch 与删除标记抑制迟到写入；一份请求可关联多个服务端响应段节点。压缩只恢复已提交摘要，子任务快照恢复把非终态标成 interrupted/stale，保留子会话定位，未接自动继续推理（[AIO 会话笔记](<AIO-Hub-会话与消息管理调查笔记.md>) 第 6.1–6.3 节）。
- **类目边界**：本对比只回答数据语义；流式节流落盘、压缩触发与中断结算在对话请求与上下文横向对比；搜索入口、分支导航与消息操作的用户工作流在 Chat UI 横向对比。
- **追加事实与可见历史分离（DeepSeek Harness）**：模型从五类表面派生历史，压缩保留影子化原事件；模型尝试的原始流在收口时内嵌。成本在日志持续增长和读取折叠，zstd 帧减小磁盘体积。
- **格式版本惰性迁移（DeepSeek Harness）**：当前 v4，格式目录按相邻版本边组装读取器；读旧代仅在内存迁移，写打开发布不可变后继文件，源字节保留。未知且未标可忽略的事件会拒绝重建，避免静默丢失事实。
- **模型历史与 transcript 双投影（DeepSeek Harness）**：模型读表面（遮蔽被替换范围），人类 transcript 读 append-origin 事件，两者同源于日志但语义刻意不同：替换拷贝只服务模型，不吞掉用户已见过的对话。
- **可寻址身份与 transcript 代际分离（OpenClaw）**：会话用 `sessionKey` 稳定寻址、以 `current_session_id` 表达当前一代 transcript，reset/rewind/branch/recovery 通过轮换 generation 保留可追踪历史，并用 expected `sessionId`/lifecycleRevision 拦截 stale writer；手动压缩不再提供检查点 branch/restore RPC，改走 `sessions.compact`（预检、裁剪、写压缩边界并发布 session 状态事件）；代价是读取必须区分逻辑会话、当前 generation 与历史窗口，删除先归档再回收，依赖归档 worker 与 pending row。通用 export/import RPC 本次未找到。
- **同为追加日志，索引策略决定恢复路径（Codex / OpenOcta）**：Codex 把 SQLite 当可丢弃的投影，恢复靠回放 rollout，列表与分页可读库，回退靠切换指针；OpenOcta 没有投影，每轮上下文、列表、预览与成本统计都重读文件。前者的代价是投影表与迁移子系统、以及文件与库两份状态要对齐；后者是 O(文件) 读取、索引无锁且没有 schema 版本。
- **"重开"与"回退"是两种语义（Codex / OpenOcta）**：Codex 的回退保留同一线程 id、换一份物理历史，因此可审计、可切换回；OpenOcta 的 `/new`、`/reset` 换 sessionId 与新文件，旧文件只留在磁盘上，没有指回旧历史的入口。

## 未验证事项

- DeepChat 的 FTS5 搜索索引写入触发点与清理策略未完整追踪。
- SillyTavern 隐藏消息（`is_system`）是否真的被排除出 prompt 构建未核实（属于数据与执行的交界，见请求类对比）。
- VCPChat 群聊写盘并发覆盖风险未构造场景验证；VCP-CDS 影子镜像与 `history.json` 之间的摄取一致性未做运行验证。
- Hermes Agent 压缩轮转后 lineage 重锚的完整行为未实测。
- DeepSeek Harness：崩溃恢复路径（torn tail 截断、interrupted closers 合成）与 resume 往返未运行验证；跨进程写同一 JSONL 的 kernel lease 行为、FTS5 召回质量与同步阻塞影响、/export ZIP 端到端均未实测。
- Risuai：冷存储读写与惰性恢复、备份回退、账户迁移、WebRTC 多用户同步、多标签页竞争均未运行验证；多窗口广播与 bin 写入之间的竞争窗口未实测；导入导出（risuChat v1/v2、JSONL Tavern、HTML `.idat`）只核实了识别与转换代码，未用样本文件验证；"消息内容搜索不存在"的结论受检查范围限制（未覆盖插件第三方能力与 Hub 服务端）。
- OpenClaw：未运行真实 Gateway、Control UI 或多窗口场景，事件乱序、客户端 delta merge、断线重连与 in-flight snapshot 恢复为静态推断；PostgreSQL 引擎只按文档与 schema 注释确认契约，未实际启动 PG 16–18 或验证双引擎迁移、备份与恢复；崩溃、SQLite worker 失败、archive 发布中途退出、legacy `sessions.json`/旧 transcript 端到端迁移与大规模 FTS reconcile 未实测；通用 export/import RPC 与通用消息级就地编辑/删除 RPC 的"未找到"均受本次检查范围限制。
- Codex：SQLite 与 rollout 在崩溃窗口内的不一致程度未通过故障注入验证；`revert` 在多进程并发、压缩同胞文件与附属线程组合下的行为未实测；Legacy → Paginated 迁移的中断恢复与回滚路径未运行验证；ripgrep 在超大历史量级下的分页稳定性与内存占用未实测，`AttachmentStore` 的实际默认后端由宿主注入。
- OpenOcta：并发 patch 与 touch 的实际丢失范围未做运行验证；压缩把消息切成半截后模型对首条残缺消息的处理未实测；单行超过 32MB 时的界面表现、多窗口同时打开同一会话与重连后历史合并、`session.store` 指向自定义路径时旁路行的落点、旧版兼容路径在真实升级场景中的命中率均未验证。
