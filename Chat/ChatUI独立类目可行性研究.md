# Chat UI 独立类目可行性研究

> 研究日期：2026-08-11
>
> 研究对象：16 篇单项目 Chat 调查笔记、`Chat横向对比.md`、消息渲染器类目的指南与单项目笔记
>
> 研究目的：判断 Chat UI 能否形成稳定、可比较且不与相邻类目重复的独立调查范围
>
> 本文定位：类目可行性研究与调查指南草案，不改写现有项目结论

## 结论

Chat UI 可以独立成类目，建议名称为 **Chat UI（对话工作台与交互）**。

它的核心对象不是 UI 组件库，也不是消息正文的渲染器，而是用户围绕一次或多次对话完成工作的交互表面：进入会话、组织输入、配置发送、观察生成、停止或追加指令、操作消息、切换分支、搜索定位，以及离开后恢复现场。

该类目应采用适用性门槛，不要求所有项目形式对称：

- 项目拥有自己控制的最终用户聊天界面、TUI 或 WebChat 时，建立单项目 Chat UI 笔记；
- 项目只提供后端协议、网关或第三方页面增强时，标记为不适用并说明边界；
- 外部 IM 客户端的界面不计入项目自己的 Chat UI，项目自带的 WebChat 或管理界面可以单独调查。

## 可行性依据

### 已有材料足够形成独立研究线

按现有二级标题保守提取，“工作台布局”“核心 UI 交互”“Chat 交互边界”“前端发送与渲染”等候选章节已经覆盖 14 个项目，合计约 32,820 个字符。Jan 的输入、队列、Thread 导航和消息操作散落在其他章节中；VCPToolBox 则明确没有自己的聊天主界面。

这 32,820 个字符只计算标题边界清晰的现有段落，没有纳入以下内容：

- 会话列表、未读、搜索和分支导航中同时包含数据与交互的段落；
- 输入框、附件、模型切换、工具审批和队列状态中同时包含请求与交互的段落；
- “UI 交互再深挖”中与聊天工作流直接相关的少量内容。

因此，现有材料不是为了凑出一个新类目而重新命名；只是目前被分散存放在 Chat、消息渲染器和通用 UI 补录中。

### 横向对比已经出现稳定维度

当前 `Chat横向对比.md` 的 UI 主表已经能够统一比较：

- 主界面和导航；
- 消息对用户的投影方式；
- 输入与生成中交互；
- 关键 UI 取舍。

表中还能稳定观察到多模型并行、队列与 follow-up、分支树图、群聊调度、TUI/Web 双表面、多窗口、后台生成和第三方 UI 边界。这些差异无法仅靠会话 schema、请求编排或 Markdown 渲染解释。

### 相邻类目中存在范围泄漏

消息渲染器笔记中已经出现输入框、会话列表、导航、模型切换和消息操作等内容。它们有时是理解渲染入口所需的上下文，有时已经进入完整聊天工作流。

建立 Chat UI 后，消息渲染器可以回到更稳定的职责：消息状态如何成为列表、消息壳、Markdown、结构化 part 和可见反馈。Composer、会话侧栏、工作台布局和生成控制则有明确去处。

## 类目定义

### 调查对象

项目自己控制的聊天工作台及其交互状态，包括 GUI、Web、移动端、TUI 和项目内置 WebChat。

### 用户主链

```text
进入聊天表面
  -> 创建、选择或恢复会话
  -> 组织文本、附件和其他输入
  -> 确认 Agent、模型、工具等发送前状态
  -> 提交或排队
  -> 观察生成、审批、停止或追加指令
  -> 编辑、重试、续写、分支、复制或删除消息
  -> 搜索、定位、切换会话或离开
  -> 再次进入并恢复工作现场
```

一篇标准调查至少应走通这条主链中的一个完整闭环。项目不支持的步骤明确标记，不用扩写占位内容。

## 必查问题草案

1. **工作台结构**：聊天入口、会话导航、消息区、输入区、辅助面板和移动端布局如何组织？哪些区域可折叠、分离或多开？
2. **会话导航**：新建、切换、分组、置顶、归档、未读、拖放、搜索和定位通过哪些界面完成？切换时保留哪些局部状态？
3. **输入与草稿**：文本、富文本、命令、提及、附件、语音、变量和快捷回复如何输入？草稿按会话还是全局保存？
4. **发送前配置**：用户如何看到和修改 Agent、模型、参数、工具、知识库、联网和推理设置？这些设置的作用域是否清晰？
5. **生成状态与控制**：排队、发送、流式、等待审批、后台生成、停止、错误、重试和完成如何反馈？按钮状态与真实任务状态如何对应？
6. **消息操作工作流**：复制、编辑、删除、重试、续写、分支、版本切换、翻译、导出和审批从哪里进入？操作可用性由什么状态决定？
7. **搜索、分支与阅读导航**：会话内搜索、跨会话搜索、消息跳转、分支树、版本导航、minimap 和滚动恢复如何协作？
8. **并发与多路对话**：多会话、多模型、群聊、子 Agent 和后台任务如何在界面中区分？用户如何知道哪一条仍在运行？
9. **跨窗口与跨平台连续性**：桌面、Web、移动端、TUI、悬浮窗和系统通知之间如何同步当前会话与生成状态？
10. **关键路径可用性**：键盘能否完成选择会话、输入、发送、停止和消息操作？焦点、可访问名称、响应式变化和错误恢复是否保持主链可用？
11. **UI 状态所有权**：draft、selection、panel、scroll、active message、pending input 和 busy 状态存在哪里？切换会话、刷新和重连时如何恢复？

## 推荐结构草案

```md
## 结论摘要
## 工作台边界与用户主链
## 1. 页面结构、导航与多窗口
## 2. 会话列表、搜索与现场恢复
## 3. Composer、草稿、附件与快捷输入
## 4. Agent、模型、工具与发送前配置
## 5. 发送、排队、流式反馈与停止
## 6. 消息操作、分支与版本导航
## 7. 多会话、多模型、群聊与后台生成
## 8. Chat UI 状态所有权与同步
## 9. 键盘、焦点、响应式与关键路径可用性
## 10. 设计取舍与已确认边界
## 11. 未验证事项
## 12. 关键源码索引
```

标题是覆盖检查表，不要求机械保留。没有 GUI 的 TUI 项目可以按命令面板、选择器、状态行和键盘工作流重新组织。

## 与相邻类目的边界

| 同一能力 | 会话与消息管理 | 对话请求与上下文 | Chat UI | 消息渲染器 |
|---|---|---|---|---|
| 停止生成 | 不展开 | abort、任务取消、最终化和落盘语义 | 停止入口、按钮状态、等待反馈和失败恢复 | 中断消息、partial 内容和错误块如何显示 |
| 搜索 | 索引、查询对象、命中数据和定位标识 | 通常不涉及 | 搜索入口、过滤器、结果列表和跳转工作流 | DOM 高亮、滚动锚定和虚拟窗口内的可见定位 |
| 分支 | 树模型、active pointer、复制或版本语义 | 从哪个节点重新构建请求 | 分支按钮、兄弟版本导航、树图和确认流程 | 活动路径如何投影为消息列表 |
| Composer | 只记录草稿是否持久化及绑定粒度 | 输入如何转换为请求 parts 和参数 | 编辑器、附件、命令、提及、快捷键和发送前配置 | 不负责；只在输入组件与消息区共用渲染器时记录交接 |
| 消息操作 | 编辑、删除、重试产生的数据变更 | 重试、续写和再生成的执行链 | 操作入口、可用性、菜单、确认和反馈 | 操作栏在消息壳中的组件装配与视觉状态 |
| 工具审批 | 审批结果是否写入会话 | 审批如何恢复工具循环 | 审批卡、待处理提示和用户操作路径 | 工具卡内容与状态如何渲染 |
| 多会话生成 | 每个会话保存什么任务引用 | 并发、队列、后台任务和取消粒度 | 运行标记、切换反馈、通知和返回入口 | 当前消息流如何更新可见列表 |

边界判断使用三个问题：

1. 研究的是业务对象如何改变，进入会话与消息管理；
2. 研究的是生成任务实际如何执行，进入对话请求与上下文；
3. 研究的是用户如何发现、触发、观察和恢复这个能力，进入 Chat UI。

消息渲染器只接手内容和列表的投影实现。这样允许同一能力在不同笔记各出现一次，但每次回答的问题不同，不复制整条调用链。

## 通用 UI 内容过滤规则

Chat UI 独立后，最大的风险是再次吸收所有界面调查。以下规则需要写入指南。

### 应纳入

- 会话侧栏在移动端如何变为抽屉，以及切换后是否保持当前输入；
- 发送、停止、排队和审批控件的状态与反馈；
- 消息搜索弹窗如何返回并定位到目标消息；
- 附件拖入 Composer 时的可见反馈和失败恢复；
- 回复完成通知能否深链回对应会话；
- 键盘能否完成聊天关键路径；
- 分离窗口如何同步草稿、busy 和 active session。

### 不应纳入

- 全项目使用了哪套 Modal、Toast 或 Tooltip 库；
- 所有页面的主题 token、动画时长和响应式断点清单；
- 设置页、关于页、许可证页和首次启动流程的完整盘点；
- 与聊天无关的托盘、更新器、资源管理器和窗口管理；
- 仅为了评价视觉风格而记录的颜色、阴影和装饰细节。

### 只记录交点

- Chat 页面调用通用 Modal 时，记录这个弹窗承担的聊天任务、关闭语义和状态恢复；不追完整 Modal 基础设施。
- Chat 页面使用 Toast 时，记录错误、完成或审批通知是否能让用户继续工作；不统计全仓库 Toast 调用。
- 主题和响应式只有在改变聊天布局、控件可达性或状态连续性时展开。
- 无障碍只覆盖聊天关键路径及其直接依赖，不升级为全应用审计。

## 项目适用性

| 项目组 | Chat UI 处理方式 |
|---|---|
| AIO-Hub、Chatbox、Cherry Studio、Jan、LobeHub、NextChat、Open WebUI、SillyTavern、VCPChat | 标准 GUI/Web 调查，现有材料较充足 |
| DeepChat、Hermes Agent、OpenCode | 同时比较 GUI、Web 或 TUI 表面，明确共享状态与不同交互协议 |
| Pi | 以 TUI 键盘工作流、选择器、状态行和命令入口为主，不套用桌面布局标题 |
| AstrBot | 只调查项目自带 WebChat 和管理界面；QQ、Telegram 等外部客户端 UI 不归项目所有 |
| Manifold Desktop | 可以建立短笔记，重点记录标签页、全局 stop 和持久化缺口，不扩写不存在的能力 |
| VCPToolBox | 不适用；AdminPanel 是运维界面，OpenWebUISub 是第三方聊天页面增强层 |

## 横向比较字段

至少记录：

- 主工作台拓扑和导航模式；
- 会话列表组织、未读、搜索和恢复；
- Composer 类型、草稿粒度和附件入口；
- Agent、模型、工具等发送前配置的可见性与作用域；
- 发送、排队、流式、审批、停止和错误的用户可见状态；
- 消息操作、分支和版本导航方式；
- 多会话、多模型、群聊和后台生成反馈；
- 多窗口、多端和通知的返回路径；
- UI 状态事实源和刷新、切换、重连后的恢复；
- 关键路径的键盘与焦点可用性。

不把“用了哪套 UI 框架”“动画多少”“视觉更现代”作为核心横向字段。

## 主要风险与控制方式

| 风险 | 控制方式 |
|---|---|
| 与消息渲染器重复 | Chat UI 回答用户工作流和状态可见性；消息渲染器回答内容与列表如何绘制 |
| 与请求运行时重复 | Chat UI 到 command/action/RPC 入口为止；abort、队列和恢复的真实执行继续下钻到请求类 |
| 与会话管理重复 | Chat UI 记录界面操作和现场恢复；数据结构、事务和持久化语义留在会话类 |
| 再次变成通用 UI 大杂烩 | 使用“是否属于聊天主链”过滤，并禁止全仓库组件库盘点 |
| 项目之间界面形态差异太大 | 用用户任务和状态反馈比较，不按 React/Vue/TUI 组件名称对齐 |
| 文档数量增加 | 采用适用性门槛；短能力项目允许短文，后端项目不建立占位文档 |

## 试点建议

建议先用四个正例和一个反例验证指南：

1. **Cherry Studio**：覆盖多模型 Composer、Topic 分支图和 Home/Agent 共用消息 UI，最容易暴露与消息渲染器的边界。
2. **Open WebUI**：覆盖队列、停止、工具确认、side-by-side、MoA 和服务端任务，最容易暴露与请求运行时的边界。
3. **OpenCode**：同时有 TUI 和 Web，可以验证指南是否真正按用户任务抽象，而非只适配桌面 GUI。
4. **AstrBot**：项目自带 WebChat，但主要交互来自外部 IM 平台，可以验证“项目拥有的 UI”边界。
5. **VCPToolBox**：作为不适用反例，确认指南不会把运维面板或第三方页面增强误写成项目 Chat UI。

试点完成的判断标准：

- 每篇能走通一条“进入 -> 输入 -> 发送 -> 控制 -> 操作 -> 恢复”主链；
- 不需要复制会话表结构、完整请求编排或 Markdown 管线；
- 同一横向字段可以同时描述 GUI、WebChat 和 TUI；
- 通用 Modal、Toast、主题和动画内容不会重新占据正文主体；
- VCPToolBox 能自然得出“不适用”，而不是被迫生成空洞文档。

满足这些条件后，Chat UI 适合作为第三个正式类目，与“会话与消息管理”“对话请求与上下文”并列；原 Chat 目录则保留短概览和跨类目导航。
