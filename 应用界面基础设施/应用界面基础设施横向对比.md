# 应用界面基础设施横向对比

> 对比对象：AIO Hub、AstrBot、Chatbox、Cherry Studio、DeepChat、Hermes Agent、Jan、LobeHub、Manifold Desktop、NextChat、Open WebUI、OpenCode、SillyTavern、VCPChat、VCPToolBox；Pi 作为 TUI 形态单列
>
> 对比更新日期：2026-08-13
>
> 依据：本类目各单项目调查笔记及其记录的代码快照
>
> 对比方法：按应用装配、弹窗与浮层、通知、主题、响应式、内容交互和验证范围统一比较；表格只保留共同维度，项目细节回到单项目笔记
>
> 对比范围：应用级界面基础设施；聊天业务主链和消息内容渲染分别由 Chat UI 与消息渲染器类目承接
>
> 文档定位：实现学习与跨项目横向比较，不作为整改方案

## 结论摘要

这些项目没有形成共同的界面基础设施方案。弹窗既有 Radix、Reka、Kobalte、Vuetify 和 Mantine 等依赖，也有原生 dialog、手写 DOM 和独立窗口；通知既可能是组件库 Toast，也可能包含持久通知中心、跨窗口语义路由或终端反馈协议。

成熟度差异主要体现在“公共机制覆盖到哪里”。Cherry Studio、DeepChat、Hermes Agent 和 LobeHub 已把弹窗、主题或通知收束到公共层；AIO Hub 和 VCPToolBox 也有完整自研基座。AstrBot、SillyTavern 等项目则更多由业务页面直接消费库或局部实现，统一入口较少。

主题是差异最大的维度。部分项目只提供明暗两档，部分项目支持主色、字体和背景图，Hermes Agent、SillyTavern、AIO Hub 与 VCPToolBox 已形成主题资源或外观编辑子系统。主题权威源也分散在 localStorage、服务端设置、主进程设置文件和终端环境中。

静态源码能确认装配、状态流和事件绑定，却不能替代对焦点顺序、Toast 堆叠、触摸手势、多窗口同步和终端协议的运行验证。下表中的“依赖默认”均表示项目侧没有覆盖，不能直接推定实际行为已经验证。

| 项目 | 产品表面 | 公共界面层 | 主要状态所有者 |
|---|---|---|---|

| AstrBot | Web 管理台 | Vuetify 直接消费，少量公共插件 | Pinia 与 localStorage |

| Cherry Studio | Electron 多窗口 | 内部 UI 包与 Popup Host | 主进程设置、模块级 store |
| DeepChat | Electron 多窗口 | shadcn-vue、Reka、dc-ui | 主进程设置与渲染层 store |
| Hermes Agent | Electron、TUI、Web | 三套独立组件层，共享后端协议 | 各表面独立 store |
| Jan | Tauri、Web、移动端 | shadcn 风格 Radix 组件 | zustand 与后端设置 |
| LobeHub | Web、桌面、移动端 | `@lobehub/ui` 与 antd-style | next-themes、用户 store |
| Manifold Desktop | WinUI + WebView2 | 原生 DOM/CSS 单例组件 | 原生设置与局部 JS 状态 |

共同趋势是应用公共层通常只覆盖“怎么显示”，业务 store 仍决定“何时显示”。DeepChat 的通知和 Hermes Agent 的贡献注册表是少数把策略或应用装配也纳入基础设施的例子。

## 2. 弹窗、浮层与焦点

| 项目 | 主弹窗机制 | 关闭策略 | 焦点边界 |
|---|---|---|---|
| AIO Hub | 自研 BaseDialog | Esc 与关闭按钮共用开关；遮罩可配置 | 项目侧没有统一焦点陷阱 |
| AstrBot | Vuetify Dialog | 依赖默认；persistent 可阻止关闭 | 依赖内部未核实 |
| Chatbox | Mantine 为主，vaul 负责移动端 | 逐弹窗配置 | 部分场景主动关闭焦点陷阱 |
| Cherry Studio | 内部 UI 包封装 Radix | 支持延迟卸载和业务覆盖 | Radix 管理，支持指定归还目标 |
| DeepChat | Reka Dialog 与全局消息框 | 依赖默认；自研 Spotlight 单独处理 | Reka 未下钻；Spotlight 无陷阱 |
| Hermes Agent | Radix Dialog | 依赖默认；Portal 容器处理嵌套浮层 | Radix 未下钻 |
| Jan | Radix、vaul 与全局门控 | 依赖默认 | Radix 未下钻 |
| LobeHub | base-ui 命令式弹窗 | 多数允许遮罩关闭，高危场景关闭 | base-ui 未下钻 |
| Manifold Desktop | 手写 DOM 单例 | 各组件自行处理 | Confirm 缺 Esc、陷阱与归还 |
| NextChat | 每次调用新建 React root | 遮罩点击关闭，无退场阶段 | 无统一焦点管理 |
| Open WebUI | 自研 Modal + focus-trap | Esc、遮罩与滚动锁定 | 项目侧已接入 focus-trap |
| OpenCode | TUI store 栈；Web Kobalte 栈 | TUI 与 Web 各自统一 | TUI 显式归还；Kobalte 未下钻 |
| SillyTavern | 原生 dialog + Popup | 遮罩不关闭；阻塞弹窗双击 Esc | 有归还，没有焦点陷阱 |
| VCPChat | template 弹窗与 Promise 确认框 | 确认框支持 Esc、Enter、遮罩 | 无焦点陷阱 |
| VCPToolBox | BaseModal + feedback Host | BaseModal 完整；命令式确认框较弱 | BaseModal 有陷阱，其他弹窗不一致 |

弹窗“使用同一底层”并不等于行为一致。Chatbox、VCPToolBox 和 DeepChat 都存在不同弹窗类型采用不同焦点或关闭规则的情况。依赖库项目还需要区分项目侧配置和依赖默认，静态调查不能把后者写成已验证事实。

## 3. 通知、Loading 与错误恢复

| 项目 | 临时反馈 | 持久或跨窗口反馈 | 错误恢复层 |
|---|---|---|---|
| AIO Hub | Element Plus 包装与严重级分发 | 通知中心 | Vue 全局钩子、Rust 探针、启动兜底 |
| AstrBot | 单例 Snackbar 队列 | 无独立中心 | axios 拦截与业务捕获 |
| Chatbox | MUI Snackbar + sonner | 无统一中心 | 多层 Sentry ErrorBoundary |
| Cherry Studio | 自研 Toast store | 每窗口 Host | 窗口、路由与消息多层边界 |
| DeepChat | NotificationManager + sonner | 主进程跨窗口语义路由 | 功能级反馈为主，无应用总边界 |
| Hermes Agent | 双栈通知 | 后端通知协议 | 根边界与贡献 slot 边界 |
| Jan | sonner | 无系统通知 | 根级对话框和业务捕获 |
| LobeHub | base-ui Toast | 独立悬浮通知卡 | 路由、局部、启动与 chunk 分层 |
| Manifold Desktop | 单条手写 Toast | 无 | 前端局部处理 |
| NextChat | 手写 Toast | 更新系统通知 | 前端错误提示为主 |
| Open WebUI | svelte-sonner | 浏览器通知与 webhook | 业务级错误反馈 |
| OpenCode | TUI 单条；Web 两代 Toast | 浏览器系统通知 | TUI 与 Web 各自处理 |
| SillyTavern | toastr | Action Loader | 有限重载，无全局错误边界 |
| VCPChat | 浮动 Toast | 持久通知侧栏 | 自定义错误提示 |
| VCPToolBox | feedback Host | WebSocket 通知列表 | 业务捕获，无应用错误边界 |

Loading 也呈现两种路线。LobeHub 和 Cherry Studio 有共享骨架组件，AIO Hub 会按真实布局绘制聊天骨架；Chatbox、Manifold Desktop 等项目则更多使用文本、局部 spinner 或场景自建占位。

错误恢复最完整的不是 Toast 数量最多的项目，而是边界层次清楚的项目。LobeHub 区分路由、局部组件、启动和分包加载；Cherry Studio 区分窗口、路由和消息；Hermes Agent 还会把插件故障限制在贡献 slot 内。

### 主题能力分组

**基础明暗层。** Manifold Desktop、NextChat、Jan 和 DeepChat 的主题入口较收敛，重点是明暗、字号或字体。它们更容易解释权威源，但自定义能力有限。

**产品外观层。** AIO Hub、Chatbox、Open WebUI 和 VCPToolBox 把背景图、主色或布局偏好纳入主题。这里容易出现权威源分裂，例如 Open WebUI 的明暗模式留在设备本地，背景图却随账户同步。

**主题资源层。** Hermes Agent、OpenCode、Pi 和 SillyTavern 支持主题文件、资源注册或扩展贡献。Hermes Agent 还包含 VS Code Marketplace 查询、VSIX 下载、转换和用户注册表；Pi 通过文件系统、包与扩展发现主题，但没有市场 UI。

**特殊切换方式。** VCPChat 通过覆写 CSS 文件后重载窗口切换主题，代价与 CSS 变量热替换不同。LobeHub 则把明暗模式和主色分别交给 next-themes 与用户 store，首屏还需 cookie 和 HTML 脚本参与。

## 7. 动画与 reduced motion

多数项目没有为消息卡片首次出现增加明显动画。常见方案是组件库的开合过渡、CSS transition 和少量局部 motion，而不是全应用统一的页面动效体系。

- AIO Hub、NextChat、Manifold Desktop 和 VCPChat 以 CSS 过渡为主。
- Cherry Studio、DeepChat、Jan 和 OpenCode Web 使用 Tailwind 动画类与 Radix、Reka 或 Kobalte 状态属性。
- LobeHub 与 Hermes Agent 只在少数组件使用 motion；消息列表本身没有统一入场动画。
- SillyTavern 另有流式文本渐显，Pi 和 OpenCode TUI 使用字符帧、flash 或 spinner。
- VCPToolBox 的用户动画开关和 reduced-motion 覆盖最广；DeepChat 也有全局动效 token 与 reduced-motion 兜底。

项目内自定义动画不一定服从全局开关。LobeHub 的面板滑动会检查动画设置，但 WorkflowCollapse 没有同类判断；这类差异需要逐组件核对，不能只凭依赖清单判断。

## 8. 代表性设计差异

**公共层迁移。** Chatbox、LobeHub 和 OpenCode Web 都保留两代基础设施。兼容层能降低迁移成本，也使同类反馈的行为在一段时期内不完全一致。

**跨窗口通知。** DeepChat 将通知拆成渲染层仲裁和主进程语义路由，能按窗口能力与焦点状态投递。其它 Electron 项目多以每窗口 Host 或渲染层浏览器通知为主。

**插件与贡献隔离。** Hermes Agent 的应用壳由贡献注册表组织，插件渲染失败会限制在 slot 内。相比简单的根 ErrorBoundary，这种边界更贴近可扩展应用的所有权结构。

**无框架自研。** Manifold Desktop、NextChat、VCPChat 和 VCPToolBox 都有手写基础设施，但完整度差异很大。VCPToolBox 的 BaseModal 和 feedback Host 已形成公共机制；Manifold Desktop 和 NextChat 仍以模块单例或每次创建 root 为主。

**主题与外观边界。** SillyTavern 的主题文件会打包大量界面偏好，AIO Hub 把外观效果独立成系统，Open WebUI 将背景图放在账户设置，Hermes Agent 则把主题当可安装资源。它们都叫“主题”，实际数据边界并不相同。

## 9. Pi：TUI 形态映射

Pi 是纯 TUI 项目，不适合直接放进 GUI 弹窗、灯箱和断点表格。对应关系如下：

| GUI 概念 | Pi 中的对应机制 |
|---|---|
| Modal / Overlay | overlay 栈；常规选择器通过编辑器插槽替换 |
| Esc 与焦点 | 统一键位注册表；overlay 关闭后恢复 preFocus |
| Toast | 聊天区状态文本、fullscreen flash、OSC 9;4 进度 |
| 主题 | JSON token、终端色彩检测、文件与扩展资源发现 |
| 响应式 | 根据终端行列重新布局 regular 或 fullscreen |
| 图片 | Kitty / iTerm2 协议，无能力时文本 fallback |
| 拖放 | 终端没有文件拖放事件，以粘贴路径和附件补全替代 |
| 剪贴板 | 原生插件、平台命令和 OSC 52 多层回退 |

Pi 的主题、键盘和终端协议基础设施很完整，但读屏、触摸和桌面窗口语义不适用于这一表面。所有终端行为仍需在具体模拟器中验证。

## 10. 未验证事项

- Radix、Reka、Kobalte、Vuetify、Mantine、base-ui 和 focus-trap 等依赖的默认焦点、Esc、滚动锁与动画行为，除单项目笔记注明外均未下钻。
- Toast 的像素级堆叠、遮挡和标题栏避让没有进行统一截图测试。
- 主题首屏、多窗口同步、系统跟随和自定义字体加载多为静态链路确认，尚未跨平台重放。
- 图片灯箱的触摸手势、超大图片性能、OCR 效果和变换后导出质量未统一实测。
- 响应式结论主要来自断点、路由和状态分支；实际窗口拖动、软键盘和安全区域表现未逐项目验证。
- 无障碍结论来自静态语义与事件绑定，不代表完成 WCAG 或读屏审计。
- Pi 的 Kitty、iTerm2、OSC、IME 和 fullscreen 行为未在不同终端模拟器中运行验证。
