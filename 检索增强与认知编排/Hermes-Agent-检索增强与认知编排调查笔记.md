## 结论摘要

**源码直接确认。** Hermes 的检索增强由三条不同目的的路径组成，而非统一知识库 RAG：内置记忆把人工或模型明确写入的短条目保存到 profile 目录下的 `MEMORY.md` 与 `USER.md`，在下一会话启动时作为冻结快照进入系统提示词；可选外部 MemoryProvider 在每轮用户消息前按该消息预取上下文，并只把当前轮的 API 副本附加该结果；`session_search` 则对 SQLite 会话库执行 FTS5 搜索，再返回命中消息的锚定窗口。三者均属于“上下文即时注入”或“工具化检索”，不是文档摄取、Embedding 或多阶段认知路径系统。

**源码直接确认。** 一条完整的外部记忆主链是“用户消息 -> provider `prefetch` -> `<memory-context>` 围栏写入本轮 API 内容 sidecar -> 模型调用 -> 完成回合异步 `sync_turn` -> 下轮预取”。sidecar 与原始消息同行持久化，以保证后续重放的 API 前缀与初次请求字节一致；因此每轮召回结果并不改写已存的用户正文，也不在同一会话中重建系统提示词。入口与拼装见 `agent/turn_context.py:54-109, 1375-1434`，异步写回编排见 `agent/memory_manager.py:564-770`。

**源码直接确认。** `session_search` 是另一条由模型工具调用触发的跨会话召回路径。它按查询、滚动、读取和浏览四种参数形态工作；查询先从 FTS5 候选中排除子代理等默认隐藏来源、将 cron 结果降权、按会话谱系去重，再围绕命中消息取窗口与首尾书签。它不调用 LLM，也不把结果自动写回记忆或自动驱动下一次查询；是否继续滚动、读取或使用结果由模型决定。见 `tools/session_search_tool.py:1-33, 761-950, 953-1079`。

**静态推断。** Hermes 有“主动记忆演化”的接口和后台复习机制，但它并非所有安装均可用的固定检索链：内置文件记忆的写入由模型工具调用和可选人工审批驱动；外部提供方的提取、向量化、重排、会话结束归纳与长期用户建模由被选中的单一插件实现。本仓库可确认宿主生命周期、隔离和失败处理，不能据此确认任一外部后端的召回质量、索引结构或自动知识演化效果。

## 事实对象、摄取与索引

### 内置记忆对象

内置记忆是以裸 `§` 分隔的文本条目，不是带向量、标签或关系边的数据库记录。`MEMORY.md` 保存环境事实、惯例和经验，`USER.md` 保存用户身份、偏好及沟通习惯；两者有独立字符上限，加载时去重，并为系统提示词保留一份不随会话中写入而改变的快照。学习图把每个分隔块投影成可见卡片，并按词汇重叠连接到技能，但该图是观察投影，未作为运行时召回索引。见 `tools/memory_tool.py:1-24, 159-264`、`agent/learning_graph.py:193-245`。

写入入口是 agent-level `memory` 工具。它提供 add、replace、remove 与原子批量操作，先执行威胁模式扫描和目标可用性检查，再在独立锁文件保护下重新读取、检测外部编辑漂移并原子写回；若开启审批，工具结果可先成为待批准写入，只有实际提交成功的变更才会通知外部 provider。内置记忆并不会从普通对话自动抽取事实。见 `tools/memory_tool.py:80-100, 227-385, 1207-1390`、`agent/memory_manager.py:1201-1249`。

### 外部提供方与会话索引

MemoryProvider 是可选扩展契约，定义初始化、预取、回合同步、工具暴露、会话结束、会话切换和压缩前回调。该契约不规定文档切块、Embedding、K 值、重排器或结果字段，因此 Honcho、Mem0 等 provider 可能采用不同的事实模型；本笔记不将它们的能力归结为 Hermes 核心能力。宿主对非内置预取设置 8 秒默认等待，超时跳过该轮，并将回合写回放入单线程后台队列以维持写入顺序。见 `agent/memory_provider.py:1-31, 110-247, 263-327`、`agent/memory_manager.py:410-439, 564-639, 714-770`。

会话检索的事实源是 profile 的 SQLite `state.db` 消息与会话行。检索函数根据查询形态选择通用 FTS5、CJK bigram、trigram 或 LIKE 路由；索引重建进度可返回给 `session_search` 调用者，以避免把重建期间的稀疏结果当作完整历史。工具默认只检索 user/assistant 角色，工具输出需显式要求才纳入。见 `hermes_state_search.py:1415-1487`、`tools/session_search_tool.py:259-278, 761-813, 1145-1247`。

## 查询、候选与重排主链

### 外部记忆预取与注入

每个非平凡用户消息开始时，运行时先通知 provider 新回合，再同步调用 `prefetch_all`。管理器逐 provider 聚合返回文本，外部 provider 的单次预取逾时或报错不阻止对话；返回内容经 `<memory-context>` 和“不是新用户输入”的系统说明围栏包裹，附加到 API-bound user content。原始消息仍保持干净，带注入内容的 `api_content` sidecar 随消息持久化，后续回放使用同一 sidecar，从而兼顾动态记忆与提示词前缀缓存。见 `agent/turn_context.py:54-109, 1375-1434`、`agent/memory_manager.py:386-400, 564-639`。

这一链路是单轮查询：provider 得到当前用户消息，返回已格式化上下文，宿主不保留候选分数、来源、K 值或 rerank 原因的统一结果契约。`recall_status` 仅可提供“召回了 N 条记忆”的确定性状态提示，不能替代候选可解释性。普通问候和斜杠命令会跳过预取，避免无语义消息引入陈旧上下文。见 `agent/memory_provider.py:73-107, 178-211`、`agent/memory_manager.py:641-670`。

### 跨会话 FTS5 召回

`session_search(query=...)` 先向数据库请求最多 300 个 FTS 候选，以便在按谱系去重之前仍能找到互动会话。随后稳定地将 cron 会话排到互动会话之后，排除当前仍在活上下文中的谱系，并对已压缩或 `/new` 后离开上下文的旧内容保留可发现性。最终结果以命中锚点为中心，第一名返回约五条消息的窗口和首尾书签，较低排名可只返回锚点；调用方还可再用锚点滚动，或按会话 ID 读取。见 `tools/session_search_tool.py:42-96, 281-295, 761-950, 953-1079`。

这里的“重排”只包括 FTS/BM25 或可选时间排序、cron 降权、谱系去重和结果负载整形，没有跨查询的 reranker 或 LLM 判断。输出包含会话 ID、来源、模型、标题、命中角色、消息 ID、摘要片段、窗口和分页方向等可复查字段，但不把自身结果写入 `MEMORY.md`，也不主动发起下一轮检索。见 `tools/session_search_tool.py:884-950`。

## 阶段、反馈与结果注入

Hermes 支持模型在同一工具循环内根据 `session_search` 结果再次读取或滚动会话，也允许一个外部 provider 在自身实现中维护异步预取缓存；这些是可组合的工具行为。当前宿主没有把“召回结果 -> 重写 query -> 下一阶段召回”编码为固定状态机，未设置跨阶段 K、停止条件或统一的候选融合层。因此它可与提供跨会话全文召回或用户记忆的客户端比较作用域、注入口和恢复性，不能按同一维度与思维簇、关系传播或递进查询系统比较。

内置文件记忆与外部预取的注入位置也不同。前者的快照在会话初始化时进入系统提示词，当前会话内即使写入成功也不会改变该提示词；后者只加入本轮 user message 的 API 副本，并将精确字节持久化用于后续重放。这一取舍避免会话中修改历史前缀，但意味着刚写入的内置条目要到下一会话才自动可见。见 `tools/memory_tool.py:1-24, 159-167`、`agent/turn_context.py:59-70`。

## 记忆写回与主动维护

回合完成后，MemoryManager 将 user/assistant 内容和可选完整消息列表交给每个已启用 provider 的 `sync_turn`。写入在单 worker 后台串行执行，避免慢网络后端把 UI 长时间保持在运行状态；进程退出时只做有限等待，未完成工作可被放弃并记录。会话结束、切换与压缩前也有明确 hook，provider 可在这些边界提取或检查将被压缩的内容。见 `agent/memory_manager.py:714-869, 954-1061, 1083-1143`。

内置文件记忆没有 `sync_turn` 自动抽取。模型须主动调用 memory 工具，且写入可受用户审批；写入成功后，管理器会将 add、replace、remove 的来源元数据镜像给外部 provider。这个设计将短期会话历史的全文检索、人工可读的稳定事实和外部后端的自动提取分离，代价是它们没有统一的去重、冲突解决或来源图。见 `tools/memory_tool.py:1262-1331`、`agent/memory_manager.py:1171-1249`。

## 与相邻谱系的可比/不可比边界

与传统客户端记忆或跨会话搜索相比，Hermes 可比较的维度是 profile 作用域、文件记忆是否在下会话生效、FTS 的谱系去重、外部 provider 的每轮预取及其写回边界。它没有内置文档摄取资产、Embedding 模型选择、向量库或统一来源引用协议，不能在这些维度与知识库产品做同口径比较。

与检索驱动认知编排相比，本仓库提供的是模型可自行组合的检索工具和 provider 生命周期，而非由框架保存阶段状态、根据结果改变查询方向、传播关系图或形成固定思维模块链。后台复习或外部 provider 的智能行为应在对应实现已被逐条追踪后再比较，不能由本宿主接口推定。

## 未验证事项

- 未运行 SQLite FTS5、CJK bigram/trigram、LIKE 回退和索引重建，故未验证不同语言查询的召回、排序、延迟和重建期间完整性。
- 未配置或调用任一外部 MemoryProvider，故未验证其数据模型、Embedding、候选数、重排、费用、写回时序、会话结束提取及数据驻留。
- 未发起真实模型工具调用，故未验证模型是否恰当地选择 `session_search`、记忆工具或多步滚动，也未验证预取上下文对回答质量的影响。
- 未运行内置记忆审批、文件漂移、跨 profile 读取、压缩谱系召回和进程中断路径；本文对一致性与隔离的描述仅限静态代码。
- 本次未审查所有 provider 插件、后台复习实现和桌面学习图的 UI 交互；“未找到固定多阶段编排”仅限文中列出的宿主入口与搜索范围。
