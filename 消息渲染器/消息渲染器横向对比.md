# 十七个消息渲染器横向对比

> 对比对象：AIO Hub、AstrBot、Chatbox、Cherry Studio、DeepChat、DeepSeek Harness、Hermes Agent、Jan、LobeHub、Manifold Desktop、NextChat、Open WebUI、OpenCode、Pi、Risuai、SillyTavern、VCPChat
>
> 对比更新日期：2026-08-18
>
> 依据：同目录十七份源码调查笔记及其记录的代码快照；AI 开发过程部分另含开发者群口述与用户提供的 Fable 5 模型说明
>
> 对比方法：统一比较产品定位、主要工作流、消息模型、流式更新、列表、Markdown、工具扩展、安全边界、测试与维护成本；未运行跨项目 benchmark
>
> 对比范围：产品定位、消息模型、流式更新、列表、Markdown、工具扩展、安全边界、测试与维护成本
>
> 文档定位：实现学习与跨项目横向比较，不作为整改方案

## 结论摘要

十七个项目并不是在实现同一种“Markdown 组件”，而是在解决多类不同问题：

1. **结构化聊天 UI**：Chatbox、Cherry Studio、LobeHub、Jan 先把正文、推理、工具、附件和状态建模，再由专用组件渲染。Markdown 只是 text part 的叶子节点。
2. **面向 LLM 输出的增量富文本引擎**：AIO Hub 将正文解析成业务 AST，流式期间用 stable/pending 区分已稳定与未稳定内容，并以 Patch 增量保留 Vue 子树；它最接近一个独立 renderer runtime。
3. **把消息当作可执行页面片段**：VCPChat 和 SillyTavern 以字符串转换和 DOM 后处理为主。VCPChat 进一步支持脚本、动画与 Three.js；SillyTavern 更重视角色卡 HTML/CSS、正则和扩展事件兼容。
4. **服务端 IM 机器人组件链**：AstrBot 先把 LLM 与插件结果归一化为 `MessageChain`（`BaseMessageComponent` 列表），再交给各平台适配器自行转换；没有统一的转换函数，WebChat 前端只是其中一条消费者。
5. **结构化块 + 标签解析**：DeepChat 以 `AssistantMessageBlock` 为事实源，`useArtifacts` 把 antThinking、antArtifact、tool_call 三种标签从正文解析为独立渲染路径。
6. **marked token 树 + 组件逐个渲染**：Open WebUI 不用 marked 的 HTML 字符串输出，而是让 Svelte 组件逐个消费 token，自制 details/KaTeX/引用/冒号围栏扩展。
7. **轻量字符串链**：NextChat 以 react-markdown 为核心、SSE 文本经 rAF 逐帧吐出；Manifold Desktop 最简，每 chunk 用 `marked.parse` 重解析累计全文，再以 innerHTML 整体替换整块 DOM，没有 sanitizer。
8. **宿主算意图、client 折快照的托管渲染**：DeepSeek Harness 没有传统“消息渲染器”组件——宿主按工具声明的呈现函数计算渲染意图，随会话事件流下发（`ToolEventView` 不落盘，回放由宿主重算）；client runtime 折叠快照后由 ui-conversation、ui-tool、ui-primitives 三组插件绘制。呈现意图是纯函数契约：presentCall/presentResult 无 I/O，结果期事实经 presentationMeta 随日志持久化、回放重算；流式是逐 chunk 折叠（PartialAccumulator 与 assistant Definition）→ animation-frame 帧合并 → MarkdownText 增量解析（只重解析尾部两块）；工具卡片分 generic/terminal/diff/search/read/web 六类；raw HTML 字面输出、链接仅 http(s)/mailto，用户消息字面渲染不解析 markdown；聊天列表无虚拟化。
9. **纯字符串管线的角色扮演前端**：Risuai 以消息 `data` 纯字符串为唯一事实源（role 仅 user/char），正文渲染是一条「变量解析 → 资产/inlay/Thoughts/工具标记 → editdisplay 正则脚本 → markdown-it+KaTeX+hljs → DOMPurify」的字符串管线，没有 part 或 AST 层；流式三档（off/balanced/strong）任何档位都是非增量重解析，strong 档在流式期间完全跳过脚本与 Markdown、直接显示原文，收尾再补跑脚本并整条重挂载。

Pi 属于终端类：**终端组件树渲染**。它以 ANSI 行为输出，`Markdown` 组件把 marked 令牌直接转成主题化终端行，没有 HTML/DOM、没有虚拟列表、没有 artifact 域；流式更新是“每 delta 用完整 partial 消息重建组件 + TUI 帧节流”。它的安全边界天然不同于 GUI 项目——终端渲染不产生 HTML，模型内容只能影响 ANSI 样式与文本布局。

Hermes Agent 与 OpenCode 属于服务端事件协议类：**事件网关 + 多渲染面**。Hermes 的 Python `tui_gateway` 把 agent 回调翻译成 `message.delta/interim/complete` 等事件，TUI（Ink）、Electron 桌面（Streamdown）与 web dashboard（xterm 嵌入真实 TUI）各自独立渲染；OpenCode 的服务端 part 事件协议同样被 Web（Solid session-ui 包）与 TUI（opentui）两端零共用代码地消费。

横向看，主要结论是：

- **在结构化消息、历史窗口化、流式尾部优化和工具组件四个维度上，Cherry Studio 和 LobeHub 的覆盖最完整。** Cherry 的输入到 DOM 性能链、普通 Markdown 净化和测试证据更完整；Lobe 的 conversation-flow、AssistantGroup 和工具注册表更适合复杂 Agent 工作流。
- **AIO Hub 和 VCPChat 都把流式优化推进到稳定前缀识别。** 两者不只限制更新频率，还只更新不稳定尾部。AIO 在 AST/组件树层做 diff 和 Patch；VCPChat 在 HTML/DOM 层用 stable blocks 界定稳定区，把不稳定尾部交给 morphdom 增量更新。前者结构更明确，后者更能保留任意 DOM 运行时状态。
- **AIO Hub 的产品方向比单看 AST 架构更接近 VCPChat 与 SillyTavern。** 它不仅解析 VCP 私有语法，还能直接扫描并导入 VCPChat Agent；对 ST 生态则已覆盖 JSON/PNG 角色卡、Context Preset、内嵌或独立世界书、正则脚本和快捷动作，世界书还有独立编辑器与实际上下文运行时。AIO 用 typed AST、专用组件和 iframe 重建这类体验，没有照搬 VCPChat 的主文档运行时或 SillyTavern 的 DOM 扩展契约。
- **AIO Hub 不缺少可执行消息，只是实现形态与 VCPChat 不同。** HTML/SVG 代码块可在 iframe 中运行 JavaScript、表单和 Canvas 小应用，Action Button 可发送消息、插入文本或复制内容。VCPChat 的主文档脚本、宿主 DOM 与运行时 SDK 生命周期治理更深；AIO 的能力边界是 iframe 内应用加预定义宿主动作。横向评价应写成“宿主运行时深度不同”，不能把 AIO 归为只有富文本预览。
- **AIO Hub 提供了覆盖面较广的人工验证设施。** 它内建桌面与移动 renderer 测试页；桌面页直接驱动生产组件，并覆盖真实 Token 流模拟、stable/pending 可视化、AST、样式逃逸、26 组预设、报告与截图。这些设施降低了开发期诊断与问题复现成本，但不能替代 CI oracle。
- **AIO Hub 已覆盖多类富消息与生态兼容能力，但工程收尾并不均匀。** 调查确认了无效的 `virtualListOverscan` 设置、桌面/移动渲染分叉、Pure/mobile 未净化的 `v-html`、高能力 same-origin artifact、未完成的 V3/renderer registry，以及集成、安全和性能自动回归缺口。开发者群口述称其主要依靠 Gemini 免费额度施工、少量 Opus/GPT 复核；现有材料不足以判断这种资源分配与具体问题之间是否存在因果关系。
- **Chatbox 的结构化方案路径较短、边界清楚。** part 模型、Virtuoso 和不执行原始 HTML 使主要职责容易定位，但当前每个 text delta 都会触发累计 Markdown 重解析，长回复的流式成本随正文增长。
- **SillyTavern 的兼容面较广，核心实现延续了传统页面脚本的组织方式。** 30 FPS 只限制更新频率，没有解决累计全文反复转换、净化和整体替换 DOM 带来的随长度增长的成本。
- **Risuai 把角色扮演的内容权限维持在样式与字符串协议层。** 消息内可注入经 `.chattext` 前缀作用域化的 CSS 与白名单 HTML（iframe 仅放行 YouTube embed），脚本只存在于插件沙箱 iframe；它把 SillyTavern 的字符串兼容面与脚本可执行面分开，是本次样本中“正文无脚本面”与“插件有脚本域”并存的代表。
- **AstrBot 是样本中渲染链分叉最多的形态。** 统一组件链在上游，出站/入站转换与长度策略（TG 4096、LINE 5000、aiocqhttp 缓冲或句号切分）全部下放平台适配器；业务语义（tool_call、reasoning、audio_chunk 三种类型值）通过 `MessageChain.type` 元协议只被 WebChat 两端消费，其他平台忽略。前端流式正文有 320 节点上限，complete 事件补缺失文本。
- **Jan 和 DeepChat 用结构化 parts/blocks 承接 AI SDK 与标签协议。** Jan 直接消费 AI SDK `UIMessage.parts`，用 fork 的 streamdown（rehypeKatex + harden，替换默认 rehype-raw/rehype-sanitize）渲染正文；DeepChat 以自研 assistant blocks 为事实源，`useArtifacts` 再从正文解析前述三种标签（兼容流式未闭合）。两者都把推理、工具与正文分开建模，不从 Markdown 反向猜语义。
- **Open WebUI 走“token 树组件渲染”，与字符串转换路线都不同。** marked lexer 出 token 后由 Svelte 组件逐个渲染，自制 details/KaTeX/引用/冒号围栏/提及扩展；流式用 rAF 节流 + 双缓存 + `TextToken` 复用，`content-visibility: auto` 做离屏虚拟化。它是本次样本中唯一把“解析”与“HTML 字符串生成”拆开的浏览器实现。
- **NextChat 与 Manifold Desktop 都在轻量端，但工程下限差距很大。** NextChat 用 react-markdown + SSE rAF 文本动画 + opaque-origin artifact，结构可预期；Manifold 每 chunk 用 marked.parse 重解析累计全文再以 innerHTML 整体替换、无 sanitizer、无节流、历史代码块 renderer 存在已复现的签名不匹配错误，是本次样本中 HTML 信任面最大、自动验证最少的 GUI 项目。
- **Hermes Agent 与 OpenCode 都把渲染能力拆到多面，但复用边界不同。** Hermes 的 TUI 自研 `markdown.tsx`（行级状态机）与桌面 Streamdown 是两套互不相干的实现，只共享网关事件；OpenCode 的 Web 端把渲染核心放进可复用 `session-ui` 包、TUI 完全独立，两端同样零共用渲染代码。两家的共同点是不给模型内容脚本执行面（Hermes 桌面仅有 3 处 SVG 片段 `dangerouslySetInnerHTML`，OpenCode 统一 DOMPurify）。
- **本次样本中，可执行富内容的权限越高，隔离通常越弱。** VCPChat 允许模型脚本在主页面运行；AIO 和 Cherry 的 artifact iframe 同时允许 scripts 与 same-origin；DeepChat 的 HTML artifact 也是 `allow-scripts allow-same-origin`，React artifact 仅 `allow-scripts`。Chatbox、Lobe、NextChat 与 Jan 的 artifact 默认不带 `allow-same-origin` 或启用严格 CSP，边界相对更清楚。OpenCode、Pi、Hermes TUI 没有可执行富内容面。
- **安全链路的两个极端都有可参照的实现。** 需求“尽量保留模型生成的 HTML 交互”看 DeepChat/NextChat 的 artifact iframe 与 Open WebUI 的 `injectCsp`+导航拦截；需求“正文默认不可信”看 OpenCode（DOMPurify + 无脚本面）、Open WebUI（DOMPurify + `sanitizeSvg`）、Jan（harden + 严格 artifact）与 Chatbox。Manifold 的裸 innerHTML 不能作为任何新项目的参照。
- **不能给十七者排一个脱离场景的总名次。** Agent 工作流、通用桌面聊天、IM 机器人、Web 服务、VCP 协议兼容、角色扮演内容、可执行 artifact 和终端编码 Agent 的目标不同，合理选择也不同。
- **消息渲染架构与产品承诺基本对应。** Chatbox 要让多模型聊天稳定可预期，Cherry 要让多种业务入口共用一套生产力 UI，LobeHub 要展示 Agent 的工作过程，AIO 要让高级用户精确控制 LLM 输出，SillyTavern 要承接社区内容与旧扩展，Risuai 要承接角色扮演、角色卡资产与正则脚本生态，VCPChat 则允许 Agent 直接生成界面，AstrBot 要把同一套组件链送进形态各异的 IM 平台，Open WebUI 要把多模型聊天托管给浏览器并内建代码执行，Jan/DeepChat 要承接 AI SDK 生态的结构化消息，Hermes/OpenCode 让同一服务端会话被多种客户端按各自技术栈消费，NextChat/Manifold 则是不同成熟度的轻量客户端。相应的消息模型、扩展点和脚本权限也各不相同。

## 从产品调性反推设计逻辑

这里的“产品调性”具体指产品反复承诺给用户的工作方式，而非配色或界面风格。判断时采用三层证据：

1. **公开定位**：README 把产品称作桌面客户端、Agent 工作空间、创作工作站还是运行引擎。
2. **主要对象**：用户主要在管理对话、结构化任务、角色内容，还是可执行的 AI 生成界面。
3. **代码取舍**：消息模型、渲染扩展点、兼容层和权限边界是否持续支持上述定位。

这仍是设计动机的推断，不是提交者访谈。只有公开定位与多处实现选择相互印证时，本文才给出较强判断；单个历史包袱不能直接解释成产品哲学。

### Chatbox：把模型能力收进稳定客户端

Chatbox 的公开定位仍以“多模型桌面客户端”和 local-first 为中心，README 强调本地数据、免部署安装、易用界面、快捷键与跨平台。对应到渲染链，正文、reasoning、工具、图片和错误先成为 `contentParts`，Markdown 只处理文本；原始 HTML 不直接执行，HTML 预览进入 opaque-origin iframe。

由此可以推断，Chatbox 优先降低的是**普通聊天的不确定性**。模型厂商可以增加新的流事件，但这些事件要先被翻译成客户端认识的 part，不能直接改写页面。其代价也与这种克制一致：分派树较固定，富内容自由度有限；当前流式正文逐 delta 重解析，说明工程资源更先投向产品边界和跨平台可用性，而非打造独立的增量排版引擎。

### Cherry Studio：用统一组件族承接不断扩大的产品面

Cherry Studio 同样从桌面客户端出发，但公开能力已经覆盖预设 Assistant、多模型并行会话、文档、知识管理、翻译、MCP 和 Agent。产品压力并非只让单条回复显示正确，还要让 Home、Agent 等入口共享操作习惯，同时允许各页面注入自己的删除、重试、审批和导出能力。

这能解释它为何比 Chatbox 多出 adapter、provider、layout projection、history/live overlay 和工具投影层。结构化 parts 保证能力可组合，adapter 保证共享 UI 不反向依赖页面类型，历史层与 live tail 分离则让功能密度增加后仍能控制更新范围。Cherry 的 renderer 因而更像**桌面 AI 套件的公共呈现层**。复杂度是产品面扩张的结果，但 HTML artifact 的宽权限也表明局部新能力曾越过原有安全分层，需要单独收紧。

### LobeHub：消息列表承担 Agent 工作流的可观测性

LobeHub 明确把 Agent 视为工作单元，并用团队、项目、日程、工作区和长期记忆组织产品。用户面对的不再只是问答序列，还包括一个 Agent 为完成任务产生的推理、搜索、工具调用、子任务和中间状态。

因此 `conversation-flow` 先把扁平数据库消息编译成 display message、虚拟消息和 `AssistantGroup`，随后才进入角色与工具 renderer。这个额外编译阶段承担的是**工作过程的组织与压缩**：相关步骤可以归组、折叠、恢复，也能由专用组件表达状态。Markdown 留在叶子层，正好对应“正文是工作结果的一部分，而非全部工作流”的产品结构。代价是 flow、局部 Store、工具状态机和 Markdown 各有状态，理解与调试门槛明显高于通用聊天客户端。

### AIO Hub：以结构化实现靠拢 VCPChat/ST 的体验面

AIO Hub 将自己定位为面向开发者和创作者的工作站，但聊天产品的演进方向已经不止于“可调试的 Markdown”。它在吸收 VCPChat 的 Agent、私有协议、工具、多媒体和交互式界面能力，同时承接 SillyTavern 用户常用的社区资产与上下文玩法。这个方向在源码中有完整链路，不只是 README 宣传：

- `agentImportService.ts` 解析 ST Character Card V2/V3，支持 JSON 与带元数据的 PNG 卡，并提取预设消息、正则和嵌入式世界书；
- `sillyTavernParser.ts` 解析 prompts、prompt_order 等 Context Preset 结构，`STPresetImportDialog.vue` 提供独立预设导入；
- `worldbookImportService.ts` 导入 JSON/`.lorebook`，也能从 ST 角色卡 PNG 或 AIO Bundle 中提取世界书；
- `vcpChatAgentImportService.ts` 可扫描 VCPChat 目录，把 Agent 配置、模型参数、正则和头像转换成 AIO 导入包。

因此 AIO 与 VCPChat 的接近首先发生在**用户能带入什么资产、Agent 能输出什么内容、聊天里能运行什么交互**这三个层面。V2 renderer 把 `think`、VCP 工具、角色、日记、交互按钮、HTML 和媒体纳入业务 AST，再用 stable/pending、节点身份与 Patch 管理流式变化；HTML 小应用则进入可执行 iframe。当前 VCP 展示解析会跳过 ESCAPE 围栏，并可在损坏块后从下一请求起点恢复，渲染层还有面向显示的模糊补全；工具执行解析沿用共享边界工具，但保持更严格的可执行块契约。AIO 没有照搬 VCPChat 在主文档中执行消息脚本的做法，而是用 parser、typed node、专用组件和独立预览域重新组织相近的体验目标。它也没有完整复刻 SillyTavern 的 DOM 与扩展事件契约，所以“能导入常用资产”不等于“兼容全部酒馆扩展”。

这种路线可以概括为**体验上向 VCPChat/ST 扩张，实现上尽量保持可观察和结构化**。内建测试台同时展示原文、AST 与稳定区，也延续了产品其他“分析器”式功能的调试取向。代价是 renderer 与 VCP、资产、正则和样式协议耦合较深；新增入口尚未在跨平台一致性、安全测试和自动回归上获得同等覆盖。

调查中记录的问题需要分级，不能全部笼统称为 bug：

| 类型 | 已确认现象 | 更准确的判断 |
|---|---|---|
| 明确失效 | `virtualListOverscan` 有默认值、类型和设置 UI，但消息列表没有读取 | 用户可见设置无效，属于已确认缺陷 |
| 未完成或历史残留 | V3 只有 disabled 占位；强行写入会落到 Pure；没有 renderer registry；Patch 调度仍留有未使用字段 | 设计尚未收尾或重构残留，不一定影响默认主路径 |
| 平台分叉 | 桌面 V2 与移动 `marked.lexer()` 是两套能力和安全模型 | 兼容成本会继续增长，部分功能无法跨端复现 |
| 安全风险 | Pure/mobile 直接 `v-html`；artifact 同时允许 scripts 与 same-origin；链接依赖上游 scheme 过滤 | 需要运行时验证与攻击语料，不能仅凭静态调查宣布可利用 |
| 验证缺口 | 自动测试集中在 Patch、个别 VCP parse 和 StreamSource，缺 stable/pending 集成、sanitizer、版本切换与性能阈值 | 人工测试台很强，但无法阻止所有回归进入主分支 |

开发者群的口述只能说明其开发资源分配方式：Gemini 开发者免费额度承担多数实现，Opus 用于少数质量和性能复核，GPT 参与部分逻辑审查。由于缺少提交级归因、调用日志和验收记录，本文不据此解释上述缺陷，也不推断模型预算与工程质量之间的因果关系。

### SillyTavern：兼容性本身就是功能

SillyTavern 的 README 只用一句“LLM Frontend for Power Users”定位产品，但源码中的角色卡 HTML/CSS、正则脚本、swipe、`display_text`、reasoning、媒体和全局渲染事件共同说明：用户不仅消费回复，也在制作、导入和改写内容。大量社区素材与扩展已经把字符串格式、DOM 结构和事件时点当成公共接口。

这使 String/DOM-first 方案带有现实合理性。统一 `messageFormatting()`、DOMPurify、innerHTML 和 rendered events 可以让旧内容继续工作，也允许扩展在核心提交 DOM 后追加行为。若直接改成封闭的 typed parts，迁移成本会落到角色卡作者和扩展维护者身上。相应代价是累计全文重渲染、主文档 CSS、关闭 CSP 和 DOM 级扩展耦合。这里不能简单把旧架构等同于疏于设计；更准确的判断是，项目长期把**生态兼容和作者自由**排在了严格封装之前。

### Risuai：字符串协议上的角色扮演前端

Risuai 与 SillyTavern 同属字符串与 DOM 后处理家族，但把渲染进一步收敛成一条字符串管线：正文、推理、工具、资产、交互按钮都以文本进入消息 `data`，按「变量解析 → 资产/inlay/Thoughts/工具标记 → 正则脚本 → markdown-it+KaTeX+hljs → DOMPurify」依次处理，没有 part 或 AST 层。内容权限被明确切成两段：消息内样式经 hex 编码后以 `.chattext` 前缀作用域化、消息壳 `guiHTML` 只接受白名单标签转译，脚本则整体被推到插件沙箱 iframe（无 same-origin + 独立 CSP），正文不存在可执行脚本面——比 SillyTavern 的“净化后允许受控 HTML/CSS”收得更紧。

流式三档（off/balanced/strong）都以合帧限制更新频率，但任何档位都非增量重解析；strong 档在流式期间完全跳过脚本与 Markdown、只显示原文，收尾再补跑脚本并以真实 data 哈希整条重挂载。列表是哈希差量窗口化（默认 30 条、滚顶追加 15 条），卸载彻底。这套取舍回答的是“角色扮演内容如何在纯字符串协议上保持可预期”，代价与 SillyTavern 一致：每次显示更新都重走整条管线，成本随单条回复线性增长。

### VCPChat：消息渲染器就是 AI 应用运行时

VCPChat 的公开定位直接要求打通 AI、UI 与 App，并把聊天前端描述为 VCP 后端的“眼睛”和“画板”。Agent 输出要能显示异步任务、多媒体、日记、群体协作，还能生成动画、Three.js 场景和桌面 Widget。此时消息的产品单位已经从“文档”扩展为“可持续运行的界面”。

主文档 HTML/CSS/JS、DOM 后处理、stable blocks、tail 处的 morphdom 增量更新、可见性激活和资源登记都服务于这一目标。稳定前缀不仅是性能优化，还要避免反复创建脚本产生的 DOM、动画和 WebGL 状态；长列表也不能默认卸载所有离屏消息，因为卸载可能终止仍有语义的运行时。VCPChat 因而选择**表达权限与状态连续性优先**，并接受更大的主页面信任面、生命周期复杂度和自动化验证成本。这不是通用聊天 renderer 的自然终点，而是其产品承诺推到实现层后的结果。

### AstrBot：渲染工作分散到每个目标平台

AstrBot 的公开形态是消息型机器人框架，核心承诺是“同一套 LLM 与插件逻辑接入多个 IM”。这使渲染问题被拆成两段：上游只要把结果归一化成 `MessageChain` 组件列表，下游由每个平台适配器自行决定如何呈现。业务语义（思考、工具调用、音频）靠 `MessageChain.type` 元协议传递，只有 WebChat 两端消费。

这套结构让“渲染器”没有一个统一实现：TG 把 4096 字符逐级切块并 markdownify，LINE 直接截断 5000，aiocqhttp 缓冲合并或按句号切句，WebChat 走 `[IMAGE]` 前缀字符串与结构化 parts 双通道。优点是平台差异被隔离在适配器内；代价是转换逻辑重复、同一链在不同平台呈现不对称，且前端流式正文只能靠 320 节点上限与 complete 补齐兜底，没有稳定前缀类优化。它的设计动机是**多平台可达性**，不是排版引擎或安全边界。

### Jan 与 DeepChat：承接 AI SDK / 块协议的结构化生态

Jan 的公开定位是本地优先桌面客户端，渲染侧直接消费 AI SDK `UIMessage.parts`，Markdown 只是 text part 的叶子。它替换了 streamdown 默认的 rehype-raw/rehype-sanitize，改用 rehypeKatex + harden，并把 HTML 工件默认放进不透明源严格沙箱。产品承诺“本地数据、富内容克制”，实现上表现为 parts 分派 + 插件级替换，而不是自建语法。

DeepChat 的定位更靠近“结构化工具会话”，`AssistantMessageBlock` 把 content、search、reasoning、plan、tool_call、action、image、audio 和 artifact-thinking 都作为一等类型；`useArtifacts` 再从正文里解析前述三种标签（兼容流式未闭合）。它介于“纯 parts”与“正文标签协议”之间：类型在传输层就结构化，但 artifact 与工具仍靠正文标签桥接，标签解析器的正则顺序因此成为隐式契约。

### Open WebUI：浏览器托管的长会话与代码执行

Open WebUI 的承诺是自托管的完整聊天服务：多用户、RAG、联网搜索、代码执行都在浏览器里呈现。渲染侧选择“marked lexer 出 token + Svelte 组件逐个渲染”，扩展全部自制（details、KaTeX、引用按钮、冒号围栏、提及）。这使它绕开了字符串渲染器“先拼 HTML 再净化”的两段式，HTML token 统一走 DOMPurify，Mermaid/vega 的 SVG 再走 `sanitizeSvg`。

流式优化是 rAF 节流 + 双缓存 + `TextToken` 复用，列表用原生 `content-visibility`。产品重心明显在“托管服务能力”（引用、结构化输出、代码执行双通道、Artifact）而不是排版引擎；对长回复、代码块、图表这些高频场景，它选择的是“复用 token、降低重渲染面积”，而不是 stable/pending 或尾部块。

### Hermes Agent：事件网关决定渲染面边界

Hermes 的公开定位是本地编码 Agent，TUI 是主渲染面，Electron 桌面与 web dashboard 是并列消费方。渲染差异被收敛到事件协议层：Python `tui_gateway` 只发 `message.delta/interim/complete` 等结构化事件，各前端自己决定怎么画。TUI 因而可以自研行级 Markdown（无第三方依赖），桌面可以用成熟 Streamdown + Shiki + KaTeX，Web 甚至直接嵌入真实 TUI 的 PTY。

它证明了“事件协议稳定时，渲染栈可以按端自由演进”与 OpenCode 相同的结论；差别在于 OpenCode 的 Web 端把渲染核心包进 `session-ui` 供复用，Hermes 的三面则完全没有共用渲染代码，共享的只有网关契约与状态语义（如分段、去重、finalTail）。

### DeepSeek Harness：宿主算渲染意图、client 折叠快照的托管渲染

DeepSeek Harness 不是聊天应用，仓库里没有传统意义上的“消息渲染器”组件；它是基于 vendored Cordis 的 agent harness，Web UI 只是 client 渲染面。渲染职责被拆成两段：宿主按工具声明的呈现函数计算渲染意图，随会话事件流下发且不落盘；client runtime 把事件折叠成快照，再由 ui-conversation、ui-tool、ui-primitives 三组插件绘制。呈现函数必须是无 I/O 的纯函数，回放时宿主重算；结果期结构化事实随 presentationMeta 持久化，实时与历史共用同一套契约。正文自建 mdast→React 管线，raw HTML 字面输出、链接仅放行 http(s)/mailto，无脚本执行面；流式是逐 chunk 折叠、RAF 帧合并、只重解析尾部两块。代价是 UI 展示数据不进会话日志，聊天列表没有虚拟化。

### NextChat 与 Manifold Desktop：轻量客户端的两种成熟度

NextChat 的定位是轻量可自托管 Web 客户端，渲染链保持最小可预期：react-markdown + SSE rAF 逐帧吐字 + 分页窗口 + opaque artifact。它没有自己的流式排版引擎，但安全边界（不启用 rehype-raw、artifact 无 same-origin）清楚，属于“把生态库用稳”的路线。

Manifold Desktop 的承诺更弱：聊天 + 工具 + 终端三个页签的桌面助手。渲染只有两条正文路径，流式路径每 chunk 全文重解析再以 innerHTML 整体替换，无 sanitizer；历史路径的代码 renderer 还有已复现的签名错误。它不是“刻意简洁”的取舍，而是渲染侧没有形成可维护契约——这类项目适合作为反面参照：**只要存在模型输入到 DOM 的直通路径，至少需要一个显式清洗点和一个统一的流式收口。**

### 两条比“架构流派”更有解释力的轴

十七个项目不适合排成一条从简单到高级的直线。用下面两条轴观察，设计选择更容易预测：

1. **消息的产品单位**：模型回答 → 结构化工作过程 → 用户创作内容 → 可执行应用。
2. **内容拥有的 UI 权限**：只能填充文本 → 选择宿主组件 → 注入样式与扩展行为 → 直接运行脚本并持有状态。

Chatbox、Jan、Open WebUI 位于“回答 + 低权限”一端；Cherry 和 LobeHub 把产品单位提升为结构化工作过程，但仍由宿主组件掌权；DeepChat 在结构化过程一端但保留正文标签桥接；SillyTavern 通过兼容层向作者开放样式和 DOM 扩展；Risuai 同处字符串生态，把样式开放给作者、把脚本整体推入插件沙箱；VCPChat 位于“应用 + 高权限”一端。AIO 横跨中间数档：普通业务节点由宿主 AST 组件掌权，导入能力承接 ST/VCPChat 资产，可执行 artifact 又把内容权限推近网页应用。AstrBot 的分发对象是 IM 平台，内容权限由平台决定，产品单位仍停留在“回答 + 附件”。OpenCode 位于“回答 + 低权限”一端但走双栈：Web 端把模型内容约束在 DOMPurify 清洗后的静态 HTML 与注册表组件内，TUI 端把输出约束为 ANSI 行；Hermes 同理，TUI 无 HTML sink，桌面仅 3 处 SVG 片段使用 `dangerouslySetInnerHTML`。Manifold 在第二条轴上意外地高（无清洗直通 innerHTML），但这是缺失工程边界的结果，不是产品决策。沿第二条轴向右移动时，流式算法会从文本刷新转向节点身份和运行时保活，列表策略会从直接窗口化转向冻结/恢复，安全问题也会从 XSS 净化升级为应用权限治理。

这一视角还能解释技术相似但动机不同的情况：AIO 与 VCPChat 都识别稳定前缀，前者主要为了保持 AST/组件渲染稳定，后者还必须保存脚本和 DOM 运行状态；Chatbox 与 SillyTavern 都以字符串正文作为重要输入，前者尽快把业务语义分离成 parts，后者则保留字符串和 DOM 契约以兼容社区内容；Hermes 与 OpenCode 都采用事件协议 + 多渲染面，前者三面零共用渲染代码，后者至少把 Web 渲染核心包成可复用包。

## 架构分型

### 1. Parts-first：Chatbox、Cherry Studio、Jan、DeepChat

这些项目从传输阶段就保留 text、reasoning、tool、image、error 等类型。渲染器不需要从 Markdown 中重新猜测业务语义。

```text
stream chunk
  -> typed parts
  -> message layout / timeline
  -> part renderer
  -> Markdown only for text
```

共同收益：

- 工具审批、错误、图片和 reasoning 有稳定的数据契约。
- 业务内容不会因为 Markdown 容错或正则顺序而被误解析。
- 新增能力可以独立测试状态转换与叶子组件。

差异在于，Chatbox 的实现更直接，主要分派仍集中在 `Message` 和 `ToolCallPartUI`；Cherry 多了一层 layout projection、history/live overlay、页面 adapter 和工具投影缓存，规模更大但高频更新边界更清楚；Jan 直接消费 AI SDK 的 UIMessage.parts，把 Markdown 替换成自己的 streamdown fork（rehypeKatex + harden），工具/推理/引用都从 part 分派；DeepChat 用自研 AssistantMessageBlock 建模 content/reasoning/tool_call/action/image/error，是 parts-first 的本地变体——但它的 artifact 与工具仍通过三种正文标签桥接，`useArtifacts` 的正则顺序构成隐式契约，这一点又接近 String/DOM-first 的解析方式。

### 2. Flow-first：LobeHub

LobeHub 不直接渲染数据库消息，而是先由 `conversation-flow` 重建树、虚拟消息和 `AssistantGroup`。这一步相当于消息 UI 前的编译器：

```text
flat DB messages
  -> semantic conversation flow
  -> display messages / assistant groups
  -> role and workflow renderers
```

这层 flow 专门表达“模型回答”和“模型为回答执行的过程”之间的关系。代价是每次 dispatch 都要重新 parse，再依赖结构共享恢复引用；全局 ChatStore、会话局部 Store、Markdown 和工具 workflow 也各有状态机。

### 3. AST-first：AIO Hub

AIO Hub 的业务协议深入正文 AST：`think`、VCP 工具、角色、日记、交互按钮、HTML、媒体和样式都是节点类型。它的关键边界不是 part，而是 parser 与 AST node：

```text
string / StreamSource
  -> tokenizer + parser
  -> stable AST + pending AST
  -> diff / Patch
  -> typed Vue node components
```

收益是同一棵树可统一处理流式节点身份、复杂嵌套和专用 UI；代价是 renderer 与 VCP、Agent 资产、样式系统和 llm-chat 强耦合。当前扩展仍需修改固定 union、parser、组件映射和版本枚举，没有运行时 registry。

### 4. String/DOM-first：SillyTavern、VCPChat、Risuai

两者都保留字符串兼容性，以有序转换、Markdown 转 HTML 和 DOM 后处理叠加能力。

SillyTavern 的主线较简单：

```text
message string
  -> macro / regex / repair
  -> Showdown
  -> DOMPurify
  -> innerHTML
  -> reasoning / media / highlight / extension events
```

VCPChat 的层次更深：保护映射和转换顺序构成隐式 grammar，Marked 只生成基础 HTML，后续还要处理 KaTeX、Mermaid、工具块、CSS、脚本、动画和资源生命周期。它比 SillyTavern 更复杂，也更接近一个宿主页面运行时。

Risuai 的主线同样是字符串转换：变量/CBS 解析 → 资产/inlay/Thoughts/工具标记 → 正则脚本 → markdown-it + KaTeX + hljs → DOMPurify。消息内样式经 hex 编码后以 `.chattext` 前缀作用域化、消息壳 `guiHTML` 由白名单标签转译，脚本整体进入插件沙箱 iframe，正文没有脚本执行面；流式以 125ms+rAF 合帧限制频率，但每帧仍对累计全文全量重解析。

### 5. 组件链 + 平台自治转换：AstrBot

AstrBot 的渲染事实源是 `MessageChain`（BaseMessageComponent 列表），但转换不集中：每个平台适配器自行实现出站/入站。

```text
LLM 结果 / 插件 CommandResult
  -> MessageEventResult（MessageChain 子类）
  -> ResultDecorateStage（reasoning 注入 / TTS / t2i / 转发 / @/Reply 前缀）
  -> RespondStage（校验 -> 分段/直通/防重 -> send / send_streaming）
  -> 平台 AstrMessageEvent.send / send_streaming（平台重写）
       aiocqhttp: OneBot JSON / telegram: 4096 切块+markdownify / webchat: 组件序列化
  -> WebChat 前端：parts 流 -> messageBlocks() -> markstream-vue 渲染
```

它没有“前端”，只有多个平台的出口；`MessageChain.type` 元协议（tool_call、reasoning、audio_chunk 三种类型值）只被 WebChat 两端消费。这套分型的本质是**渲染职责的分布式下放**：平台差异被隔离在适配器内，代价是转换逻辑重复、同一链在不同平台呈现不对称，且没有任何平台获得稳定前缀类流式优化。

### 6. Token 树组件渲染：Open WebUI

Open WebUI 与字符串转换路线不同：marked lexer 出 token 树后，由 Svelte 组件逐个渲染，而不是让 marked 拼 HTML 字符串。

```text
content（流式累加）
  -> processResponseContent / replaceTokens（占位符仅代码块外替换）
  -> marked.lexer -> MarkdownTokens.svelte 逐 token 渲染
       CodeBlock / details / HTMLToken / KatexRenderer / SourceToken / colonFence
  -> rAF 节流合并解析 + TextToken 复用
```

自制扩展（details 深度配对、KaTeX、引用 `[n]`、冒号围栏、提及、脚注）都发生在 token 层；HTML token 统一先 DOMPurify，Mermaid/vega 的 SVG 再 `sanitizeSvg`。收益是每个 token 类型有独立组件与清洗点，流式期间可以按 token 复用；代价是扩展点绑定到 marked 的 token 结构，模型正文里出现的裸 HTML 形态依赖约定的占位符协议。

### 7. 轻量字符串链：NextChat、Manifold Desktop

两者都以“字符串正文 + 外部 Markdown 库”为主干，但工程成熟度相差很大。

NextChat 的链是“SSE 拼接 -> rAF 逐帧吐字 -> react-markdown -> 组件覆盖”，推理输出被转成 Markdown 引用文本，没有独立数据结构：

```text
SSE delta -> parseSSE -> remainText
  -> requestAnimationFrame(animateResponseText)  每帧 max(1, remain/60) 字符
  -> ChatStore.onUpdate -> Markdown(streaming ? loading : done)
```

Manifold 的链是“chunk 累计 -> marked.parse(全文) -> innerHTML 整体替换”：

```text
CHAT_CHUNK -> streamingText += chunk.text
  -> marked.parse(streamingText) -> streamingEl.innerHTML = ...
```

两者都未做稳定前缀或尾部块；NextChat 靠 rAF 限制**更新频率**（仍每次全量解析当前文本），Manifold 连节流都没有，且历史路径与流式路径的 Markdown 配置不一致、没有 sanitizer。这一分型在样本中代表“最低工程投入的可用路线”。

### 8. 终端组件树：Pi

Pi 是十七个项目中唯一的纯终端渲染器，主线是“事件 → 组件树 → ANSI 行”：

```text
AgentSessionEvent (message_start/update/end, tool_execution_*, bash_execution_update)
  -> 组件分派 (user/assistant/tool/bash/custom/compaction/branchSummary)
  -> Markdown: marked lexer + 自定义 tokenizer (LaTeX/strikethrough)
       -> 主题函数着色 -> ANSI 感知换行 -> 边距/背景填充
  -> TUI requestRender 帧节流 -> 整屏输出
```

它与浏览器类分型没有可比的安全模型：没有 HTML sink、没有脚本执行面；模型内容经 ANSI 转义输出到终端，隔离边界主要落在终端模拟器本身。流式优化只有两层：`Markdown` 组件按 `text+width` 缓存，TUI 按帧合并——既没有稳定前缀也没有尾部块切分。

### 9. 事件协议 + 多渲染面：OpenCode、Hermes Agent

两者的共同点是：消息渲染不绑定单一前端，服务端（或网关进程）负责事件协议，各客户端按自己的技术栈独立渲染。

OpenCode 的 Web 端是 parts-first 的变体，但渲染核心被拆成独立包 `packages/session-ui` 被 `packages/app` 复用；TUI 是完全独立的第二栈：

```text
服务端 part 事件（message.updated / message.part.updated / message.part.delta）
  -> SSE 读取循环（16ms 批量 flush + delta 拼接）
  -> Solid store 投影（part_text_accum_delta 累积）
  -> Web：虚拟化 timeline -> PART_MAPPING 分派
       -> TextPartDisplay -> PacedMarkdown（24ms 步进）
       -> markdown-stream 切块 -> Worker 内 marked+shiki 解析 -> DOMPurify
       -> morphdom / 增量 token span 命令式写 DOM
  -> TUI：opentui <markdown>/<code>（tree-sitter 高亮，streaming 模式）
```

Hermes 的形态相同但更分散：Python `tui_gateway` 通过 stdio/WS JSON-RPC 发 message.delta/interim/complete、reasoning.delta、tool.* 等事件，三个消费方全部独立实现渲染——TUI 自研行级 markdown.tsx，桌面用 `@assistant-ui/react-streamdown` + Shiki + KaTeX，web dashboard 干脆通过 PTY 嵌入真实 TUI：

```text
agent 回调 -> tui_gateway（token 合批 30fps）-> JSON-RPC 事件流
  -> TUI：turnController（先缓冲后分段 + 16/80/96ms 节流）-> turnStore -> Md / StreamingMd
  -> 桌面：use-message-stream -> StreamdownTextPrimitive -> Shiki / KaTeX
  -> web：xterm 嵌入 hermes --tui 的 PTY
```

与其余项目的区别：两端共享数据契约与事件协议，但渲染代码零共用（OpenCode 的 Web 是 Solid + Worker、TUI 是 opentui；Hermes 的 TUI 与桌面完全各自实现）；OpenCode 的流式期间「壳层响应式渲染 + 正文命令式 DOM 补丁」并存、markdown 解析整体搬到 Web Worker；Hermes 则在网关侧做 token 合批与 inflight 累积，前端只管缓冲、分段和定稿去重。两家的共同约束是：**事件协议必须携带足够的收口信息（completed/finalText/status），否则各渲染面无法保证最终一致。**

## 流式渲染对比

流式性能应拆成三个问题：**多久更新一次、每次重算多少内容、是否保留已渲染节点状态**。只做 30 FPS 节流仅解决第一个问题。

| 项目 | 更新调度 | 每次主要重算范围 | 节点状态保留 | 长回复增长特征 |
|---|---|---|---|---|
| AIO Hub | rAF 平滑 + Patch 约 80ms 节流 | pending 尾部重解析，整树 diff 后局部 Patch | 通过稳定 node ID 和引用复用保留 | 较好，但 parser/Patch 本身复杂 |
| AstrBot | 平台流式直通；前端 markstream-vue 平滑流式 + 320 节点上限 | 前端按 think/tool_call/content 切块，MarkdownRender 流式解析 | 未确认（节点上限触发截断策略） | 服务端缓冲平台可能峰值=全文；前端受节点上限约束 |
| Chatbox | 每个可见 delta 更新 React Query cache | 当前累计 text part 重新走 LaTeX、ReactMarkdown、HAST | React key/memo 可保留外围，正文树会重算 | 成本随正文增长，缺 UI 合帧 |
| Cherry Studio | IPC/overlay 按帧提交 + jitter buffer | live tail；Streamdown 处理不完整 Markdown | 历史冻结、settled part 引用恢复；结束不换组件类型 | 当前证据中最完整的端到端控制 |
| DeepChat | MarkdownRenderer 流式小 batch + 短 delay + parse coalesce | 当前 content 的流式 Markdown 子树；未闭合标签跨帧保留 | artifact store 按 snapshot 同步/完成，避免重建 | 与 markstream-vue 版本行为绑定，未实测长回复 |
| DeepSeek Harness | 流式 chunk 请求 animation-frame 发布、同帧合并（markFrameDirty）；收口与 tool/result 走 microtask | MarkdownText 增量解析只重解析末尾两块；收口以完整 content 全量重解析（数学/高亮落地） | 折叠块不可变、冻结块缓存为 React 元素、块以源码偏移作稳定 key | 增量解析把全文二次增长降为尾部小区域；聊天列表节点数仍随会话线性增长 |
| Hermes Agent | 网关 token 合批 30fps；TUI 16/80/96ms 分场景节流 | TUI 仅重解析 in-flight tail（StreamingMd）；桌面 Streamdown tail | TUI 已定稿块只 tokenize 一次；`finalTail` 去重保顺序 | 流式状态有 16000 字符/240 行上限；定稿后一次性落 transcript |
| Jan | AI SDK useChat throttle 50ms + `useDeferredValue` 合并 token | 流式代码块不跑 Shiki，正文仍走 streamdown 流式解析 | memo 比较器忽略无关字段；插件引用 hoist 防破坏 memo | 流式期间按 token 合并重解析，随单条回复增长 |
| LobeHub | 自适应平滑输出 | Marked block 切分后只重渲染变化尾块 | block cache、keepMounted | 较好，基础 flow parse 仍会全量重建 |
| Manifold Desktop | 无节流，每 chunk 立即重渲染 | 累计全文 marked.parse + innerHTML 整体替换 | 正文内部状态必然丢失 | 最明显的随长度增长（且无 sanitizer） |
| NextChat | SSE -> rAF 每帧 `max(1, remain/60)` 字符 | 当前消息全文 react-markdown 重解析 | 仅靠 streaming 键切换 loading 态 | 频率受 rAF 限制，但每次仍全量解析当前文本 |
| Open WebUI | rAF 节流合并一次解析；done 立即处理并取消残留帧 | 仅 text token 经 TextToken 增量复用，块级 token 重新渲染 | `{#key id}` + TextToken 复用；结构化 clone 快照防抖动 | 解析频率被 rAF 合并，token 复用降低 DOM 重建 |
| OpenCode | SSE 事件 16ms 批量 flush；文本 24ms 步进节流 | markdown 切块投影只更新尾部 block；code 块按 stable/unstable token 增量追加/裁剪 | morphdom 保留非 code DOM 状态；`renderedCodeTokens` WeakMap 按 key 缓存 | 文本分块增量与 Worker 并发（每 key supersede），随单条回复增长成本较低 |
| Pi | 事件驱动 `requestRender`，帧节流合并 | 当前 assistant 消息整体重建（组件级），Markdown 按 text+width 缓存命中 | 组件对象在流式期间复用，内容容器清空重建 | 每次 delta 全量重解析当前消息，随单条回复增长 |
| Risuai | off 逐 chunk；balanced 125ms 定时器 + rAF 合帧（串行、丢中间帧）；strong 流式期间跳过脚本与 Markdown 显示原文 | 每次合帧对累计全文重走字符串管线（含正则脚本、KaTeX、高亮、清洗）；strong 不解析 | 流式哈希排除 data 保住已挂载实例、只调实例方法；收尾真实 data 哈希整条重挂载 | 每帧全量重解析，成本随单条回复线性增长；三档区别仅在合帧频率与是否跑脚本 |
| SillyTavern | 默认 30 FPS | 累计全文 regex + Showdown + DOMPurify + innerHTML | 正文内部状态容易丢失 | 最明显的随长度增长 |
| VCPChat | 全局 rAF，约 30 FPS | 新 stable block 处理一次，tail 重新生成并 morphdom | preserve hook + stable DOM + 运行时资源登记 | 对复杂 DOM 最有针对性 |

从十七个实现中可以提炼出以下复用判断：

1. **先合帧，再缩小重算范围。** Cherry 解决从 IPC 到 overlay 的提交频率，AIO/Lobe/VCPChat 进一步缩小到 pending AST 或尾部 block。
2. **稳定区比纯节流更重要。** 消息变长后，累计全文解析即使只有 30 FPS 也会越来越贵。
3. **最终帧不应无故更换组件类型。** Cherry 让曾流式的 block 在结束后继续使用同一组件；AIO 保留 node ID；两者都在保护 selection、focus 和局部状态。
4. **若流中使用简化语义，结束时必须有权威重放。** VCPChat 明确把流式 DOM 视作临时投影，最终用完整原文重新解释。
5. **数据持久化不应跟随 token 频率。** AIO、Chatbox、Cherry 都把高频显示与低频持久化或历史层分开。

## 安全边界

以下比较的是默认信任模型，不等同于完成渗透测试后的风险评级。桌面端还必须结合 BrowserWindow/WebView 配置、preload 暴露面和 IPC sender 校验判断最终影响。

### 普通消息正文

- **Chatbox**：ReactMarkdown 不启用 raw HTML，URL 经 `sanitize-url`，工具结果按文本显示。普通正文边界最克制。
- **Cherry Studio**：允许扩展 HTML/SVG，但有明确 rehype sanitize 白名单、ID 前缀和安全测试；普通 Markdown 防护证据最完整。
- **LobeHub**：使用 `rehype-raw` 与组件管线，调查笔记确认 artifact 隔离较好，但没有像 Cherry 一样完整盘点 sanitizer 测试，不能仅凭本次材料给出同等级结论。
- **AIO Hub**：V2 对 inline/block/generic HTML 分别净化或过滤，但 Pure 与移动端存在直接 `v-html` 路径，版本间边界不一致。
- **SillyTavern**：正文经 DOMPurify，但 style 在净化后恢复进主文档，CSS scope 只是防御性重写；CSP 关闭。
- **Risuai**：正文统一经 DOMPurify 清洗（class 加 `x-risu-` 前缀、iframe 仅放行 YouTube embed、href 仅 http(s)，blob: src 保留供 inlay）；消息内 `<style>` 经 hex 编码躲过首轮清洗后用 `.chattext` 前缀做 CSS 作用域再二次清洗；主文档未启用 CSP；脚本只能在插件沙箱 iframe 中运行，插件域带独立 CSP。
- **VCPChat**：assistant HTML、CSS 与脚本可进入主页面，属于有意提供的高信任运行时，不应按普通不可信 Markdown 看待。
- **OpenCode（Web）**：marked 允许 raw HTML 解析，随后统一经 DOMPurify 清洗（`USE_PROFILES:{html,mathMl}`、FORBID_TAGS/FORBID_CONTENTS 含 style/script、ADD_TAGS svg/path 供 KaTeX）；链接协议过滤依赖 DOMPurify 默认 URI 白名单（静态推断，未运行验证）；无 iframe/artifact，模型内容没有任何脚本执行面。TUI 侧无 HTML sink，模型内容只能影响 ANSI 样式与文本布局。
- **Open WebUI**：正文 `<`/`>` 先实体化，HTML token 一律 `DOMPurify.sanitize`（默认配置）再渲染；Mermaid/vega 输出 SVG 再走 sanitizeSvg 白名单清洗（允许 style/foreignObject 等）；通用 iframe 分支取清洗前 src 且空 sandbox；`ui.iframe_csp` 默认空字符串即不注入 CSP。安全测试与攻击语料未见记录。
- **Jan**：正文由 streamdown fork 的 harden 插件消毒，仓库源码未见 DOMPurify；`LINK_SAFETY = { enabled: false }` 被显式关闭，其影响范围未确认；链接改为锚到引用区（#cite-/#webcite-）而非直接跳转。
- **DeepChat**：普通正文走 markstream-vue 安全 HTML policy；SVG artifact 不直接渲染，交 main process `sanitizeSvgContent`；Mermaid 渲染前移除 script/iframe/object/embed/form/link/style/meta/img 与 on* 属性、协议过滤，并初始化 `securityLevel: 'strict'`。HTML artifact 允许脚本，sandbox 与 Electron webPreferences/CSP 的组合未运行验证。
- **Hermes Agent**：TUI 纯终端字形渲染、无 HTML 节点，链接经 `openExternalUrl` 协议白名单；桌面正文经 Streamdown 渲染，仅 3 处 SVG 片段使用 dangerouslySetInnerHTML（svg-embed、mermaid-embed、preview-artifact），SVG 是否白名单化未读到实现；web 版 Markdown 仅允许 http(s|mailto)。
- **AstrBot**：平台端没有 HTML sink（消息组件序列化为文本/文件）；WebChat 前端 markstream-vue 自带安全 HTML policy，工具参数/结果经 `Json` 组件与 ToolCallCard 展示；`[IMAGE]` 等前缀字符串与正文存在解析歧义（未实测）。
- **NextChat**：未启用 `rehype-raw`，普通 HTML 不进入 React DOM；媒体扩展名链接渲染为 `<audio>/<video controls>`；未发现统一的 `rel="noopener noreferrer"` 注入。
- **Manifold Desktop**：assistant Markdown 无 sanitizer，marked 保留的原始 HTML 直接写 innerHTML；页面无 CSP，WebView2 显式启用脚本与 WebMessage，链接无导航白名单。属于本次样本中正文信任面最大的 GUI 项目。
- **DeepSeek Harness**：raw HTML 以字面文本输出，不进入 DOM；链接目的地经归一化后仅放行 http(s) 与 mailto，未命中渲染为纯文本；图片仅接受绝对 http(s) 地址并带 no-referrer；唯一 `dangerouslySetInnerHTML` 是 shiki 生成的静态 span 树；KaTeX 输出经 DOMParser 映射且词汇表限定 span/MathML/SVG；无 artifact/iframe，模型内容没有任何脚本执行面。用户消息经 MessageText 字面渲染，不解析 markdown。

### HTML artifact

| 项目 | sandbox 关键项 | parent DOM 隔离判断 |
|---|---|---|
| Chatbox | 模型 HTML：`allow-scripts allow-forms` | 无 `allow-same-origin`，保持 opaque origin；相对更强 |
| LobeHub | `allow-scripts allow-forms allow-modals` | 无 `allow-same-origin`；相对更强 |
| Jan | 默认不透明源 + 严格 CSP + sandbox；`allowNetwork`/`allowScripts` 需非流式且设置开启 | 默认路径最强；放宽路径由设置控制 |
| NextChat | `srcDoc` + `allow-forms allow-modals allow-scripts` | 无 `allow-same-origin`；高度经 postMessage 回传，父端未校验 origin/source |
| Open WebUI | srcdoc + `allow-scripts allow-downloads`（可选 allow-forms/allow-same-origin）+ `injectCsp`（默认空）+ iframe 内导航拦截 | 默认无 same-origin、无 CSP；配置项可放宽，需按部署判断 |
| DeepChat | HTML artifact：`allow-scripts allow-same-origin`；React artifact：仅 `allow-scripts` | HTML 分支可访问父窗口；SVG/Mermaid 走清洗路径 |
| Cherry Studio | `allow-scripts allow-same-origin allow-forms` | 可访问父窗口；结合完整 preload 暴露为 P0 |
| AIO Hub | `allow-scripts allow-same-origin allow-forms ...` | parent DOM 未隔离；Tauri capability 影响需运行时验证 |
| VCPChat | iframe 可执行；正文脚本本身已在主页面 | iframe 不是整体安全边界 |
| SillyTavern | 没有同类独立 artifact 主路径 | 主要风险在主文档 CSS，而非 artifact iframe |
| Risuai | 正文无 artifact 面；插件域沙箱 iframe 仅 `allow-scripts allow-modals allow-downloads`（无 same-origin）+ 独立 CSP | 插件沙箱保持 opaque origin、postMessage 桥通信；不参与消息正文渲染路径 |
| DeepSeek Harness | 不适用（运行时不承载 HTML/iframe/Artifact） | 无 artifact 面；raw HTML 保持字面文本，模型内容无脚本执行面 |

安全方面最明确的工程结论是：

1. 不可信 `srcdoc` 不应同时获得 `allow-scripts` 和 `allow-same-origin`。
2. CSS selector scope、Shadow DOM、timer 包装和资源回收都不是权限沙箱。
3. artifact 最好运行在无 full preload 的独立低权限页面，并默认以 CSP 禁网。
4. 主窗口一旦设置 `webSecurity: false` 或暴露宽泛 IPC，任何 renderer XSS 的后果都会显著放大。
5. 普通 Markdown、artifact、工具结果和导出 HTML 是四个不同 sink，必须分别建立安全契约与测试。

## 工具与扩展能力

### 工具 UI

- **LobeHub** 的工具注册表最成熟：`identifier + apiName` 可分别提供 inspector、streaming renderer、custom renderer 和 fallback，消息层只处理生命周期与布局。
- **Cherry Studio** 也有 Agent tool registry、builtin/MCP chooser 和统一状态投影，且明确覆盖 streaming、approval、done、error、cancelled。当前压力点是 `MessagePartsRenderer` 已很大。
- **Chatbox** 有清晰 typed part 和通用 fallback，但专用 renderer 仍是固定条件分派，继续扩展适合引入 registry。
- **AIO Hub** 同时存在 role=tool 和正文 VCP AST 两条路径，兼容力强但语义分散。
- **DeepChat** 的 tool_call 是 block 一等类型：参数、响应、图片预览、diff 与 MCP App view 各有组件，按 block status 切换 calling/response/end/error 图标；`exec`/`process`/subagent 等工具运行中自动展开属于显示规则。
- **Jan** 以 `tool-<name>` parts 分派：ChainOfThoughtGroup 折叠推理与工具调用，ToolCallCard/RagToolWidget/WebToolWidget 分类型展示，引用经 grounding 句子级校验后聚合。
- **Open WebUI** 把工具调用、reasoning、code_interpreter 归组为 detail token（`detail_group`），由 `StructuredOutputRenderer` 与正文混排；代码执行另有 CodeExecutions 徽章与模态框。
- **AstrBot** 用 `type=tool_call` 链 + 单个 `Json` 组件表达工具调用与结果，前端 upsertToolCall 维护卡片；工具执行中的缓存图片以独立链 yield。
- **Hermes Agent** 的 TUI 用 ToolTrail 按组渲染工具（braille spinner + 耗时 + verbose args 上限 800 字符），SubagentAccordion 树状展示 spawn tree，另有 TodoPanel；desktop 有 tool-group 与 run-ticker。
- **SillyTavern** 的工具信息在结构化旁路字段中，扩展主要依赖全局事件与直接 DOM 操作。
- **Risuai** 的工具调用在请求层序列化为 `<tool_call>` 文本，展示层替换为一行只读提示（无工具卡、审批或展开交互）；参数与结果都在上下文侧处理，不进入消息正文。
- **VCPChat** 擅长兼容文本中的 VCP 工具协议，但转换顺序本身成为 grammar，新规则必须理解保护占位与后处理时机。
- **NextChat** 的工具没有独立消息树节点，只是 assistant bubble 上方按 success/error/loading 渲染的状态区。
- **Manifold Desktop** 的工具调用/结果用独立折叠块，名称 esc、参数与结果 textContent；位置固定，无注册表。
- **Pi** 的工具是事件驱动节点：`ToolExecutionComponent` 按工具定义选择 `renderCall/renderResult` 或内置/文本兜底，流式参数与部分结果逐步刷新；工具渲染器通过注册表获得，没有消息正文里的私有标记解析。
- **OpenCode** 的工具 UI 是注册表形态：`ToolRegistry.register/render` 已注册 14 个工具渲染器（read/glob/grep/shell/edit/write/task 等），未注册走 `GenericTool`；连续上下文工具（read/glob/grep/list）合并为 context 组折叠；shell 输出 stripAnsi 后用 `<pre><code>`，edit/write/patch 用虚拟化 diff 视图；工具调用与模型部分仍是同一 part 状态机驱动（pending/running/completed/error）。
- **DeepSeek Harness** 以呈现意图词汇驱动：工具声明 `presentCall`/`presentResult`（纯函数）产出 ToolCallView/ToolResultView，client 按 card 判别分派为 generic/terminal/diff/search/read/web 六类卡片并派生渲染 props，未知取值降级 generic；keyed 槽位 `tool.call.toolview` 按工具名注册专属卡片（ui-cordis 即此路），未注册回退 `GenericToolCard`。

### 通用扩展

SillyTavern 的 rendered event 对第三方扩展最开放，代价是核心提交 DOM 后结果仍可能被任意修改，静态推理和测试更难。LobeHub/Cherry 的 registry 与 Provider action 边界更适合大型 TypeScript 项目。AIO 的 typed AST 适合内建协议扩展，但当前没有运行时插件接口。VCPChat 的运行时能力最大，却也要求扩展作者同时理解文本 pipeline、DOM 后处理和资源清理。Open WebUI 的扩展点绑定 marked token 结构与自制扩展模块（`utils/marked/*.ts`）；Hermes 的扩展点分面（TUI `domain/roles` + messageLine，桌面 embeds 注册表）；AstrBot 的扩展点是 `ComponentType` 枚举与平台适配器，新增组件类型需要同时动枚举、注册表和适配器；DeepChat 的扩展点是 block 类型与 useArtifacts 标签解析；Jan 通过替换 streamdown 插件集与组件覆盖扩展；NextChat/Manifold 没有独立扩展机制，靠组件覆盖与固定 JS 文件。Risuai 的扩展点是字符串协议的各阶段：`registerCBS` 注册变量/函数、改资产正则与清洗白名单、在正文标记解析处加正则，脚本层另有正则脚本四模式与 Lua 触发器、壳层靠 `guiHTML` 白名单转译。DeepSeek Harness 的扩展面是注册式三件套：新消息节点注册 `ConversationNodeDefinition`（match/start/update/buildViewNode）并挂 keyed `conversation.chat.node` 渲染器，新工具卡片走 `tool.call.toolview` 槽位，新投影在 `SessionProjectionMap` 上声明合并；折叠按日志 seq 确定，可确定性重放。

## AI 开发门槛估算

这里的“成本”指**需要携带什么等级的编码 AI，以及大致什么订阅档位才适合持续完成该类实现**，不是传统团队人月。套餐只代表可用额度、并发和组织能力，模型等级决定单次任务上限；两者不能混为一谈。

估算采用以下前提：

- AI 可以读写完整仓库、运行测试、启动应用、操作浏览器并检查截图，不是只在网页对话框中生成代码片段。
- 有一个人负责产品边界、验收和高风险决策，但可以不是每天手写代码的主力工程师。
- 可以使用成熟 Markdown、虚拟列表、sanitizer、代码高亮和 DOM diff 库；AI 不从零重写通用基础库。
- “做出主路径”指常规消息、流式正文、工具块和长列表可用；“追平当前能力”还包括异常输入、最终化竞态、平台接入、兼容行为、安全测试和性能回归。

### AI 等级参照

| 等级或角色 | 当前模型参照 | 适合承担的工作 | 不宜单独承担的工作 |
|---|---|---|---|
| 高吞吐执行模型 | GPT-5.6 Terra；具备代码 Agent 能力的 Gemini 档位 | 搜索仓库、补叶子组件、写单测、机械重构、修明确 bug、大量尝试 | 自主决定跨层架构、解析器语义和安全边界 |
| 前沿编码模型 | Claude Opus 5；GPT-5.6 Sol High/XHigh | 跨文件实现、状态机、虚拟列表、流式链路、工具 UI、疑难调试与审查 | 在缺少规格和语料时独自承诺历史兼容或安全完备 |
| 长任务 Agent 模型 | Claude Fable 5；GPT-5.6 Sol Max/Ultra 配子 Agent | parser/runtime 设计、大仓库迁移、连续多阶段实现、竞态排查和长任务闭环 | 代替真实用户兼容测试、渗透测试和最终产品责任人 |
| 视觉与体验审查模型 | 具备较强视觉理解的 Gemini 档位 | 截图比较、布局与配色审查、发现视觉不一致、提出交互修改 | 独自判断数据契约、并发正确性和权限边界 |

这里的等级不是一条简单的总分排行。Terra 或 Gemini 一类高吞吐模型适合搜索、批量修改和明确模块；Opus/Sol 一类前沿编码模型适合疑难实现与质量审查；[Fable 5 的公开定位](https://www.anthropic.com/news/claude-fable-5-mythos-5)则直接面向 long-running agents，更适合持续操作仓库、反复验证并跨阶段收尾。最高档也不必全程使用：让便宜或免费额度承担大量实现，再用强模型审查架构、性能和逻辑，往往比从头到尾只用一个最高价模型更接近真实开发过程。

| 项目 | 口述中的模型组合 | 推测的分工 | 对成本判断的修正 |
|---|---|---|---|
| VCPChat | 大量使用 Claude Opus 与 Fable 开发，同时用 Gemini 做美学把关 | Fable 承担长时间 Agent 任务和连续实现；Opus 处理复杂编码、重构与疑难问题；Gemini 从截图和界面结果做视觉审查 | 它确实需要前沿/长任务模型，但不等于一个模型全程 Max；实际成本来自两个高端开发模型的高用量，再加独立视觉审查 |

“Gemini 开发者免费额度组成号池”只用于描述已知开发过程。账号池是否符合当时及当前供应商条款未在本调查中核实，不应作为新项目的采购或规避限额建议。可复制的部分是**高吞吐主力 + 稀缺强模型审查 + 异构模型复核**，而不是具体的账号组织方式。

按当前官方说明，Plus 是“每周少量专注编码会话”的定位；Pro 提供约 5 倍或 20 倍于 Plus 的 Codex 用量。Business 更适合多人工作区和数据治理，但若团队要高频跑大型 Agent，仍需 credits 或 API，不能只看每席位价格。具体额度会调整，购买前应以 [Codex pricing](https://learn.chatgpt.com/docs/pricing) 为准。

这张套餐表只是 Codex 等价参照，不表示十七个项目实际使用了 OpenAI 套餐。按口述过程复现 VCPChat，更接近“可大量使用 Opus/Fable 的 Claude 高档订阅或 API + 一个有视觉能力的 Gemini 渠道”；复现 AIO，则更接近“高额度或低成本 Gemini 主力 + 少量 Opus + 少量 GPT/Codex 审查”。后者的现金支出可能很低，但会付出账号管理、限额波动、任务切换和多模型上下文交接成本。

Fast mode 只提高速度并更快消耗额度，不提高推理上限；Codex-Spark 也更适合低延迟的小步编辑，不应作为 AIO/VCPChat 这类架构工作的主模型。降低额度消耗的一种可控做法是把任务切成可验证层次：Terra 做检索、测试和机械实现，Sol 做设计、整合、疑难调试和最终审查。

### 对两套组合方案的判断

本文推荐的均衡组合需要至少一个 **Opus/Sol XHigh 级模型负责架构和审查**，主力施工可以使用 Gemini/Terra 类高吞吐模型。单一 Plus 可以慢慢做原型，但若目标是连续推进到可上线状态，应准备一个稳定的高用量渠道，或采用 AIO 式“低成本主力 + 少量强模型复核”；同时必须让浏览器回归、安全攻击语料和性能阈值成为机器可执行的反馈。缺少这些反馈时，即使使用最高档模型，也无法稳定判断行为是否正确。

“极致自由型”可执行消息运行时属于 **Fable 长任务 Agent + Opus 复杂编码与审查** 的典型任务；Codex 等价方案是 Sol Max/Ultra + 子 Agent，再配浏览器与性能工具。这里 AI 可以完成绝大部分实现和测试基础设施，但不能单独签署“脚本隔离可靠”或“兼容全部 VCP 内容”的结论。若没有人工定义权限表、整理真实兼容语料并审查跨域/IPC 边界，购买最高套餐也不会消除核心风险。

## 按目标选择

### 新建通用 AI 桌面聊天

优先参考 **Cherry Studio 的总体分层**，并采用 **Chatbox/LobeHub 的 opaque-origin artifact sandbox**。原因是结构化 parts、history/live 分离、虚拟列表和专用工具组件能覆盖大多数产品需求，同时不必把业务协议塞回 Markdown。

不建议原样复制 Cherry 的 artifact 配置，也不必一开始复制其全部 adapter 和缓存层。可以先建立 typed parts、单一 MessageList contract、流式 overlay 和安全 artifact 进程，再按性能数据增加结构共享。

### 构建复杂 Agent 工作流

优先参考 **LobeHub**：conversation-flow、AssistantGroup 和工具注册表能表达任务、审批、多工具与中间过程。若数据源已经是 AI SDK `UIMessage.parts`，也可以使用 Cherry 的 part layout projection，再借鉴 Lobe 的 group/compiler 层。

### 构建高性能流式 Markdown 引擎

优先研究 **AIO Hub、LobeHub、VCPChat**：

- 需要类型化组件树和可预测 Patch：选 AIO 的 stable/pending AST 思路。
- 已使用 React Markdown/unified，希望控制实现规模：选 Lobe 的 block tail 思路。
- 必须保留任意复杂 DOM、媒体和动画状态：研究 VCPChat 的 stable DOM 与 morphdom 增量更新，但不要继承其主页面脚本信任模型。

### 兼容 VCP 文本协议与可执行富消息

VCPChat 的协议兼容和运行时最完整，AIO Hub 则提供更结构化的 AST 方向。长期演进可采用“两段式”方案：先将 VCP 文本协议编译为 typed IR/AST，再由静态组件或隔离 runtime 分别消费，避免继续让字符串转换顺序同时承担 grammar 与安全边界。

### 兼容角色卡、正则脚本与社区扩展

SillyTavern 的事件模型、统一 formatter 和角色卡 HTML/CSS 兼容最有参考价值。新实现应保留这些产品契约，但把 formatter、净化、CSS 解析、DOM 装配和生成生命周期拆成独立可测模块；流式更新应升级为尾部 block 或 AST 增量，而不是继续重画累计全文。若同时要求脚本权限不进正文，可参考 Risuai 的切分：消息内只保留作用域 CSS 与白名单 HTML，脚本整体放在无 same-origin 的插件沙箱 iframe。

### 接入多个 IM 平台

AstrBot 的“统一 `MessageChain` + 平台自治转换”是唯一完整样本。若目标是把同一套 LLM 结果送进 QQ/Telegram/LINE/Discord 等平台，可以借鉴它的组件枚举、装饰阶段集中重写（reasoning/TTS/t2i/转发）与长度限制下放，但应给“统一转换函数”留出集中收口（AstrBot 是每适配器自实现），并让 WebChat 一类富端与文本端共享同一套业务语义标记，避免两套表示长期并存。

### 自托管多模型 Web 服务

Open WebUI 是主要参照：token 树组件渲染 + 自制 marked 扩展 + DOMPurify/sanitizeSvg 清洗点 + `content-visibility` 离屏跳过 + artifact/Pyodide 双沙箱。NextChat 可作为轻量替代参照：react-markdown 链 + 分页窗口 + opaque artifact，工程更小但富内容与代码执行能力弱。若同时要求多用户与代码执行，Open WebUI 的多租户配置、引用渲染与执行后端分离更值得保留。

## 推荐的组合架构

如果目标是新建一套同时兼顾**渲染能力、交互上限、流式性能、安全边界和可维护性**的桌面端方案，可以组合十七个项目中已经验证过的不同做法：

| 层次 | 建议采用的做法 | 主要来源 | 组合理由 |
|---|---|---|---|
| 事实模型 | typed message parts，正文、reasoning、工具、附件、错误、审批分别建模 | Cherry Studio / Chatbox | 避免从 Markdown 反向猜测业务状态，支持独立演进和测试 |
| 工作流投影 | `conversation-flow` + `AssistantGroup` 式语义编译层，仅在 Agent 会话启用 | LobeHub | 能表达多轮工具调用、审批和中间过程，又不让普通聊天承担额外复杂度 |
| 流式调度 | transport 与 UI overlay 分离，rAF 合帧、抖动缓冲、低频持久化 | Cherry Studio | 覆盖从网络/IPC 到界面的完整高频更新边界 |
| 正文内核 | tokenizer/parser -> stable/pending AST -> keyed Patch | AIO Hub V2 | 对非完整 Markdown、复杂嵌套和节点状态保留最有针对性 |
| 工具交互 | `identifier + apiName` 注册表，并统一 streaming/approval/done/error/cancelled 状态 | LobeHub + Cherry Studio | 同时获得可插拔 renderer 和完整工具生命周期 |
| 长会话 | 真正窗口化，流式尾消息独立；重型节点按可见性暂停/恢复 | Cherry/Lobe + VCPChat 的资源生命周期思路 | 限制常驻组件数量，同时照顾媒体、动画和编辑器状态 |
| 富内容 | CodeMirror、KaTeX、Mermaid、媒体等作为懒加载 typed node | AIO Hub | 能力完整，中间状态可观察，不依赖正文 DOM 后处理 |
| 可执行 Artifact | VCPChat 级 HTML/CSS/JS/Canvas/Three.js 能力，运行在 Chatbox/Lobe 式强隔离环境 | VCPChat + Chatbox/LobeHub | 保留交互上限，但不继承在宿主主文档执行模型脚本的信任边界 |
| 验证体系 | AIO 式人工测试台 + Cherry 式自动回归 | AIO Hub + Cherry Studio | 人工探索、问题复现和 CI 确定性判定互补 |

目标链路可以具体化为：

```text
transport chunks
  -> normalized typed events
  -> canonical message parts / tool state machine
  -> live overlay (rAF batched + jitter buffer)
  -> optional conversation-flow compiler (Agent mode only)
  -> virtualized message list with isolated live tail
  -> part registry
       -> text: stable/pending AST + keyed Patch
       -> reasoning / tool / media: typed components
       -> artifact: separate low-privilege executable runtime
  -> typed action bus / capability bridge
  -> final authoritative snapshot
  -> persistence handoff
```

### 关键交互设计

宿主页面内的交互应由 typed component 发出结构化 action，例如复制、重试、批准工具、打开附件、运行代码和更新 Artifact；消息内容不能直接操作会话 store 或宿主 DOM。工具 renderer 从注册表获得所需 action 和最小上下文，不获取完整应用能力。

可执行 Artifact 则采用另一条路径：允许 HTML/CSS/JS、Canvas、动画和 Three.js，但放入独立低权限页面或进程，使用 opaque origin、无宿主 preload、默认禁网的 CSP，并通过白名单 `postMessage`/IPC capability bridge 请求保存文件、打开链接等宿主操作。需要持久化的交互状态由 Artifact 显式序列化，不能依赖其 DOM 永久常驻。

普通正文不要同时混用 AST Patch 和 morphdom 两种更新手段。前者负责 Markdown 与 typed 富节点；后者若有必要，只应留在隔离 Artifact 内部以保留任意 DOM 运行时状态。最终帧由完整原始内容重新解析并与流式结果校验，但沿用稳定 node ID，避免完成瞬间重挂载导致选区、焦点和展开状态丢失。

桌面和移动端应共享 parser、typed IR、sanitizer 契约和预设语料，只更换叶子组件与列表 adapter。AIO 当前桌面 V2 与移动 `marked.lexer()` 分叉的做法不应带入目标架构。

### 验证闭环

以 AIO 的 26 组预设和流速/延迟/抖动控制为人工测试入口，再为每组预设补充确定性的 AST、最终 DOM 和关键截图基线。自动化还应覆盖流式/最终一致性、节点 ID 稳定性、工具状态转换、虚拟列表滚动锚定、sanitizer 攻击样例、Artifact capability 拒绝路径，以及长回复和长会话的帧耗时、内存与节点数阈值。

应明确保留的约束：

1. 原始消息或结构化 parts 是事实源，DOM 不是。
2. 流式显示、持久化和历史查询使用不同更新频率。
3. 工具、reasoning、附件和错误不通过 Markdown 私有标记表达。
4. 文本 renderer 只重算不稳定尾部，并在最终化时保证权威一致性。
5. 列表默认窗口化；只有确实持有运行时副作用的消息才采用显式暂停/恢复策略。
6. 普通 Markdown、工具结果、artifact 和导出 HTML 使用独立 sanitizer/权限策略。
7. 不可信脚本只能进入无宿主 preload、默认禁网、不可访问 parent 的环境。
8. parser/flow/part projection 的中间结果必须可快照测试，流式与最终输出必须有一致性用例。

这套组合划分为两个运行域：**宿主域负责结构化消息、可信组件和工具工作流；Artifact 域负责不可信但高交互的可执行内容。** VCPChat 的主文档运行时允许更宽的页面执行能力；若同时要求权限隔离、可维护性和长会话稳定性，上述双运行域组合更符合这些约束。

## 极致自由型组合

如果目标更接近 VCPChat，即优先保证 LLM 能自由生成 HTML、CSS、JavaScript、Canvas、动画、音视频、WebGL/Three.js 和持续交互，并愿意接受脚本执行、联网与持久状态带来的更大信任面，那么目标不应再叫“Markdown renderer”，而应定义为 **Executable Message Runtime（可执行消息运行时）**。

VCPChat 当前复杂度并不主要来自安全措施，而是多种语言共享同一字符串：VCP 标记、工具载荷、代码围栏、LaTeX、Markdown、HTML 和脚本需要依次保护、转换、恢复，再经过 DOM 后处理。放宽安全限制不会消除这些语法冲突。真正能简化链路的做法是把可执行内容提升为一等 part，使语言边界在进入 renderer 前就确定。

### 推荐模型

```text
stream events
  -> forgiving top-level segmenter
  -> MessagePart IR
       -> prose: Markdown / AIO-style stable AST
       -> tool: structured tool renderer
       -> app: executable document source
       -> media: native media component
  -> keyed message composition

app source
  -> dedicated browser realm
  -> native HTML/CSS/JS module execution
  -> runtime SDK + shared event/state bus
  -> inline resize / host action bridge
```

`MessagePart IR` 只规定顶层内容岛，例如 prose、tool、app、media，不尝试把 JavaScript 或任意 HTML 再翻译成大量业务 AST 节点。旧 VCP 文本协议可以保留一个兼容 adapter，但只负责一次性编译到 IR；后续渲染、流式和交互均不再扫描原始协议标记。工具调用和结果也直接进入结构化 part，不再穿越 Markdown 占位符。

app part 应直接描述一个可运行文档包，例如 HTML、CSS、JavaScript module、资源与初始状态。HTML 使用浏览器解析器，CSS 可使用 PostCSS/CSSOM，JavaScript 原样交给独立 realm 执行；不要继续用正则改写 selector、脚本和嵌套 HTML。KaTeX、Mermaid、Three.js 等能力作为 runtime SDK 或标准 module import 提供，而不是宿主在 innerHTML 之后逐项扫描并增强。

### 运行域选择

为了接近 VCPChat 的能力而显著降低生命周期代码，建议每个活动 `app` 使用独立 iframe/WebView realm。它可以允许脚本、模块、网络、存储、WebSocket、Canvas、音视频和 WebGL，并获得透明背景、主题变量、自动高度和输入焦点，因此视觉上仍是消息正文的一部分。卸载整个 realm 就能统一清理 timer、事件监听器、Worker、AudioContext 和 WebGL，避免 VCPChat 为每类资源分别登记和回收。

这里可以有三个信任档位：

| 档位 | 能力 | 代价 |
|---|---|---|
| `prose` | Markdown、typed nodes，不执行脚本 | 普通消息默认路径 |
| `active` | 脚本、联网、存储、模块、WebGL；不能直接调用宿主原生 API | 已接近网页小应用，允许内容追踪和外部请求 |
| `trusted` | 在 `active` 基础上开放宽能力 bridge，可读会话上下文、发消息、调用工具、保存文件和驱动画布 | 接近 VCPChat 自由度；恶意或错误脚本可执行高影响用户操作 |

如果产品明确选择极致模式，可以让指定 Agent 或会话默认进入 `trusted`，而不必每个动作弹审批。仍建议保留最后一条硬边界：模型脚本不直接取得 Electron/Tauri 的完整 preload、任意文件系统和密钥对象，而是经版本化 runtime SDK 调用。这个 bridge 即使很宽，也比让脚本依赖宿主 DOM、全局变量和内部 IPC 名称更容易维护。

若确实要求模型脚本修改整个聊天页面，可再提供显式的 `host-integrated` 开发模式，让脚本进入主文档。它最接近 VCPChat，但会重新引入全局 CSS、DOM 归属、脚本清理、虚拟列表冲突和聊天切换竞态；这部分复杂度不是换一个 parser 就能消除。因此它更适合作为调试/插件模式，而不应是可执行消息的唯一实现。

### 流式与交互

流式阶段只识别顶层 part 边界。`prose` 使用 stable/pending AST；`app` 在开始标记未闭合时显示源码或轻量占位，文档边界稳定后再启动 realm。若必须边生成边运行，则只向同一个 realm 发送源码 revision，由 realm 内部使用 keyed DOM diff/HMR 更新，不让宿主对脚本产生的 DOM 做后处理。结束时以完整原文重新生成 IR，并校验 part 身份，但不无故销毁仍匹配的 realm。

跨消息交互通过共享 event/state bus 完成：应用可以订阅会话事件、发布 UI 状态、请求工具、向后续消息传递结构化数据。宿主只管理 part 身份、可见性、尺寸、权限和持久化，不理解应用内部 DOM。长会话窗口化时，普通消息直接卸载；活动应用采用最近使用池、冻结快照或 `serializeState()/restoreState()`，而不是让全部可执行 DOM 永久常驻。

### 这套组合实际取自哪里

- 采用 **VCPChat** 的能力目标、稳定前缀、运行时 SDK、可见性激活和跨消息交互思路。
- 采用 **AIO Hub** 的容错 tokenizer、stable/pending、节点身份和人工测试台，但仅用于 prose 与顶层 part，不把任意应用翻译成封闭 AST。
- 采用 **Cherry Studio** 的 typed parts、流式 overlay、合帧和持久化分流。
- 采用 **LobeHub** 的工具注册表和 Agent 工作流投影。
- 采用 **Open WebUI/Jan/NextChat/DeepChat** 的 artifact 沙箱经验：`injectCsp` + iframe 内导航拦截（Open WebUI）、默认不透明源 + 严格 CSP（Jan）、无 same-origin（NextChat）、SVG/Mermaid 前置清洗与 `securityLevel: strict`（DeepChat）。
- 与前一套均衡方案不同，`active/trusted` runtime 主动允许脚本、联网、存储和丰富浏览器 API；它牺牲的是内容安全和资源可预测性，换取接近完整网页应用的 LLM 自由度。

这一路线**保留 VCPChat“消息可以是一段程序”的产品能力，同时取消“所有能力必须穿过一条 Markdown 字符串流水线”的实现约束。**

## 最终判断

如果问题是“哪套最值得作为新项目底座”，答案是 **Cherry/Lobe 的结构化消息架构**，再补上 Chatbox/Lobe/Jan 的 artifact 隔离方式；如果问题是“哪套流式正文技术最值得研究”，答案是 **AIO 的 AST Patch 与 VCPChat 的稳定 DOM 尾区**，中量级场景可看 Lobe 的尾部 block、Open WebUI 的 token 复用与 Hermes TUI 的 in-tail 增量；如果问题是“哪套最能承载模型生成的小应用”，答案是 **VCPChat**，但它同时拥有最大的信任面和验证成本；如果问题是“哪套原生承接社区角色卡与传统扩展契约”，答案仍是 **SillyTavern**；若在承接角色卡与正则脚本生态的同时要求脚本权限不进入正文，Risuai 提供了收得更紧的参照——样式与白名单 HTML 保留、脚本全部落入插件沙箱 iframe；如果希望直接导入 ST/VCPChat 常用资产，再用更结构化的消息与 AST 继续演进，**AIO 是最明确的跨生态汇合点**，但当前完成度和安全边界并不均匀。**Pi 是唯一的纯终端渲染样本**：它以 ANSI 行为边界，把 HTML/脚本安全问题整体排除在消息渲染之外，但也不拥有 GUI 项目的富内容、窗口化与 artifact 能力；对“终端里的编码 Agent”这一目标，其组件树 + 帧节流方案与产品形态匹配。**Hermes 与 OpenCode 提供了“同一会话协议、多渲染面独立演进”的答案**：Hermes 的 TUI/桌面/Web 三面只共享网关事件，OpenCode 的 Web 端以 Solid + Worker + 虚拟化 timeline 提供完整 GUI 能力、TUI 端以 opentui 组件树消费同一事件契约，两端都不给模型内容脚本执行面；对“多前端共用一个服务端 Agent 会话”的目标，两者都证明渲染栈可以按端独立演进，前提是事件协议带齐收口信息。

十七个项目共同说明，架构设计前需要先确定**消息在产品里是一段回答、一项工作过程、一份可编辑内容、一个可运行应用，还是一条要送进多个 IM 平台的消息链**，随后再划定三条工程边界：业务语义是否结构化、流式时什么内容已经稳定、模型内容拥有多少页面权限。产品单位和这三条边界确定后，renderer、列表与安全架构才有一致的取舍依据；Markdown 库只是后续选择。Pi 的终端形态提供了这些边界之外的另一种答案：输出只到 ANSI 行，业务语义在组件树里结构化，HTML/脚本问题在渲染层整体不存在。Hermes/OpenCode 的双（多）栈形态则说明：只要事件契约稳定，不同渲染器可以在零共用代码的前提下各自演进，渲染栈的选择不绑定消息协议。Manifold 作为下限样本说明另一件事：没有显式清洗点与流式收口的字符串直通链，是十七个实现中唯一不应被复制的一档。
