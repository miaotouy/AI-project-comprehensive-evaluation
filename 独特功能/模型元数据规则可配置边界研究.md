# 模型元数据规则可配置边界研究

> 对比对象：AIO Hub、AstrBot、Chatbox、Cherry Studio、DeepChat、DeepSeek Harness、Jan、LobeHub、Open WebUI、OpenCode、Pi、SillyTavern
>
> 对比更新日期：2026-08-18
>
> 依据：LLM 渠道管理单项目调查笔记、当前代码快照中的模型目录/能力配置入口，以及 AIO Hub 模型元数据编辑器实现
>
> 对比方法：把“元数据来源”“单模型覆盖”“可匹配规则系统”分开，检查配置对象、管理入口、持久化、运行时消费者和是否改变请求行为
>
> 对比范围：模型身份、能力、上下文/价格、模态、Tokenizer、媒体参数及其可配置规则；不把会话消息 metadata、文件 metadata 或 Agent 角色 metadata 纳入本研究
>
> 文档定位：实现学习与跨项目横向比较，不作为整改方案

## 结论摘要

“模型元数据规则可配置”目前更适合归入 **LLM 渠道管理的模型目录与能力元数据扩展**，不应单独计入独特功能，也暂不足以建立新的横向分类。原因是它的事实对象仍是“某条渠道提供的某个模型”，主要用途是让模型可被正确发现、展示、筛选和调用；它没有脱离渠道管理而成立的独立用户目标。

AIO Hub 是本次样本中唯一确认形成完整规则工作台的项目：用户可以维护一组按 Provider、模型 ID 或模型片段匹配的规则，设置优先级、正则、启停和独占关系，编辑能力/上下文/价格/Tokenizer/媒体参数，并在设置页测试命中、查看覆盖分析、导入导出和合并内置预设。规则不仅改变列表展示，还进入模型导入、请求参数过滤、Adapter/操作类型选择、Token 计算和媒体生成参数面板。因此它是 LLM 渠道管理中的**稀有扩展能力**，而不是普通 Provider 表单字段。

其余项目大多落在两个较窄的层级：

- **目录富化**：内置 Model Bank、models.dev 或 Provider `/models` 返回模型后，由代码或远端数据补充能力、上下文和价格；用户不能定义匹配规则。
- **单模型覆盖**：用户可以编辑一个 Provider/模型实例的能力、上下文或请求参数，或者在配置文件中用模型 ID 做覆盖；这是渠道的子级配置，不是全局规则编辑器。

只有当至少三个项目都具备独立的规则对象、可达编辑入口、匹配/合并语义、持久化和运行时影响时，才值得把它提升为“模型元数据规则”单独分类。当前证据不满足这个条件。

## 1. 分类口径

### 1.1 三层能力

| 层级 | 事实对象 | 典型实现 | 用户是否定义匹配逻辑 | 建议归类 |
|---|---|---|---|---|
| 目录事实/富化 | Provider 返回或内置目录中的模型条目 | `/models`、models.dev、Model Bank、静态模型表 | 否 | LLM 渠道管理基础能力 |
| 单模型覆盖 | `provider + model` 的一条模型实例配置 | 修改 vision、reasoning、context、endpoint 或自定义参数 | 通常只能选定单个模型 | LLM 渠道管理的模型子配置 |
| 规则系统 | 独立规则集合及其匹配、优先级、合并结果 | Provider/精确 ID/片段/正则匹配，规则链深合并 | 是 | LLM 渠道管理的扩展能力；当前不单列新类别 |

“独立设置页”不是单列类别的充分条件。判断重点是规则是否围绕模型目录运行，是否影响请求主链，以及是否有跨项目的稳定同构对象。

### 1.2 与独特功能的边界

独特功能类目要求能力在去除普通 Chat、Agent 和 Provider 底座后仍保留独立产品语义。模型元数据规则通常服务于以下渠道工作流：

```text
发现/手工添加模型
  -> 补全模型事实和能力
  -> 在 UI 筛选或选择模型
  -> 请求入口按能力和协议构造请求
```

这条链的起点和终点都属于 LLM 渠道管理。它可以是稀有的工程机制贡献，但不能仅因规则编辑器跨越多个消费者，就改写为新的用户产品工作流。

## 2. AIO Hub：完整规则工作台

### 2.1 规则对象和编辑入口

AIO 的 `ModelMetadataRule` 将匹配条件与属性覆盖放在同一持久化对象中。匹配类型包含 Provider、精确模型和模型片段；规则还带有优先级、启用状态、正则开关、独占标记和描述。属性范围不止图标和分组，还包括能力、上下文长度、价格、描述、Tokenizer、模型特性及媒体生成参数，类型定义允许继续扩展字段（`aio-hub/src/types/model-metadata.ts:15-20,25-98,324-377`）。

设置页是独立的模型元数据入口，提供添加/编辑/删除/启停、预设查看、覆盖分析、导入导出、合并新内置规则和重置默认等操作；测试模式可输入模型 ID 与 Provider 查看命中结果（`aio-hub/src/views/Settings/model-metadata/ModelMetadataSettings.vue:17-45,64-117`）。规则编辑器还直接呈现匹配类型、优先级、正则、能力开关和媒体参数约束（`aio-hub/src/views/Settings/model-metadata/components/ModelMetadataConfigEditor.vue:17-98,127-157`）。

Store 将规则保存到 `metadata-rules.json`，从旧版 localStorage 迁移，并支持保留用户同 ID 规则、增量合并新内置规则、规则级增删改和启停（`aio-hub/src/stores/modelMetadataStore.ts:37-50,75-119,176-297`）。这已经是可迁移、可备份的配置实体，而不是编译期常量。

### 2.2 匹配、合并和覆盖语义

规则先按优先级排序，再筛选命中项；命中独占规则后丢弃更低优先级规则，最后按低到高的顺序深合并属性。模型片段的非正则模式是对完整模型 ID 做不区分大小写的包含匹配，正则错误会记录日志并跳过（`aio-hub/src/config/model-metadata.ts:46-109,112-169`）。

覆盖分析会把每条规则贡献拆成“最终生效字段”和“被高优先级规则覆盖字段”，并将结果展开到渠道下的模型实例（`aio-hub/src/views/Settings/model-metadata/utils/coverageAnalysis.ts:23-39,84-109,139-180`）。这使规则链的解释和调试成为用户可见能力，也是它区别于简单模型编辑表单的证据。

### 2.3 运行时消费者

AIO 的规则参与至少四类运行时路径：

1. 模型列表导入时，先合并活动规则能力，再用 API 明确返回的能力覆盖；远端没有返回的能力不会被错误写成 `false`（`aio-hub/src/llm-apis/model-fetcher.ts:100-149`）。
2. 模型快照上的能力决定工具、思考等级、视觉和媒体参数是否进入请求；模型绑定还参与 Chat、Embedding、Rerank 或媒体 Adapter 的选择。
3. 规则中的模型家族和部分属性仍会被请求构造、Token Calculator 和媒体生成器读取；因此规则不只是列表图标配置。
4. 渠道模型编辑器可以对单模型的媒体参数做更高优先级覆盖，和全局规则形成“全局默认 + 模型实例覆盖”的两层结构。

现有 LLM 渠道笔记已确认：大部分规则结果会在模型创建、导入、刷新或批量应用时写入模型对象，但部分模型家族、Tokenizer 和工具判断仍读取当前活动规则。因此 AIO 当前更准确地描述为“模型快照为主、少量运行时规则读取并存”，而不是完全的导入时快照。

## 3. 横向样本

| 项目 | 用户可配置形态 | 规则匹配/合并 | 运行时影响 | 判断 |
|---|---|---|---|---|
| AIO Hub | 独立全局规则编辑器；另有单模型覆盖 | Provider/模型/片段/正则，优先级、独占、深合并、覆盖分析 | 能力门控、Adapter/操作选择、参数清洁、Tokenizer、媒体 UI | 完整规则系统，稀有扩展 |
| LobeHub | Model Bank + `ai_models` 用户差量；模型项可编辑 | 无通用用户规则；能力/价格通常按模型实例整体覆盖 | 工具、多模态、搜索、推理参数、上下文和费用展示 | 单模型覆盖 + 目录富化 |
| Jan | Provider 详情中的模型元数据/参数可编辑 | 未找到跨模型规则集合 | capability 与参数表影响 wire 字段和 router | 单模型/Provider 子配置 |
| Cherry Studio | Registry 的模型本体、Provider-模型覆盖与用户 Provider 差量分层 | Registry 合并，不是用户规则编辑器 | Endpoint、能力和参数合并后进入请求 | 目录合并 + Provider/模型覆盖 |
| DeepChat | `ModelConfig` 保存模型能力、上下文、采样、endpoint 和媒体字段；支持模型配置 CLI | 未找到通用匹配规则 | 有效模型配置影响 route、工具、媒体和 endpoint | 单模型覆盖 |
| AstrBot | models.dev/`LLM_METADATAS` 与 source 创建模型时的 metadata；可补 modalities、上下文、reasoning | 未找到用户规则编辑器 | Provider 实例能力和 payload/fallback 判断 | 目录富化 + 单模型实例配置 |
| DeepSeek Harness | pi-ai 目录、profile `models` 整表替换、`modelOverrides` 按 ID 覆盖 | 按模型 ID 查表；无独立 UI 规则工作台 | 上下文、输出上限、模态、思考等级参与请求构造 | 配置文件级覆盖 |
| OpenCode | models.dev 目录 + `config.models` Provider/模型覆盖 | 无用户规则链 | 能力、上下文、价格参与请求和成本记录 | 目录富化 + 配置覆盖 |
| Chatbox | Provider API、manifest、models.dev 和本地 custom provider 富化 | 未找到用户规则系统 | 元数据参与模型实例化和能力测试 | 目录富化 |
| Open WebUI | URL/模型记录、Workspace Model、preset/override 组合 | 未找到通用模型规则编辑器 | `urlIdx`、权限、工具/能力和 preset 继承影响路由 | 模型记录与渠道路由配置 |
| SillyTavern | Provider 返回的异构字段、模型列表和 Profile 设置 | Provider 专属字段与名称 fallback；未形成统一规则矩阵 | 上下文、多模态、推理和工具 UI/请求判断 | Provider 专属元数据读取 |
| Pi | 构建期目录、pi.dev 远端叠加、`models.json` 定义/覆盖、扩展注册 | 配置层级覆盖，不是用户规则编辑器 | 能力、价格、contextWindow 参与请求和成本计算 | 目录配置覆盖 |

这张表中的“有覆盖”不能直接等同于“有规则编辑器”。例如 LobeHub 的模型项可编辑、DeepChat 的 `ModelConfig` 可通过 CLI 写入、DeepSeek Harness 的 `modelOverrides` 可按 ID 重塑模型，但它们都缺少 AIO 的规则集合、匹配测试、优先级链和可解释覆盖分析。

## 4. 分类决策

### 4.1 当前推荐归类

在现有笔记体系中，建议采用以下归类：

1. **主归类：LLM 渠道管理 > 模型目录与能力元数据**。记录模型来源、元数据合并、模型实例覆盖、规则对请求/Adapter/参数的影响。
2. **能力标签：模型元数据规则编辑器**。仅在 AIO 这类具备独立规则对象、编辑入口、持久化、匹配语义和运行时消费者的项目上使用。
3. **独特功能统计：不重复计数**。如果要体现 AIO 的差异，可在 LLM 渠道横向对比或 AIO 单项目笔记中标注“稀有扩展能力/机制贡献”，不要把它和媒体工作站、Pages、主动 Agent 等独立用户工作流并列。
4. **暂不新建独立横向类别**。当前只有 AIO 达到完整规则系统，其他项目主要是目录富化或单模型覆盖，样本不足以形成稳定比较维度。

### 4.2 何时可以升级为独立分类

后续若有三个以上项目同时满足下面至少五项，可以再建立“模型元数据规则”分类：

- 有独立的规则集合，而非单个模型字段；
- 用户能创建、编辑、启停、删除或导入规则；
- 支持模型/Provider 匹配、优先级或合并语义；
- 规则结果持久化并可迁移/备份；
- 有命中测试、覆盖解释或冲突诊断；
- 规则影响能力门控、请求参数、Adapter、Token 或媒体工作流；
- 规则与渠道/模型生命周期存在清晰交接，而不是仅用于展示。

这个门槛把“配置对象相似”与“完整产品能力相似”区分开，避免把任何 `metadata` 字段都纳入新类别。

## 5. 已确认边界与未验证事项

- AIO 的规则编辑器 UI、Store、匹配算法和静态消费者已由源码确认；本次未启动 Tauri，未运行验证导入导出、覆盖分析和修改规则后的所有界面变化。
- 横向样本中的“未找到”均限定于相应项目调查笔记和本轮源码搜索范围，不表示项目未来版本或外部插件绝对没有规则编辑器。
- 目录富化与单模型覆盖的具体字段会随项目版本变化；本研究只保留能决定分类的结构差异，不把所有能力字段逐一复制到横向表。
- AIO 规则影响请求构造的静态路径已确认，但“规则修改后已有模型快照与当前活动规则的具体优先级”仍需结合运行态逐项验证。
