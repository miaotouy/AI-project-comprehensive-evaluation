# 外部执行体与应用协作分类边界研究

> 对比对象：`LobeHub`、`Cherry Studio`、`DeepChat`、`OpenCode`、`AstrBot`、`Jan`
>
> 对比更新日期：2026-08-13
>
> 依据：LobeHub 当前源码与产品官网、六个项目现有独特功能/Agent 工具/Agent 角色调查笔记，以及外部 Agent 运行时、Connector、IM 网关和本机控制入口的源码复核
>
> 对比方法：按外部对象在系统中的角色划分“执行者、业务对象、控制与交互表面”，再检查身份、会话、执行、结果回流、取消和权限是否形成完整生命周期
>
> 对比范围：外部 CLI/Agent runtime 的托管与委派、第三方业务应用的账号连接与动作执行、IM/CLI/浏览器等外部交互表面的双向控制；排除普通模型 Provider、只有工具调用的通用 MCP、一次性文件导入和单向分享
>
> 文档定位：正式分类建立前的命名与边界研究；当前结论已迁移到 [`../外部执行体与应用协作/`](../外部执行体与应用协作/) 继续维护，不作为功能存在性终局结论或贡献排名

## 结论摘要

本研究确定正式分类命名为 **“外部执行体与应用协作”**，不直接使用“外部应用连接与控制”。后者会把模型 Provider、普通 MCP、Notion ZIP 导入、DeepLink 和 IM 机器人都吸进来，却无法表达 LobeHub 当前最有辨识度的一部分：它会把 Claude Code、Codex、OpenCode、Pi、Qoder、Amp、OpenClaw 和 Hermes 这类拥有自身工具循环与会话的 Agent 当作可调度执行者。

这个候选类目包含三种不同接入角色：

| 接入角色 | 核心事实对象 | 用户目标 | LobeHub 代表实现 |
|---|---|---|---|
| 外部 Agent 作为执行者 | Agent runtime、原生会话、工作目录、进程/远端任务 | 从统一界面发现、启动、继续、取消和观察其他 Agent 完成工作 | 六种本地 CLI adapter + OpenClaw/Hermes platform task |
| 业务应用作为可操作对象 | 外部账号、连接、资源和动作权限 | 让 Agent 在 Gmail、Calendar、Slack、Notion、GitHub 等业务系统中读取或执行动作 | Connector/MCP/Composio，账号凭据与逐工具权限 |
| 外部控制与交互表面 | IM 线程、CLI、浏览器侧栏、设备连接 | 让用户或 Agent 从其他应用进入、接管、回答、操作、停止或观察同一项工作 | Messenger 网关；CLI Agent 可驱动内置浏览器；设备网关 |

三种角色共享身份绑定、能力发现、审批、事件回流、重连与取消等治理问题，但不能压成同一种“连接”。外部 Agent 自己拥有工具和运行状态；业务应用是被操作的资源域；IM/CLI/浏览器是人类或 Agent 进入系统的交互表面。正式调查时应使用同一总类目、分型记录，避免建立三个高度重叠的小类目。

LobeHub 是当前最完整的正样本。其官网把产品定位为 “Your Chief Agent Operator”，并称可把所有 Agent 汇入同一处、通过 Slack/Discord 等既有渠道汇报；源码进一步确认了官网没有展开说明的本地 CLI adapter、统一事件协议、工作目录与原生会话续接、外部 Agent 反向通知、Connector 权限和浏览器 MCP 桥接。现有“Agent 工具”和“独特功能”笔记分别记录了组件，但尚未用“谁是执行者、谁是被操作对象、谁是控制者”解释完整产品关系。

## 为什么现有类目不足

### 与 Agent 工具的边界

Agent 工具回答“模型本轮能调用什么函数、谁执行、是否审批”。本候选类目回答“一个外部系统以什么身份进入产品、生命周期由谁持有、其状态如何与本地任务或会话对应”。

普通 MCP server 只要完成 `tools/list -> tools/call`，仍归 Agent 工具。只有当产品额外保存外部账号/连接对象、处理 OAuth 或其他凭据、维护资源与动作权限、支持刷新/断开/工作区共享，并把执行结果归入业务工作流时，才进入“业务应用协作”分型。LobeHub 的 `user_connectors`、`user_connector_tools` 与 Connector UI 满足这一门槛；单独添加一个 stdio MCP 配置不满足。

### 与 Agent 角色和多 Agent 编排的边界

内建子 Agent、Agent Group 和普通角色委派仍归 Agent 角色或 Agent 工具。外部 Agent 分型要求执行者具有独立 runtime 身份，至少拥有自己的协议或进程、原生会话/任务状态和工具循环，宿主需要适配而不是直接复用本地 LLM runtime。

因此，LobeHub 的 `callSubAgent` 不进入本分型；Claude Code/Codex/OpenCode 等异构 runtime 进入。DeepChat 的 ACP backend 也进入，因为 `AgentManager` 按 backend 分派到独立 ACP session；Cherry Studio 的 Claude Agent SDK 路径是单一 runtime 的窄正样本。

### 与多表面连续性的边界

多表面连续性关注“同一会话或任务如何在桌面、Web、CLI、IM、移动端延续”。本候选类目只记录外部表面如何建立控制关系、能做哪些动作、如何鉴权和回流；会话是否共享事实源、所有权如何接管，仍由多表面连续性专题深入解释。

DeepChat 的 IM 远程控制和 CLI 控制面同时属于两个视角：本类目记录它们如何成为外部控制入口，多表面连续性记录它们如何复用桌面会话、审批和 pending interaction。AstrBot 的多 IM 渠道主要是机器人宿主表面；若没有“外部应用遥控既有本地任务”的语义，不应仅因支持 Telegram/Discord 就与 DeepChat 记成同一种能力。

### 与 LLM 渠道管理的边界

OpenAI、Anthropic、Ollama 等 Provider 向宿主提供模型推理能力，通常没有独立任务生命周期和文件/工具执行权，继续归 LLM 渠道管理。外部 Agent runtime 即使出现在模型选择器中，也不能按 Provider 处理：它会自行读写工作区、执行命令、派生子 Agent，并返回工具事件与会话标识。

### 与桌面自动化的边界

浏览器、窗口和 GUI 自动化是“控制外部应用”的一种执行机制，但只有形成可识别宿主、动作协议、反馈和权限边界时才进入本类目。一个通用 `runCommand` 或鼠标点击工具仍归 Agent 工具；将 Claude Code 的 MCP 调用桥接到 LobeHub 内置浏览器，并把页面快照、点击、填充和截图返回给同一 Agent operation，则是外部 Agent 与应用控制的交叉实例。

## LobeHub：外部 Agent 统一托管主链

### 支持对象与运行身份

`packages/types/src/agent/heterogeneousAgent.ts` 把异构执行者分为两类：

- `kind: 'local-cli'`：Amp、Claude Code、Codex、OpenCode、Pi、Qoder，均带安装说明、鉴权识别、默认命令、原生 resume 能力和按工作目录分组的默认语义；
- `kind: 'remote-task'`：OpenClaw、Hermes，可在本机或已连接设备上作为平台任务执行。

桌面端为六种本地 CLI 分别注册 driver（`apps/desktop/src/main/modules/heterogeneousAgent/index.ts`），公共包再为其注册流 adapter（`packages/heterogeneous-agents/src/registry.ts`）。这里不是把不同 CLI 当成六个 shell 命令按钮，而是把它们适配成同一种宿主事件模型。

### 本地 CLI 主链

完整静态主链为：

```text
Connect Agent / 对话模型选择
  -> 扫描本机命令与版本、提示安装或登录
  -> 按 Agent driver 组合命令行参数、stdin、图片和工作目录
  -> spawn CLI / Claude Agent SDK session
  -> JSONL 或 SDK stream 进入 AgentStreamPipeline
  -> provider-specific adapter 归一化为 AgentStreamEvent
  -> 对话 store 持久化文本、reasoning、tool、todo、subagent、intervention
  -> 保存原生 sessionId 与 workingDirectory，下一轮 resume
  -> UI 取消时中断进程；失败时按 CLI 缺失、鉴权、额度、目录等分类呈现
```

`packages/heterogeneous-agents/src/spawn/spawnAgent.ts` 负责统一启动、stdin、进程树终止与 session id 提取；`AgentStreamPipeline` 负责 JSONL、adapter 和事件排序；`src/store/chat/slices/agentRun/actions/transports/hetero/heterogeneousAgentExecutor.ts` 把事件接回 LobeHub operation/message 状态机，并处理 resume、工作目录、用户介入、子 Agent、额度与取消。官方词汇表对 Claude Code/Codex 的描述也明确是“在 LobeHub 桌面端驱动本地 CLI，并把任务、工具调用或文件变化渲染为对话区块”（`docs/glossary.zh-CN.mdx`）。

这一实现达到 `主链确认`（静态证据）。尚未逐个运行六种 CLI，也未验证 Windows 进程树终止、所有 CLI 版本兼容性和不同登录状态下的实际错误归一化。

### OpenClaw / Hermes 平台任务主链

平台任务走另一条链，不复用本地 JSONL adapter。`GatewayConnectionCtr.runHeteroTask` 接受来自网关的 `agentType/operationId/taskId/topicId/cwd`：

- OpenClaw 用 `openclaw agent --session-id <topicId> --message ... --local` 启动；同一 topic 新任务会先终止旧进程，避免 session 写锁冲突；首轮 prompt 注入 `lh notify` 协议，让外部 Agent 主动把阶段结果和最终结果写回 LobeHub。
- Hermes 用 `hermes chat --query ... --quiet --accept-hooks` 启动；按 topic 保存 stderr 返回的 `session_id`，下一轮追加 `--resume`；stdout 最终答复通过 `agentNotify.notify` 回流。
- 子进程环境注入 LobeHub server、JWT 和 workspace id，使通知能够落到正确的个人/工作区 topic；任务表保存 PID，可按 task id 终止。

该路径同样达到 `主链确认`（静态证据），并显示“连接 CLI Agent”不只指编码 Agent：LobeHub 已同时容纳流式本地 coding runtime 与基于通知协议的后台平台 Agent。

### 宿主能力反向注入

外部 Agent 不只是输出被收集。LobeHub 还会把宿主能力反向投给 Agent：

- Claude Code/Qoder driver 可接收临时 MCP config；
- `browserMcpTools.ts` 将 `navigate/snapshot/click/fill/press/scroll/screenshot/readPage` 注册到每个 operation 的 MCP server，工具调用再映射到 LobeHub 内置浏览器；
- `agent_intervention_request/response` 允许外部 runtime 在执行中向用户提结构化问题，并保持 MCP handler 挂起直到回答、取消或超时；
- 异构 CLI 的原生工具调用仍由 CLI 自己执行，LobeHub 只观察、渲染并记录工作树变化，不把它们误装成宿主 builtin tool。

这部分说明宿主与外部 Agent 的关系是双向协议适配，而非单向终端日志查看。

## LobeHub：业务应用协作主链

LobeHub 的 Connector 是带账号生命周期的业务应用连接，不只是 MCP URL 列表：

1. `user_connectors` 按个人、Workspace 或 Agent scope 保存连接，支持 OAuth2、bearer、API key 和自定义 header；凭据经 `KeyVaultsGateKeeper` 加密，过期时间单独索引供后台刷新。
2. 连接或 manifest 刷新后，完整工具目录批量写入 `user_connector_tools`；manifest 字段可更新，但用户的 permission、Work artifact 和 limit 设置不会被覆盖。
3. 每个工具有 `auto / needs_approval / disabled` 三态；客户端只拿工具 manifest，不拿 token，实际调用在服务端解密对应连接的凭据后执行。
4. Composio 预置 Gmail、Google Calendar、Airtable、Google Sheets/Docs/Drive、Slack、Confluence、Jira、ClickUp、Dropbox、Figma、HubSpot、OneDrive、Outlook、Salesforce、WhatsApp、YouTube、Zendesk、Cal.com、Notion、Twitter、GitHub 等 24 个应用类型（`packages/const/src/composio.ts`）。

现有 [LobeHub Agent 工具调查笔记](../Agent工具/LobeHub-Agent工具调查笔记.md) 已确认连接器调用、权限与凭据细节，本研究不重复工具执行实现。这里补充的分类结论是：只有“账号连接 + 业务动作目录 + 作用域/权限 + 生命周期”共同存在时，才把 MCP/Composio 计入应用协作；任意 MCP server 的函数调用不自动升级为独特产品能力。

## LobeHub：外部交互表面

### Messenger

Messenger 安装入口要求已登录 LobeHub 用户，OAuth state 绑定发起用户并设置短 TTL；统一 webhook 路由把原始请求交给平台 handler，由平台自己校验签名。Slack、Discord、Telegram、WeChat 已有 binder/installation/outbound 实现；网关支持 webhook 与持久连接两种模式，并可改由外部 `MESSAGE_GATEWAY` 服务维持连接（`messengerInstall.ts`、`platformWebhook.ts`、`gatewayCron.ts`）。

这一产品面已超过“发通知”：存在安装所有者、账号/线程绑定、入站命令和出站投递。不过当前 LobeHub 独特功能笔记尚未逐平台走通“外部消息 -> Agent/topic -> 回复原线程”的完整持久化链，继续标为 `入口确认`，不因官网宣称“Agents where you already chat”直接升为主链确认。

### 内置浏览器与设备网关

内置浏览器是 Agent 可见、用户实时可见的共享应用表面；设备网关则允许服务端把 external/platform agent task 分发到具体桌面设备。两者均值得在正式类目中记录执行位置、操作归属和取消语义，但它们是否构成跨设备连续性，应回链相邻专题，避免重复计贡献。

## 横向样本与反例

| 项目 | 可纳入事实 | 分型判断 |
|---|---|---|
| LobeHub | 六种本地 CLI、Claude SDK runtime、OpenClaw/Hermes platform task、Connector/Composio、Messenger、内置浏览器桥 | 三种接入角色均覆盖，当前主样本 |
| Cherry Studio | Claude Code Agent Session，SDK 自带 runtime、工具流与审批接入 | 外部 Agent 执行者的窄正样本；只有一个主要 runtime，不等于统一 CLI 控制平台 |
| DeepChat | ACP 独立 backend；IM 远程控制；本地 CLI 控制平面 | 外部 Agent 协议和外部人类控制表面的双正样本 |
| Jan | `/v1/orchestrations`、CLI/外部 Agent 预接与 MCP 编排 | 应补查外部 Agent 是执行者、调用者还是协议客户端，不能仅按端点名称归类 |
| OpenCode | ACP server、Web/桌面/CLI 共享 session 与事件源 | 主要是“把自己暴露给外部客户端”的反向样本；适合比较协议方向，不应与宿主控制外部 Agent 混记 |
| AstrBot | 多 IM 平台机器人宿主、插件和主动 Agent | 是外部交互表面样本；若各平台只承载 AstrBot 自己的会话，不构成“遥控另一个桌面应用” |

另有两个应保留的负面对照：普通 Provider API 只提供推理，不是外部 Agent；Notion ZIP 导入只迁移一次内容，没有持续连接、动作权限和结果回流，不是应用协作。

## 建议的准入门槛

一个候选至少满足以下五项中的四项，才进入本类目；只满足一两个接口条件时留在 Agent 工具、LLM 渠道或导入导出：

1. **可识别的外部身份**：Agent/runtime、外部账号、应用 installation、IM endpoint 或设备不是匿名 URL。
2. **持续生命周期**：具有安装/发现、连接、鉴权、运行/调用、恢复/刷新、断开/取消中的多个阶段。
3. **双向协议**：宿主能发任务或动作，外部端能回传结构化事件、结果、状态或用户输入，而非单向导入/分享。
4. **状态归属**：外部会话、任务、资源或线程与本地 topic/task/agent/workspace 有明确映射。
5. **治理边界**：能说明执行位置、凭据、权限/审批、取消、并发、审计和多用户 scope。

外部 Agent 执行者还应额外满足：它拥有自己的工具循环或任务 runtime，宿主需要适配其事件和原生会话。业务应用协作还应额外满足：账号/连接和逐动作权限是持久对象。外部控制与交互表面还应额外满足：用户或 Agent 能从该表面发起、接管、回答、操作或停止工作，而不只是收一条通知。

## 正式调查建议维度

1. 外部对象是谁，接入角色是执行者、业务对象还是控制表面。
2. 谁发起连接，身份如何绑定到 user/agent/workspace/device。
3. 使用 CLI、SDK、ACP、MCP、OAuth、webhook、WebSocket、HTTP RPC 还是私有协议。
4. 谁持有执行循环、进程、原生会话和工具权限。
5. 外部状态如何映射到本地 topic/task/message/work，重启后怎样恢复。
6. 能否流式回传文本、reasoning、工具、文件变化、子 Agent、审批和结构化提问。
7. 取消是否能到达真实外部执行体；断线后是重连、重放、轮询还是丢失。
8. 凭据保存、刷新、作用域、代表谁调用，以及团队共享连接的所有权。
9. 逐动作审批、自动放行、禁用、失败方向和审计记录。
10. 外部内容如何标记为不可信，是否可触发本机文件、命令、浏览器或账号副作用。
11. 产品表面是否让用户看到执行位置、账号、工作目录、状态和接管入口。
12. 与 Agent 工具、多表面连续性、Agent 编排和 LLM 渠道的交叉点如何回链。

## 正式分类落地状态

本轮仓库扫描确认至少八个项目存在可比较主链，已达到建立一级调查类目的门槛。正式目录为 [`../外部执行体与应用协作/`](../外部执行体与应用协作/)，采用稀疏调查，不为全部项目创建对称空笔记。

首批样本包括 LobeHub、DeepChat、Cherry Studio、OpenCode、Jan、AstrBot、Hermes Agent 和 VCPToolBox；横向结论见[八个项目外部执行体与应用协作横向对比](../外部执行体与应用协作/外部执行体与应用协作横向对比.md)。本边界研究保留分类形成过程、LobeHub 专项证据和准入理由，后续状态更新以正式分类文档为准。

## 已确认边界与未验证事项

- 本研究以静态源码为主；LobeHub 六种本地 CLI、OpenClaw/Hermes、Messenger 和 Connector 未逐项运行。
- LobeHub 官网当前强调 Chief Agent Operator、统一 Agent、IM Gateway 与业务协作，但本地 CLI adapter 的细节主要由源码和产品内词汇表确认，不能只从首页宣传推导实现范围。
- Claude Code SDK runtime 与 CLI runtime 的事件兼容程度、切换时 session 连续性尚未运行验证。
- OpenClaw 以 `lh notify` 主动回传，Hermes 以 stdout/stderr + 宿主 notify 回传；两者不是同一种流协议，正式比较要保留差异。
- Connector 的 24 个 Composio 应用是预置目录数量，不表示每个应用的所有动作均已运行验证，也不表示第三方服务永远维持兼容。
- Messenger 单平台完整往返、线程映射、权限审批和附件语义仍待专项走通。
- 内置浏览器 MCP 工具已确认注册和转发入口，真实页面交互、登录态、安全提示与取消行为未运行验证。
