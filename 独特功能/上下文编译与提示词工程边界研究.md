# 上下文编译与提示词工程边界研究

> 对比对象：`AIO Hub`、`SillyTavern`、`VCPToolBox`、`VCPChat`、`Chatbox`
>
> 对比更新日期：2026-08-11
>
> 依据：五个项目当前代码快照、现有 Agent 角色、会话与消息管理、对话请求与上下文、Chat UI 调查笔记，以及本次对编译入口、持久化对象、执行顺序和调试表面的源码复核
>
> 对比方法：先按事实对象和生命周期划分普通请求拼装、角色模板与可编程上下文编译，再以“可持久化编辑对象、明确编译阶段或顺序、影响最终请求、调试或可解释表面”四项检查实现完整度
>
> 对比范围：面向模型输入的消息配方、宏、变量、正则、世界书、占位符、注入规则、管道排序和最终上下文检查；不重复调查普通历史选择、Token 截断、Provider Adapter、会话 CRUD 和单段 system prompt
>
> 文档定位：独特功能自然聚类的边界研究与调查路由，不作为全项目统一功能矩阵或贡献排名

## 结论摘要

“上下文和提示词工程”与会话、请求上下文发生重叠，是因为三者最终都会接触消息数组，但它们拥有的事实对象和用户目标不同：

- **会话与消息管理**保存会话、消息、分支、摘要和绑定关系，回答“系统长期保存了什么”。
- **对话请求与上下文**执行一次生成任务，回答“本轮从哪些来源取内容、按什么顺序构造请求并发送”。历史选择、摘要、Token 截断、知识库交接和普通 system prompt 注入都在这里。
- **Agent 角色**保存人格、角色说明、开场白、示例对话和常规 Prompt preset，回答“这个角色或 Agent 被配置成什么”。
- **上下文编译与提示词工作台**让用户维护一组可组合、可排序、带作用域或阶段的规则，并把角色、世界状态、变量、历史和临时指令编译成最终请求；通常还允许检查规则为何生效及最终生成了什么。

因此，不宜把所有项目的 prompt library、摘要算法或请求拼装都列为独特功能。本次确认的自然聚类由 AIO Hub、SillyTavern、VCPToolBox 和 VCPChat 构成；Chatbox 是负面对照，其 Copilot prompt 仍是普通首条 system 消息，归并“对话请求与上下文”。

建议将待查聚类从“上下文 DSL 与提示词工程”改为**“上下文编译与提示词工作台”**。这里的“工作台”强调用户能编辑、组合和观察编译规则；“编译”强调这些对象经过确定的阶段转为模型请求，而不要求每个项目都使用形式化 DSL。

## 与相邻类目的边界

| 类目 | 核心事实对象 | 典型生命周期 | 本研究中的处理 |
|---|---|---|---|
| 会话与消息管理 | 会话、消息、分支、摘要、消息元数据 | 创建、编辑、持久化、恢复、检索 | 只记录编译器读取或写回这些对象的交接点 |
| 对话请求与上下文 | 一次 generation task 及其临时请求 | 提交、拼装、执行、流式消费、最终回写 | 固定算法的历史选择、Token 预算、压缩和 Provider 交接留在此类目 |
| Agent 角色 | Agent、角色卡、人格字段、模型配置、普通预设 | 创建、绑定、导入导出、在多次请求中复用 | 单段 prompt、角色 system prompt 和仅供选择的模板库不单列 |
| 上下文编译与提示词工作台 | 规则、宏、变量、世界条目、消息配方、注入位置、处理器顺序 | 编辑并持久化，在每轮请求中求值、排序、展开和注入 | 只收录形成可编程编译链的实现 |

边界不以代码文件归属判断。同一条发送主链可以同时被两个类目引用：请求类目记录它如何完成一次发送；独特功能专项记录用户能够编程哪些编译对象、这些对象怎样组合，以及能否解释最终结果。

## 纳入判定门槛

候选至少满足下列四项中的三项，才进入“上下文编译与提示词工作台”自然聚类：

1. **可持久化的编辑对象**：规则不是硬编码分支或单次输入，而是用户可维护的消息配方、宏、变量、世界条目、占位符文件、正则或注入规则。
2. **明确编译阶段或顺序**：存在处理器顺序、作用域合并、pre/post 阶段、depth/order、递归展开或其他可解释的求值次序。
3. **进入最终请求**：规则实际改变发送给模型的 messages、prompt、tools 或相关请求字段，而不只是改变显示文本。
4. **调试或可解释表面**：用户能查看最终上下文、激活条目、Token 分项、变量状态、占位符展开、正则命中或处理器执行结果。

下列实现默认不纳入：只把一段文本写入 system 消息；只有模板选择而没有组合和阶段；固定的摘要或 Token 截断算法；只在渲染阶段替换文本的正则；没有接入请求主链的 DSL 编辑器或配置骨架。

## 五项目分型

| 项目 | 分型与状态 | 判断 |
|---|---|---|
| AIO Hub | 完整工作台，`主链确认` | 可配置处理器管道、消息配方、宏、变量、世界书、请求/显示正则和上下文分析器共同形成客户端上下文编译环境 |
| SillyTavern | 完整工作台，`主链确认` | Prompt Manager、World Info、宏引擎、正则作用域和 prompt 分项统计共同参与每轮请求构造 |
| VCPToolBox | 服务端上下文编译器，`主链确认` | TVS/占位符语言在服务端递归展开 Agent、工具、文件、插件和条件变量，并提供编辑、浏览和最终请求检查面 |
| VCPChat | 规则型工作台，`主链确认` | VCPChatTarven 规则以全局、Agent、群组作用域维护 suffix 与 depth 注入，单聊和群聊均接入最终请求 |
| Chatbox | 普通请求拼装，`归并已有类目` | Copilot prompt 只成为首条 system 消息，没有规则阶段、注入位置、宏求值或编译调试面 |

### AIO Hub：处理器管道与同源预览

AIO Hub 的 `contextPipelineStore` 注册默认处理器，并允许用户启停、排序后持久化到 `llm-chat/pipeline-settings.json`。当前默认链覆盖 session、async result、regex、transcription、worldbook、injection、knowledge、variable、token、formatter 和 asset 十一类处理器；执行入口在 `src/tools/llm-chat/core/pipeline/defaultProcessors.ts` 与 `src/tools/llm-chat/stores/contextPipelineStore.ts`。

消息配方并非只有 system prompt：`injection-assembler.ts` 处理骨架、深度注入、锚点注入、模型匹配、消息组和宏展开。`MacroRegistry` 将宏处理分为 pre-process、substitute 和 post-process，并能读写会话变量。Regex 还区分请求与显示阶段，并按 Global、Agent、User 作用域合并。

`ContextAnalyzerDialog.vue` 通过 `getLlmContextForPreview()` 复用标准管道，展示结构化消息、Token、宏和变量状态。这里需要保留一个边界：`RawRequestView.vue` 构造的是 provider-neutral 模拟请求体，不等于 Provider Adapter 最终在线发送的精确 body；它证明编译结果可观察，但不能替代渠道层抓包。

### SillyTavern：多对象汇合的内容编译环境

SillyTavern 的 Prompt Manager 持久化 `prompts` 与 `prompt_order`，支持启停、排序、角色、相对或绝对注入、depth/order 和 generation trigger。`prepareOpenAIMessages` 在 `public/scripts/openai.js` 中把 Prompt Manager、World Info、扩展 prompt 与历史汇合，不是简单地在数组头部追加一段模板。

World Info 在 `public/scripts/world-info.js` 中实现关键词或正则扫描、递归激活、预算、概率、sticky/cooldown/delay、depth 和 outlet 等规则。新宏系统的 `MacroEngine` 使用 lexer、parser 和 CST，支持嵌套、作用域、控制流、动态与第三方注册，并输出语法诊断。Regex 又按 Global、Scoped、Preset 三种持久化域合并，区分 prompt/display、placement、depth 和宏替换。

`public/scripts/itemized-prompts.js` 按会话和消息保存 prompt 分项与 Token 统计，提供了追溯表面。SillyTavern 的能力分散在角色卡、Prompt Manager、World Info、Advanced Formatting 和扩展层，但在生成入口会汇入同一编译结果，因此仍是完整正样本。

### VCPToolBox：服务端占位符语言与最终请求留档

`modules/messageProcessor.js` 是服务端变量编译器，递归展开 Agent、Toolbox、Tar、Var、Sar、TVS 和静态/动态插件占位符。它同时处理权限角色限制、Agent/Toolbox 去重、循环引用检测、按模型选择的 SarPrompt，以及 TVStxt 文件递归引用。

TVS 文件由 `modules/tvsManager.js` 和 `routes/admin/tvs.js` 提供 CRUD、磁盘持久化、文件监听和缓存失效；管理端 `TvsFilesEditor.vue`、Placeholder Viewer/Explorer 与 Agent 文件快捷插入形成编辑和检查表面。`modules/finalContextStore.js` 在首次上游 fetch 前保存实际最终 body，并保留最近五份；与 AIO 的 provider-neutral 模拟预览相比，它更接近线上请求事实。

VCPToolBox 中还存在 OneRing、VCPTimeLine 和 ContextFoldingV2，但它们应与 TVS 语言层拆开：TVS 决定文本和能力如何展开；OneRing 维护跨端时间线与连续性；VCPTimeLine 提供持久时间线/记忆对象；ContextFoldingV2 决定长历史如何语义压缩。后三者可以使用编译器接口，却不是同一种提示词语言能力。

### VCPChat：轻量但语义明确的注入规则工作台

VCPChat 的“高级回复 / VCPChatTarven”规则对象包含 `system_suffix`、`user_suffix` 和 `context_inject`，支持 global、agent、group scope，启停、排序、可选包裹标记，以及 role 和 depth。`modules/tavernRulesEngine.js` 负责规则求值，`modules/ipc/tavernHandlers.js` 与 `Tavernmodules/tavern-manager.js` 负责管理和持久化，数据保存到 `AppData/VCPChatTarven.json` 并通过 mtime 缓存刷新。

单聊 `modules/chatManager.js` 与群聊 `Groupmodules/groupchat.js` 都在最终 `messagesForVCP` 组装中接入规则。尤其是 `user_suffix` 只影响本次 VCP 请求，不写入会话历史，明确区分了“临时编译输入”和“持久消息事实”。Agent 正则的请求层/渲染层、角色和 depth 过滤可作为同一工作台的辅助机制；模块化 system prompt 积木和普通预设仍归 Agent 角色配置。

### Chatbox：单段 Prompt 不构成编译器

Chatbox 的 Copilot 仍使用普通 Session，发送时仅把 `copilot.prompt` 写入首条 system 消息（`src/renderer/routes/index.tsx`，Copilot session 创建分支；类型见 `src/shared/types.ts` 的 `CopilotConfig`）。本次在该入口及现有请求笔记范围内未找到宏、规则作用域、可配置注入位置、编译阶段或最终上下文调试面，因此不进入本聚类。

## 编译对象矩阵

| 项目 | 可持久化编辑对象 | 顺序与阶段 | 对最终请求的影响 | 可解释表面 |
|---|---|---|---|---|
| AIO Hub | 处理器设置、消息配方、宏/变量、世界书、三作用域正则 | 处理器 priority；宏三阶段；请求/显示正则；depth/anchor | 生成最终 messages，并可注入工具、附件与知识内容 | 上下文分析器、Token、宏调试、变量状态、模拟 raw request |
| SillyTavern | prompts/order、World Info、宏、三域正则 | prompt order、relative/absolute、depth/order、递归激活、宏 parser | 汇入 text-completion prompt 或 OpenAI messages | itemized prompts、Token 分项、宏诊断、regex debugger |
| VCPToolBox | TVStxt 文件、环境变量、Agent/工具占位符、处理器顺序 | 递归展开、权限过滤、去重、循环检测、模型条件 | 在服务端形成上游请求 body 与工具上下文 | TVS 编辑器、Placeholder Explorer、Final Context Viewer |
| VCPChat | 三类 Tavern 规则、scope、role、depth、order | scope 合并、启停排序、suffix/context injection | 改写单聊或群聊的 `messagesForVCP`，临时 suffix 不污染历史 | 规则管理器与持久化列表；暂无与前三者同等完整的最终上下文分析器 |
| Chatbox | Copilot 单段 prompt | 固定首条 system 消息 | 普通 system 注入 | 本次未找到编译级调试面 |

## 语言层与策略层拆分

同一个请求中，“用什么语言表达上下文”和“如何控制上下文规模或连续性”可能连续执行，但不应合成一个独特功能：

| 层次 | 处理的问题 | 例子 | 默认归属 |
|---|---|---|---|
| 语言/规则层 | 哪些内容在何种条件、位置、作用域和顺序进入请求 | TVS、消息配方、宏、World Info、VCPChatTarven、请求正则 | 上下文编译与提示词工作台 |
| 请求策略层 | 历史过长时保留、裁剪、摘要或替换什么 | Token truncation、ContextFoldingV2、普通摘要 | 对话请求与上下文；复杂持久策略可另立能力卡 |
| 连续性/记忆层 | 跨会话、跨端或跨时间保存什么状态 | OneRing、VCPTimeLine、长期记忆对象 | 多表面连续性或记忆演化 |
| 展示层 | 模型输出在 UI 中怎样替换、隐藏或格式化 | 仅 display 阶段的正则、Markdown/AST 渲染 | 消息渲染器 |

正则是最容易跨界的对象。只有参与 prompt/request 阶段、带持久化作用域并与其他规则共同编译时，才作为本聚类的一部分；纯显示正则留在消息渲染器。摘要和折叠同理：它们可以是编译管道中的一个处理器，但其独特性来自压缩策略，而不是“提示词工程”这个泛称。

## 对待查清单的影响

1. 聚类改名为“上下文编译与提示词工作台”，并链接本研究。
2. AIO Hub、SillyTavern、VCPToolBox 和 VCPChat 标为 `主链确认` 的自然聚类样本，不扩成十六项目对称矩阵。
3. VCPChat“高级回复 / VCPChatTarven 三类注入”由 `入口确认` 升为 `主链确认`。
4. VCPToolBox 的 TVS 保留为语言层主贡献；OneRing/VCPTimeLine 路由到连续性或记忆，ContextFoldingV2 路由到请求压缩策略。
5. Chatbox Copilot、普通 prompt library、角色 system prompt 和固定摘要算法明确归并已有类目，不作为聚类缺失项统计。

## 已确认边界与未验证事项

- 本次结论来自静态源码主链，没有逐项目运行生成请求；四个正样本均为 `主链确认`，不是 `运行确认`。
- AIO Hub 上下文分析器复用真实处理管道，但 raw request 视图不是最终 Provider Adapter body。
- VCPToolBox Final Context Store 位于首次上游 fetch 前，能反映实际请求 body；本次未验证多并发请求下管理端查看顺序和敏感字段暴露边界。
- VCPChat 已确认规则接入单聊和群聊，本次未发现与 AIO、SillyTavern 等量的逐处理器 Token 或命中追踪表面，因此归为中等复杂正样本。
- SillyTavern 宏引擎、World Info、Prompt Manager 和正则由不同模块维护；本次确认它们在生成链汇合，但未运行验证所有 Provider 分支的完全一致性。
- Chatbox 的否定结论限于 Copilot 创建/发送入口和当前请求调查覆盖范围，不能外推为仓库未来或插件生态永远不存在编译能力。
