# 上下文编译与提示词工程横向对比

> 对比对象：AIO Hub、SillyTavern、Risuai、VCPChat、VCPToolBox、OpenClaw、RikkaHub
>
> 对比更新日期：2026-11-05
>
> 依据：本类目 7 篇单项目调查笔记及其链接的请求、会话和消息渲染专项；源码快照与覆盖范围以各来源元数据为准，SillyTavern 沿用 2026-09-16 调查
>
> 对比方法：按规则对象、选择和编译顺序、请求层结果、消息生命周期变换、显示投影与调试表面比较；证据只覆盖局部链路的项目明确标记
>
> 对比范围：可持久化或配置驱动的规则、模板、宏、占位符和预处理器的编译与消费面；不比较提交、Provider、流式、会话存储、工具执行和 DOM 实现
>
> 文档定位：实现学习与跨项目横向比较，不作为整改方案

## 结论摘要

- 七个项目都能追到配置或规则驱动的变换进入模型请求或显示投影，但规则对象的完整持久化语义并非都已覆盖。AIO Hub、SillyTavern、Risuai、VCPToolBox、OpenClaw 和 RikkaHub 有可比较的请求层编译链；VCPChat 的单聊已确认由独立请求编排器集中完成历史筛选、附件转换、消息正则、Tavern 规则、情绪提示、system prompt 与模型参数组装，历史从最近的压缩检查点开始截取；三模式提示词由 PromptSponsor 以白名单工具托管。
- 请求层的编译单元差异明显：AIO Hub 用可排序处理器管道，SillyTavern 在生成函数中汇合多类规则，Risuai 用模板卡片或旧式分组排序，VCPToolBox 把预设和预处理器串成单次网关请求变换，RikkaHub 用一条固定顺序的输入转换器管道。
- 同一规则系统不必只改变 prompt。SillyTavern 的正则明确分为请求、权威消息写回和显示投影；Risuai 的显示模式已由消息渲染专项定位，和请求前处理、输出写回分别消费；VCPToolBox 把初始请求、递归工具消息和客户端投影分开，OneRing 还可保留插件级历史。
- 调试面需按观察阶段比较：AIO Hub 同时提供当前配置重建预览和协议适配后的有界实发快照，SillyTavern 留存 itemized prompt，Risuai 提供 requestChatData 数组预览，VCPToolBox 保留首次 fetch 前快照。快照预算、后续请求与实际网络传输的覆盖范围各不相同。
- OpenClaw 的编译不是一个统一规则合并器：工作区文件、skills、prompt 模板、memory、prompt hooks 与可选 context engine 各自按 owner、schema 与阶段接入，多数来源只改模型输入不改 transcript，只有 compaction 摘要、memory flush 与会话 snapshot 写入持久 owner。其系统提示词编译区分 stable/dynamic cache boundary，并保留 prompt-only 与 model-only 分流的独立证据。

## 对比边界

本类以“规则对象或配置如何被选择并编译到哪个消费面”为中心。对话请求与上下文保留提交、任务和执行主链中的交接点；会话与消息管理保留权威对象的 schema 和持久化；消息渲染器保留 Markdown、DOM 和流式重绘。固定 system prompt、历史截断、检索或工具执行只有在作为规则编译输入或结果时才在这里出现。

## 编译顺序与请求层结果

| 项目 | 已确认的主要顺序 | 模型可见结果的交接 |
| --- | --- | --- |
| AIO Hub | 压缩遮罩后按处理器顺序变换历史，预设先编译有效片段再展开宏和注入；可将自动工具与 Recall 的动态部分后置 | 管道产出交给请求执行器，并在协议适配后的发送观察器捕获有界实发请求体；未做真实网络比对 |
| SillyTavern | 历史 prompt 正则、World Info、系统与扩展字符串、格式转换和预算裁剪后，再允许事件替换整体 prompt | text completion 形成 finalPrompt；OpenAI 走独立消息准备路径 |
| Risuai | 规则来源进入分组桶，历史经 editprocess，按模板或 formatingOrder 拼装，再过 depth prompt、Lua editRequest、请求触发脚本和 reformater | requestChatData 收到的数组是已确认请求层依据；Provider 适配后形状另属请求类目 |
| VCPChat | 单聊由独立请求编排器按历史筛选、附件转换、消息正则、Tavern 规则、情绪提示、system prompt、模型参数的顺序组装，历史从最近压缩检查点开始截取；群聊先选择并排序发言者，再按当前 groupHistory 为各 agent 构建上下文，启用窗口时只取最近 N 条 | 请求层顺序已可静态确认；最终消息数组与 system prompt 形状未运行核实 |
| VCPToolBox | 裁剪、预设与变量之后，按序捕获、静态注入与多模态，再托盘搬运、RAG、时间线和历史补充/折叠，最后检测与角色拆分 | 处理数组写回请求体并构造首次上游输入；托盘不自行检索，异常时本轮搬运整体回滚 |
| OpenClaw | 先准备 skills/bootstrap/工具，由 `buildAgentSystemPrompt` 生成系统提示词，再编译历史、执行 prompt hook 与运行时上下文分流，最后 transformContext/convertToLlm；skills 目录只放元数据，完整正文按需读取 | 紧邻 Provider 的证据是 streamFn 收到的 Context；CLI 经 argv/stdin、Codex 投影为 thread/turn developer instructions |
| RikkaHub | 每步合成系统提示、按开关加入记忆及工具说明；裁剪历史后依次处理提醒、规则注入、占位、文档/OCR、模板和工作区提醒；命中规则按优先级稳定排序并按位置/深度分组 | 请求使用会话固定绑定与助手实时字段的合成配置；转换结果交给 Provider，每步重新构建而不累积注入 |

## 消息生命周期与显示投影

| 项目 | 请求之外的已确认变换 | 显示层边界 |
| --- | --- | --- |
| AIO Hub | 压缩节点遮罩原历史、保留摘要；变量快照写入消息元数据；请求规则作用于消息副本 | 显示正则有独立消费点，不能从渲染替换推定权威历史或模型输入已改写 |
| SillyTavern | 无标记正则生成后清洗并写回 chat[]；promptOnly 只影响本次 prompt | markdownOnly 正则只进入 Markdown 格式化 |
| Risuai | 输出规则改写占位正文，收尾脚本继续消费；消息内交互脚本可另行写回聊天 | 显示处理在 Markdown 前运行 Lua、插件和正则，属独立消费点；详见消息渲染专项 |
| VCPChat | 压缩追加检查点而保留原历史，后续请求从最新有效点起取；串行群聊后续成员看到已更新历史 | Agent 正则按上下文与渲染分流，渲染规则不改历史真源 |
| VCPToolBox | 工具递归使用独立消息数组；OneRing 可预记输入历史，并在有效响应结束后提交正文和回合状态，失败不整体回滚此前写入 | 推理包装与工具信息投影到客户端输出；插件历史和客户端会话仍分属不同对象 |
| OpenClaw | prompt-only 注入不改写 transcript；hidden runtime carrier 进入模型后从可见 transcript 过滤；compaction 以摘要替换 active agent 消息并保留 SQLite 原文 | systemPromptReport 与 `/context` 只保存统计或账本；runtime context 用 display:false，不能从 UI 倒推权威 transcript |
| RikkaHub | 用户消息入库前跑非 visualOnly 的 USER 正则并持久化；助手输出的非 visualOnly 正则在生成收尾替换文本与推理部件后写回会话 | 显示层只跑 visualOnly 为真的正则，作用点是助手气泡、用户气泡与推理内容，替换后再交给 Markdown；显示替换不进入模型输入 |

## 已确认边界与未验证事项

- VCPChat 的三模式提示词与压缩模板分属不同对象：前者以 Agent 配置为权威，后者从全局设置读取并合成权威检查点；渲染正则又是独立消费面。规则实际命中和最终网络形状仍需分别验证。
- 所有项目的编辑器交互、规则实际命中、异步脚本组合和最终 Provider payload 的运行时一致性，仍以各单项目笔记的未验证事项为准。
- OpenClaw 的请求层证据以紧邻 `streamFn`、CLI argv/stdin 与 Codex thread/turn builder 为准；未运行真实 Provider、CLI 进程或 Codex app-server，未取得具体渠道与模型下的最终网络 payload。其可编辑规则分布在不同 owner，不提供统一命中顺序或规则 diff 界面。
- 正则不是独立顶层分类依据。同一规则需要按其进入请求、写回权威消息或仅投影显示的结果分别连接相邻类目。
