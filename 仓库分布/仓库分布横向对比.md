## 结论摘要

这些项目的仓库形态可以分为四组：以 Electron/Tauri 为中心的多端客户端、前后端合仓的 Web 服务、按能力拆包的 Agent/CLI monorepo，以及插件/附属程序集合。OpenClaw（1,265.0 万行）是源码规模最大的样本，Dify（264.5 万行）也进入大型前后端合仓组；Hermes Agent（392.6 万行）与 LobeHub（333.6 万行）仍是大型代表。LobeHub 以统一的 TypeScript 应用与业务包为主，Hermes Agent 则混合了 Python Agent 核心、TypeScript 多种 UI、测试、技能和文档；两者的目录职责并不相同。Risuai 落在四组之间：单包 SPA 加多个薄平台壳（Tauri 桌面、Node 自托管、Capacitor 移动配置），同一份业务代码靠运行时探测区分平台，平台差异由探测逻辑而非构建分支承担。RikkaHub 提供了另一种原生形态：核心代码放在单个 Gradle 多模块工程里，Android 应用按能力域拆出独立库模块，Web 前端、本地化工具与 SSE 轨迹 CLI 各自作为旁路子工程维护，平台差异由模块与构建目标承担。Codex 则是本次唯一的原生 Rust 形态：单个 Cargo workspace 承载约 166 个 crate，Bazel 负责可复现发行，Rust 占可识别源码约 95.9%，平台差异由按操作系统的沙箱 crate 与跨平台发行矩阵承担，Python 与 TypeScript 只作为 SDK 与协议生成绑定存在。

文件数同样不能直接代表源码规模。Open WebUI 当前为 5,274 个跟踪文件，静态资源仍是主要组成；VCPToolBox 的 AdminPanel 产物已不再跟踪，但仓内仍保留 `vendor`；VCPChat 最大源码区域是 `vendor`；OpenCode 的文档主要是多语言文档站；Hermes Agent 的大量文档来自 skills 与 i18n 副本；Risuai 跟踪约 80 MB 的 tokenizer 模型数据，贡献的是字节量与存储而非源码行；RikkaHub 跟踪的分词词典与原生库同样只贡献体积。横向理解仓库必须同时看源码行、目录用途和被跟踪的配套资产。

测试数量只表示仓内可见测试资产，不表示覆盖率。Hermes Agent、LobeHub、Cherry Studio、DeepChat、Dify、OpenClaw、Pi 和 OpenCode 有大规模、按模块分布的测试；Open WebUI 当前只识别到 2 个跟踪测试文件；Manifold Desktop 未识别到显式测试树；Risuai 的 32 个测试文件全部为 Vitest 单元测试，无端到端；RikkaHub 的 211 个测试文件以模块内离线夹具为主。这些是仓库结构事实，不足以推导运行质量。

结合其他类别笔记，可以做出一个范围有限的推测：仓库结构通常与产品当前的主要增长方向互相适配。共享 Web 前端有利于把聊天和设置同步带到多端，服务端合仓有利于增加账号、协作和任务治理，能力拆包有利于增加客户端或协议入口，插件/附属进程集合则有利于接入异构工具。相应成本会落在平台适配、跨层协议、包间 API 或插件治理上。第 3 节逐项说明这些可能影响；除已单列来源的 AIO Hub 早期沿革外，本文不据现状推断作者的真实选型动机或未来路线图。

DeepSeek Harness 是本次对比中插件颗粒度最细的 TypeScript monorepo 插件集合（pnpm 11.28.5 workspace、7 个成员层级 + tsc -b 的双编译面 + tsdown + vitest）：产品包分属 53 组，界面按 60 个 `ui-*` 包拆分。20,531 个跟踪文件中源码 7,712 文件 / 1,595,947 行，TypeScript 占约 94.1%，`packages/client` 与 `core` 仍是最大区域。框架运行时以 `vendor/` 9 包 vendored Cordis（本地修改清单 V1–V27）完全持有，pi-ai（`@earendil-works/pi-ai@^1.3.0`）与 pi-telemetry 则走 npm 依赖而非 vendored；文档 5,237 文件、测试代码 4,338 个（另有 1,999 个快照与夹具），四个运行时（Node、浏览器 React、Python SDK、Landlock C）各有独立对外边界。

### 结构模式

- **共享前端、多壳复用**：Chatbox、AIO Hub、Jan 和 NextChat 让 Web 技术前端被桌面或移动壳复用，但复用深度不同。Chatbox 把桌面/Web/Capacitor 差异收敛进 `src` 的平台层；AIO Hub 明确保留单独 `mobile/src`；Jan 共享 `web-app`，平台能力在 Tauri 插件与 feature 中分化；NextChat 的 Tauri 层最薄。Risuai 同一份 SPA 靠运行时探测覆盖 Web、Tauri 桌面与自托管，复用边界由探测逻辑承担，未设平台构建分支。
- **累积式工具箱**：AIO Hub 最初以工具为产品单位，聊天会话是在工具箱形成后加入的能力，当前 `src/tools` 占约 61% 源码，与这一沿革一致。其原名、正则应用器起源和 SillyTavern 背景等沿革细节见 3.2 节；代码快照只能确认当前结构和能力，无法独立复原早期历史。
- **主应用与内部包并重**：Cherry Studio、LobeHub、OpenCode、Pi。Cherry 的主进程/renderer 仍占绝对多数；LobeHub 与 OpenCode 已把数据库、模型运行时、工具和平台入口拆成大量包；Pi 的每个顶层包本身就是可说明、可测试的发布能力。
- **前后端同一发行单元**：AstrBot 与 Open WebUI 都把 Python 服务和 Web 前端合仓。AstrBot 打包时显式把 Dashboard 产物嵌入 Python 包；Open WebUI 的 Python wheel 强制包含前端 build。
- **扩展集合式仓库**：VCPToolBox、VCPChat、Hermes Agent 都含大量插件/skills/附属进程。Hermes 已有 Python/npm workspace 与明确应用边界；VCP 两仓更多依靠目录和进程协议组织，量级统计容易被 vendor、dist、知识与技能资料影响。
- **原生单应用与能力域模块**：RikkaHub 用一个 Gradle 工程承载 Android 应用与按能力域切分的库模块，`app` 聚合界面、数据层与服务，Web 前端与两个研发工具作为旁路子工程独立维护，平台差异由模块与构建目标承担而非前端探测。

## 3. 可能的选型动因与功能生长方向（推测）

本节主要依据仓库现状推测，不是提交历史或作者访谈结论。“可能的选型动因”表示现有产品能力与仓库结构之间的适配关系；“功能生长方向”用于判断新增能力在当前边界下更可能落到哪里、需要同时修改哪些层，不等同于路线图预测。AIO Hub 的早期沿革由用户补充，以下将已知背景与影响推测分开。代码侧旁证主要来自[对话请求与上下文横向对比](../对话请求与上下文/对话请求与上下文横向对比.md)、[消息渲染器横向对比](../消息渲染器/消息渲染器横向对比.md)、[Agent 工具横向对比](../Agent工具/Agent工具横向对比.md)、[生成式输出与运行时横向对比](../生成式输出与运行时/生成式输出与运行时横向对比.md)和[外部执行体与应用协作横向对比](../外部执行体与应用协作/外部执行体与应用协作横向对比.md)。

### 3.1 结构模式带来的路径依赖

| 结构选择 | 与当前产品形态的可能适配关系 | 对后续功能生长的可能影响 |
| --- | --- | --- |
| Web 前端复用到 Electron/Tauri/Capacitor | 适合先建立一致的聊天、设置和数据模型，再用壳层取得本地文件、窗口、更新与移动发布能力 | Provider、会话和大部分 UI 功能可以一次实现、多端复用；功能越依赖系统 API、后台常驻或移动生命周期，平台 adapter、条件分支和端间能力差异越会成为主要成本 |
| Electron 主进程与 renderer 合仓 | 适合桌面端同时快速扩展 UI、本地服务、文件系统、Agent 执行和多窗口能力 | 新功能容易沿 IPC 两侧纵向生长，桌面能力上线较直接；主进程、renderer、preload、持久化与测试常需同步修改，跨层契约会逐渐成为稳定性边界 |
| 前后端合仓并作为一个发行单元 | 适合自托管、多用户、机器人或管理后台产品，前端与服务端版本可以一起发布 | 鉴权、协作、任务、Connector 和管理能力更容易落在服务端统一治理；前后端状态协议、数据库迁移和部署兼容面会随功能数一起扩大 |
| 按能力拆包的 monorepo | 适合核心运行时、协议、SDK、UI 和多入口需要复用同一套类型与测试的产品 | 新客户端、新协议或新业务域可以形成独立 package/app，复用范围清楚；包间 API、依赖方向、版本协同和全仓构建成为长期维护对象 |
| 插件、skills 与附属进程集合 | 适合能力来源异构、需要低门槛接入脚本、原生工具、知识资产或外部执行体的系统 | 功能可通过新增插件或进程较快扩张，也允许不同语言各取所长；发现、配置、权限、日志、取消、升级和跨平台打包若没有统一契约，会随插件数量增加，不同插件组合的验证范围也会扩大 |
| 传统单应用与功能脚本目录 | 适合保持旧格式、社区扩展和直接修改页面行为的兼容性 | 增加局部功能的入口短，旧扩展也较少受包边界限制；共享状态、隐式调用顺序和字符串协议会积累为兼容面，使深层重构及一致测试更困难 |
| 平台专用原生核心 | 适合产品明确依赖某一操作系统、原生控件或系统集成，当前仓库也以该平台为主要目标 | 平台内能力可以直接利用原生 API；后期若加入跨平台、Web 复用和社区插件，通常需要新建抽象层或并行实现，单纯增加构建目标难以覆盖这些差异 |

框架名单本身不足以决定这些影响。仓库中是否已有稳定的消息/事件协议、插件契约、服务端事实源和平台 adapter，往往比“用了 Electron、Tauri 还是 Next.js”更能决定下一项功能要改多少层。

### 3.2 AIO Hub：已知沿革与结构影响

用户补充的早期沿革如下：AIO Hub 原名 **All in One Tools**，起点是作者用于安放个人想法的工具箱。具体做法通常是从已有在线服务或应用程序中抽取一项基础能力，再加入作者认为必要的交互或流程优化。最初的工具是正则应用器，它延续自 AIO 之前的一个 Python 小工具；正则预设编排在那个阶段已经存在。聊天模块是在工具箱之后加入的，直接原因同样是现有产品没有充分覆盖作者想要的用法。作者曾向 Cherry Studio 提交功能 PR，但其认为审批和质疑过程成本过高，后来选择在自己的产品中继续实现；作者同时有 SillyTavern 使用背景。

这段沿革可以解释当前仓库中几个仅靠框架选型不容易说明的结构信号：

- **`src/tools` 承担产品主干职责。** 它占约 56.0 万行、约为全仓可识别源码的 61%。聊天、正则、Recall、Canvas 和创作工作台继续以工具域进入同一仓库，符合“先形成独立能力，再逐步组合”的生长方式。
- **正则编排早于聊天。** 当前聊天主链中的请求正则、显示正则、预设消息、快捷动作和可调整上下文管道，可以理解为早期“规则可配置、步骤可编排”思路向聊天域的延伸。这里能由代码确认当前机制，但“由早期正则工具延伸而来”依据的是上述沿革信息。
- **聊天更像后来形成的能力汇合点。** 其他调查笔记已确认聊天会整合 Agent 配置、工具、世界书、Recall、正则、VCP 协议与可运行内容。仓库因而仍保留工具箱外形，但聊天逐渐承担跨工具编排与统一呈现职责。
- **SillyTavern 经验形成了明确的兼容方向。** 当前代码支持导入 SillyTavern 角色卡、Prompt Preset、正则脚本、Quick Reply 和世界书；这与作者的酒馆使用背景相吻合，也说明部分选型目标是保留这类资产的表达力，再重新组织编辑和运行体验。
- **自主实现的阈值较低。** Cherry Studio PR 经历只能说明作者在该次协作中认为沟通和审批成本高，不能据此评价 Cherry 的一般贡献流程。对 AIO 的影响推测是：当现有产品或上游协作无法容纳某项想法时，新增能力更可能直接进入 AIO，减少等待外部项目接纳的时间。这有利于快速试验，也会使 `src/tools`、共享协议和配置系统持续扩大。

据此，AIO Hub 后续功能的默认生长路径可能仍是“新增或吸收一个工具能力，再把其中可复用的配置、数据和运行链接入聊天/Agent”。AIO 的聊天能力是在工具箱基础上形成的，如今承担着多个工具共享模型、上下文、Agent 和渲染能力的集成职责。长期成本更可能集中在工具间契约、配置迁移、桌面/移动差异和跨工具一致性，而非单个聊天模块自身的复杂度。

### 3.4 DeepSeek Harness

DeepSeek Harness 是 DeepSeek AI 官方的 agent harness（产品命令 `dsh`），以“一切皆插件”为架构主张：框架运行时是 vendored 并 rescoped 的 Cordis，产品逻辑拆成 53 组可独立发布的 `@deepseek-ai/dsh-*` npm 包。当前仓库有 20,531 个跟踪文件、7,712 个源码文件和 1,595,947 行源码，TypeScript 仍占约 94.1%；文档 5,237 份、测试代码 4,338 个，各包自带 tests/ 区。四个运行面（CLI、Web GUI、Python SDK、Linux Landlock C）各有独立边界，平台差异按同缝隙多 provider 包组织而非条件编译。pi-ai 以 npm 依赖消费，与 Cordis 的 vendoring 形成对照。新能力预计以新包沿三件套进入，成本集中在包间 API 与 vendored 上游同步。

这些推测说明，仓库结构会影响功能的默认落点，但产品方向仍取决于后续能力和已有契约。实际形成约束的是已经被数据、插件或多个客户端依赖的接口，例如消息 parts、SSE/IPC 事件、扩展 service hub、VCP 文本标记、平台 adapter 和数据库 schema。新功能沿这些契约扩展时可以获得复用；一旦越过原有事实源、权限或运行时边界，结构调整成本就会明显增加。

## 8. 统计边界与复算

本次统一统计由 [`统计仓库.ps1`](统计仓库.ps1) 生成，规则见 [`调查指南.md`](调查指南.md)。复算示例：

```powershell
./统计仓库.ps1 -WorkspaceRoot E:\works\GitStudyNotes -Projects @('aio-hub', 'AstrBot')
```

本次对象是工作区内 24 个 AI 项目仓库；`项目调查笔记` 自身不属于调查对象。统计结果绑定各单项目笔记所列 HEAD 代码快照：21 个项目已对齐 2026-11-04 快照，Manifold Desktop、SillyTavern 仍为 2026-08-27 快照，OpenOcta 的快照与规模数字未变（`0c7dac22`）。项目更新后应重新运行脚本并同步更新单项目笔记与本文。

口径差异：脚本在 GBK 控制台（Windows PowerShell 5.1 默认）下会把含中文路径的跟踪文件解码成乱码而漏计，复算应在 UTF-8 控制台（`[Console]::OutputEncoding = [System.Text.Encoding]::UTF8`）下运行。

本快照采用不同识别口径的项目：

- Chatbox：只重算跟踪文件、源码文件与测试文件数，源码行数未重算，语言比较按文件数观察。
- Cherry Studio：重算总量与模块量级，未重新生成逐语言百分比。
- VCPChat：全部改用 `git ls-files` 文件数口径——源码 2,194 个（剔除 `vendor/` 为 2,052 个）、文档 154 个、`tests/` 515 个，未重算文本行数与提交频率。
- VCPaobile：文档按 Markdown 文件数（311 份）统计；测试按入口分布（前端单元测试 122 个、`tests/` 15 个、`src-tauri/tests` 8 个等），未汇总单一总数。
- DeepSeek Harness：文档与测试只统计文件数，未重算测试源码行。
- RikkaHub：文档未汇总统一总数，正文按 README 与技能文档分布说明。
- AIO Hub：文档按统一扩展名口径统计为 477 份，正文另保留 `src/tools` 内随工具维护的 Markdown 说明口径。

除上述项目外，其余项目均按统一脚本口径重算跟踪文件、源码、文档与测试，再复核 workspace、构建配置与平台入口。
