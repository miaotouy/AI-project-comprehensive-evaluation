# 产品结构与设计基因调查指南

本目录用于调查一个项目如何形成当前产品边界、如何组织和扩展能力，以及哪些跨模块机制长期影响用户、Agent、插件和外部系统的关系。通用写作、元数据、证据和调查深度要求见 [`../AGENTS.md`](../AGENTS.md)。

本类目补足现有专项之间的空白：Chat、Agent、媒体创作等类目分别解释具体能力，独特功能类目发现少见的完整工作流，但它们都不负责回答“产品从哪里长出”“哪些入口同属一个能力框架”“当前最复杂的模块是否就是产品中心”。

## 阅读边界

本类目主要依据本地可见的仓库快照、有限提交历史、项目文档和专项源码调查，反推当前产品结构及其可能的形成过程。它是一份学习性、探索性的记录，不是作者访谈、完整产品档案或官方设计说明；即使某项判断有源码或提交支撑，也通常只能确认可见实现与记录，不能自动确认作者动机、未公开决策、完整历史背景或未来方向。

除非笔记明确标为“作者自述”并给出可复查来源，关于产品起点、设计取舍和“为什么如此组织”的表述都应按基于有限材料的推断阅读。其他项目若没有额外外部佐证，其结论尤其只适合作为继续核查的线索或横向学习材料，不宜当作对作者意图或项目真实历史的定论。

当前 AIO-Hub 是例外较多的个案：本次调查除仓库材料外，还使用了用户因熟悉作者而提供的背景说明，并在笔记中将其与可独立印证的提交历史和当前结构分开记录。因此其已说明来源的产品演变判断相对更可靠，但这些非公开背景仍不替代源码事实，不能外推为其他项目也获得同等程度的验证。

## 类目目标

- 记录项目的起点、重要演变和当前产品边界，避免只按当前代码体量倒推产品历史。
- 识别人类 UI、Agent、CLI/API、插件、后台任务、远端节点和其他设备等产品表面及其相互关系。
- 解释能力的组织单位、接入方式、共享数据和扩展边界，说明新功能如何进入产品。
- 归纳反复作用于多个模块的设计机制，同时保留例外、阶段变化和相反证据。
- 为“已调查能力汇总”的项目概览提供一手来源，防止汇总文档自行猜测产品中心。

本类目不对产品做品牌策划，也不把“基因”当作褒义评价。设计基因是有证据的跨模块产品模式，可以带来一致性，也可以带来复杂度、边界模糊或维护负担。

## 核心术语

### 产品结构

当前可观察的产品组成与关系，包括主要用户、调用者、工作区、工具、数据事实源、运行时、扩展系统和外部依赖。产品结构回答“现在有哪些表面，它们怎样连接”。

### 产品演变

由提交历史、旧文档、版本记录和作者说明确认的形成过程。演变用于区分产品起点、后加入能力、阶段性重心和当前营销定位，不能用当前目录结构替代。

### 设计基因

跨越多个功能或产品表面、持续影响能力如何被开发、接入、操作、复用或治理的产品模式。单个共享函数、通用组件或一次性架构决策不自动构成设计基因。

### 产品表面

用户或其他调用者实际接触能力的位置，例如桌面工具页、聊天工作台、CLI/TUI、服务端 API、IM 线程、插件、后台调度器、Agent 工具目录、远端节点和移动端。

## 收录门槛

一个候选机制满足下列任一条件，并有当前实现或历史证据支撑时，可以进入本类目：

1. 贯穿三个以上功能模块或多个产品表面；
2. 决定新能力如何注册、发现、复用、调用或持久化；
3. 决定产品边界，例如本地数据所有权、人类与 Agent 的关系、宿主与插件的关系；
4. 在较长演变期内反复出现，并能从多个提交或模块观察到；
5. 作者明确将其作为稳定产品原则，且当前实现能够找到对应表现；
6. 虽只覆盖少数模块，但直接改变整个项目的产品身份或主要入口。

以下内容默认不作为设计基因：

- 只服务一个功能的完整工作流，应进入对应专项或独特功能；
- 没有用户或调用者影响的纯工程封装；
- README 中没有实现依据的愿景、口号和未来计划；
- 仅因代码量大、目录层级高或模块名称包含 core 就被认定为产品中心；
- 只在当前版本短暂出现、尚不能确认稳定性的实验实现；
- “功能很多”“扩展性强”“体验好”等没有可复查对象的概括。

## 证据分层

产品结构调查必须把不同来源分开，不能把实现推断改写成作者意图。

| 标记 | 含义 | 使用要求 |
|---|---|---|
| `作者自述` | 作者在公开文档、设计决议或本次调查补充中明确说明 | 写明来源、日期和是否为转述 |
| `历史确认` | 提交历史、旧版本或迁移记录能够确认加入顺序和阶段变化 | 给出提交、日期或可定位版本 |
| `当前结构确认` | 当前代码快照中多个模块的实现共同体现该模式 | 至少列出主要覆盖面和例外；未运行验证只限制环境相关观察，不削弱该结构结论 |
| `跨模块归纳` | 调查者根据多个事实总结出的产品倾向 | 必须明确这是归纳，不写成作者原意 |
| `候选基因` | 已有重复迹象，但跨度、稳定性或证据仍不足 | 说明升级为确认项还缺什么 |
| `阶段性/已失效` | 曾经成立，当前已改变或只属于特定时期 | 不用于定义当前产品边界 |

同一结论可以同时具有多个标记。例如“工具应用早于 Chat”可由历史确认；“AI 是后加入的跨工具增强层”还需要结合当前结构与作者说明。

作者口头说明或用户转述可以作为来源，但必须标记为“本次讨论提供，尚未定位公开文档”；若提交历史或当前实现能够独立印证，应分别列出，不能把转述当成唯一实现依据。

## 与现有类目的边界

| 相邻类目 | 本类目记录 | 留在相邻类目的内容 |
|---|---|---|
| 独特功能 | 多个独特工作流为何能以相似方式接入和共存 | 每项工作流的入口、状态、执行与结果主链 |
| 应用界面基础设施 | 跨产品表面的窗口、导航或交互机制产生的组织作用 | 组件、主题、弹窗、同步总线等具体实现 |
| Agent 工具 | Agent 在全部能力入口中的位置和覆盖范围 | 工具发现、协议、审批、执行和回注 |
| Chat / Chat UI | Chat 在产品边界中的地位及其与其他工作区的关系 | 对话、会话、输入、消息操作与界面主链 |
| 仓库分布 | 目录分布如何支持或反驳产品结构判断 | 文件、代码量、测试和语言的机械统计 |
| 外部执行体与应用协作 | 外部调用是否构成稳定产品表面 | 身份、协议、控制、回流和治理主链 |
| 已调查能力汇总 | 提供产品概览、入口图和组织骨架的一手结论 | 对已有来源进行压缩和索引，不新增判断 |

同一事实允许在本类目和功能专项中出现，但承担的解释任务必须不同。例如，registry 的自动扫描实现属于基础设施；“轻量工具和复杂工作区使用同一接入单位”属于产品结构；某个工具是否提供 Agent 方法属于 Agent 工具或该能力卡的接入说明。

## 调查流程

1. **收集自身说明**：读取 README、产品文档、设计决议、用户指南、旧介绍和作者补充，分别记录当前定位与历史定位。
2. **建立演变时间线**：检查最早提交、关键模块首次加入、拆分和迁移节点；不要只搜索包含 AI 或 Agent 的提交。
3. **盘点顶层表面**：检查导航、路由、命令、服务端端点、工具注册、插件入口、后台任务和移动端，建立调用者地图。
4. **识别组织单位**：确认产品以会话、工具、工作区、模型、项目、插件、事件还是其他对象组织能力。
5. **区分入口与中心**：统计或列举各能力由人类、Agent、内部服务、插件和外部系统中的哪些角色使用；接入范围大不等于产品中心。
6. **寻找重复模式**：观察注册、持久化、窗口、任务、资产、权限和扩展机制是否在多个模块反复出现。
7. **检查反例**：主动寻找没有采用该模式的模块、历史阶段和未接入表面，防止把局部实现泛化。
8. **回链专项笔记**：产品结构只保留关系和作用，完整实现交给对应功能类目。
9. **标记覆盖缺口**：顶层产品表面若没有任何专项承接，应明确列为调查缺口，不能在汇总中假定已经覆盖。

## 入口地图要求

每篇笔记至少区分下列入口；不适用时说明原因，尚未调查时标记“未调查”：

- 人类直接操作的 UI、CLI/TUI 或 IM 表面；
- Agent 或模型可发现和调用的能力；
- 仅供其他模块复用的内部服务；
- 插件、Skill 或扩展运行时；
- 后台调度、系统事件或远端事件；
- 外部 API、协议节点和其他设备。

入口地图可以按能力族归纳，不要求为每个函数建矩阵。工具数量较多时，至少区分“人类 UI”“人机双入口”“Agent/自动化专用”“内部基础设施”“尚未调查”，并明确统计口径。

## 设计基因卡

每项已确认或候选设计基因应回答：

1. **模式是什么**：用可观察行为描述，不使用口号替代。
2. **证据类型**：作者自述、历史确认、当前结构确认或跨模块归纳。
3. **覆盖范围**：哪些模块、工作区和调用者遵循该模式。
4. **产品作用**：它如何改变能力接入、用户操作、数据所有权或扩展方式。
5. **形成过程**：它从何时出现，是否经历重构或定位变化。
6. **例外与张力**：哪些模块不遵循，哪些当前表述与历史存在冲突。
7. **不意味着什么**：明确阻止容易出现的过度推论。
8. **专项交接**：详细实现在哪些调查笔记中。

## 向能力汇总交接

“已调查能力汇总”的项目概览应优先读取本类目，并至少保留：

- 项目起点与当前定位之间的重要变化；
- 主要产品表面和调用者；
- Agent 在整体产品中的实际位置；
- 能力组织骨架及一至三项已确认设计基因；
- 不能从局部专项外推到全项目的边界。

汇总不得只因某模块代码最多、接入 Agent 最深或风险记录最详细，就把它写成产品中心或全项目质量代表。来源笔记没有项目级可靠性审计时，汇总也不得生成项目级可靠性结论。

## 横向比较规则

- 产品结构是通用覆盖面，每个项目都可以建立表面和入口地图；设计基因部分允许为空或只保留候选。
- 至少三个项目出现相近组织模式后，再建立局部横向观察；不预先要求所有项目填写同一组“基因”。
- 不按基因数量评分。机制跨度大、历史长或命名新颖都不自动代表更成熟。
- 比较时区分作者自述、当前结构和调查者归纳，不能把不同证据层放进同一布尔矩阵。
- 某项目问题记录更多可能源于调查更深；缺少同类记录不表示其他项目更可靠。

## 维护规则

- 项目新增主要产品表面、改变顶层组织单位或重新定义人类与 Agent 的关系时，复核本类目笔记。
- 提交历史结论通常不随当前实现变化，但当前定位和设计基因可能失效，应保留阶段变化而非直接覆盖旧结论。
- 新增本类目笔记后，同步检查对应能力汇总的项目概览和功能分组。
- 普通人类工具若没有现有专项承接，应在本类目记录覆盖缺口，并推动建立合适的功能类目，不能长期用“独特功能第二梯队”替代完整调查。
