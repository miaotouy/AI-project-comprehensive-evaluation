## 结论摘要

AIO-Hub 的产品起点是多功能 Tauri 工具应用，不是 Chat 或 Agent。Git 历史显示，项目在 2025-07-24 以正则工具初始化，同日加入文本/JSON 对比、JSON 和代码格式化、剪贴板、拖放、全局快捷键及仪表盘；LLM Chat 到 2025-10-16 才以 WIP 工具加入，Tool Calling 在 2026-02-17 加入，Agent Manager 又到 2026-07-09 才从 llm-chat 拆成独立工具。这条时间线与本次讨论中用户转述的作者说明一致：AI 不是第一个加入的功能，Agent 也不是全部设计的中心。

当前产品已经明显吸收 AI、上下文工程和 Agent 能力，根 README 也使用“一站式 AI 创作与开发工作站”的当前宣传语；但仓库内已经接受的移动端设计决议把 AIO 定义为“统一框架下的可扩展能力枢纽”，并强调轻量工具与复杂系统级能力都可接入。两种表述分别描述当前宣传重心和较稳定的能力组织方式，不能用前者覆盖产品前史。

当前快照共有 47 个 `*.registry.ts` 文件，其中 18 个文件包含明确的 `agentCallable: true`。这个机械统计不能直接等同于最终可用 Agent 工具数量，却足以说明 registry 与 Agent 工具不是同义概念：大量 registry 首先注册人类工具页、内部服务或应用基础设施，Agent 只是部分能力的一个入口。

本次确认四项设计基因：统一 registry 与工作区是能力接入骨架；同一能力可形成 UI、内部服务、Agent、插件和外部协议等多个入口；复杂能力倾向于形成用户可直接操作的独立工作台；本地文件、资产和应用数据承担主要事实源，远程模型与外部节点作为可配置执行或连接层。另将“微创新累积式扩张”保留为候选基因，因为当前历史和模块分布能观察到这种倾向，但尚缺作者对其稳定性的直接定义。

## 产品起点与演变

### 作者自述与当前定位

当前存在三组需要并列保留的定位证据：

1. 根 README 当前使用“一站式 AI 创作与开发工作站｜专业级上下文工程引擎”，说明 AI 与上下文工程已经成为公开介绍的高显著度产品面。
2. `docs/guide/mobile-design-language.md` 的 Accepted v4.2 决议记录：AIO 是“统一框架下的可扩展能力枢纽”，轻量工具可以快速并入，复杂工具也可以成长为完整系统级能力。该文档还明确反对把产品压成传统小工具列表。

## 当前产品边界

### 主要用户与调用者

AIO 当前同时面向多类调用者，没有单一入口可以代表全部产品：

- **人类用户**：通过桌面工具页、Chat 工作台、媒体工作站、管理器、编辑器、播放器、监控页和分离窗口直接操作。
- **Agent/模型**：通过 Tool Calling 发现并调用明确标记为可调用的方法，或通过上下文管道、宏和专用协议影响运行。
- **内部模块**：通过 registry 服务、共享 store、资产管理器、Token 服务、OCR 平台等复用能力，不经过 Agent。
- **插件与 Skill**：JS、Native、Sidecar 插件和 Agent Skills 通过各自适配器进入运行时。
- **外部节点**：VCP 服务端可以驱动 AIO 节点执行，AIO 也可把远端清单代理为本地工具。
- **其他设备**：移动端已经形成独立 workspace；桌面作为 Companion Backend 仍主要是设计构想，本次未验证真实连接主链。

### 产品表面

当前产品表面可以按复杂度而非 AI 程度分为三层：

| 表面 | 典型对象 | 特点 |
|---|---|---|
| 轻量工具页 | JSON/代码格式化、颜色选择、配置转换、媒体信息读取等 | 用户直接进入页面完成有限目标，可选择性提供内部或 Agent 接口 |
| 复合工作台 | 正则预设、Git、网页蒸馏、窗口自动化、字幕 OCR、弹幕播放器等 | 有独立状态、编辑流程、持久化或外部系统交互 |
| 系统级工作区 | Chat、媒体生成、资产、Recall/Knowledge、Web Canvas | 拥有较复杂事实对象、任务或跨模块生命周期 |

这个分层说明 AIO 允许轻量工具与复杂工作区共用产品 Shell，并不要求所有能力最终归入 Chat 或 Agent。

### 本地与外部系统边界

会话、Agent、资产、画布、工具配置和大量工作区状态主要存放在本地应用目录或本地数据库。OCR、文件、Git、媒体处理和桌面自动化等能力可以在本机执行；LLM 推理、部分媒体生成、VCP 服务端和网页目标则依赖用户配置的远程模型或外部环境。

因此“本地优先”主要描述数据所有权、工具运行位置和用户可控配置，不等于全部能力离线。AIO 也没有把官方云模型设为产品必经入口。

## 能力组织骨架

当前结构可以归纳为五层；这是跨模块结构说明，不表示五层在历史上一次性设计完成：

| 层 | 主要职责 | 代表实现或对象 |
|---|---|---|
| 工作区 Shell | 工具发现、导航、窗口、主题、设置与多表面承载 | 工具 store、路由、分离窗口、应用设置 |
| 能力注册与执行 | UI 注册、可选服务注册、统一调用与任务状态 | `*.registry.ts`、ToolRegistry、Executor、异步任务 |
| 扩展入口 | 插件、Skill、远端代理和动态能力接入 | JS/Native/Sidecar、Agent Skills、VcpToolProxy |
| 共享本地数据 | 会话、Agent、资产、知识、Recall、项目和配置 | 文件、SQLite、索引、应用数据目录 |
| AI 与连接 | LLM 适配、上下文、Agent 调用、VCP 与移动协作 | llm-chat、tool-calling、LLM profiles、vcp-connector |

registry 是这套结构的重要接入单位，但不能把每个 registry 都解释为 Agent 工具。当前 47 个 registry 文件中，18 个文件含明确 `agentCallable: true`；其余文件可能注册 UI、内部服务、初始化逻辑或尚未调查的其他表面。文件级统计也不等于方法级覆盖率，动态方法和运行配置仍会改变最终目录。

## 入口与参与者地图

| 能力或能力族 | 人类 UI | Agent/模型 | 内部或其他入口 | 当前判断 |
|---|---|---|---|---|
| 正则预设堆叠工作台 | 用户手动编辑、排序和批处理 | 未暴露方法 | 文件批处理后端 | 人类工作台主链 |
| Git 工作台 | 用户查看 diff、暂存、提交和推送 | 无 Agent facade | LLM 仅生成提交信息 | 人类工作台，AI 是局部增强 |
| 窗口自动化 | 用户编排和执行流程 | 无 `agentCallable` | OCR 平台复用 | 人类自动化工作台 |
| 实时字幕 OCR | 用户启动、停止、导出 | 无已确认 Agent 主入口 | 可把结果注入全局 Chat | 人类工具与 Chat 发生回流 |
| 弹幕播放器 | 用户拖放与控制播放 | 无 Agent 方法 | Win32 外部播放器覆盖 | 人类媒体工具 |

| 媒体生成 | 独立创作工作站 | 动态生成模型方法族 | 任务系统、资产库 | 人机双入口与共享资产 |

| Tool Calling | 审批和配置 UI | 核心调用者 | 插件、远端 VCP 代理 | Agent 运行时，不代表全部工具 |

## 已确认的设计基因

### 一、统一工具接入骨架允许能力持续扩张

- **证据类型**：`历史确认` + `当前结构确认` + 仓库设计决议中的 `作者自述`。
- **模式**：早期正则、格式化、对比和系统工具与后来的 Chat、媒体、Recall 等都以工具模块进入同一桌面 Shell；当前 registry 自动发现减少新增工具对主路由和主框架的重复修改。
- **产品作用**：轻量工具可以快速加入，复杂能力也能继续长出自己的状态、编辑器、任务和持久化，而不必改造成 Chat 的子页面。
- **例外**：插件分发链路、移动端工具覆盖和部分历史模块仍未统一；registry 只提供接入约定，不保证所有工具成熟度一致。
- **不意味着**：工具数量多不等于所有工具形成统一体验，也不代表 registry 本身是用户价值。
- **专项交接**：仓库分布、应用界面基础设施、独特功能和 Agent 工具笔记。

### 二、能力入口并列，Agent 是其中之一

- **证据类型**：`当前结构确认`，并与本次讨论中的作者观点一致。
- **模式**：同一能力可以同时存在人类 UI、内部服务、Agent 方法、插件代理、远端协议或其他模块消费；各能力按实际目标选择入口，不强制全部 Agent 化。
- **产品作用**：用户可以直接使用 Git、正则、自动化、字幕和播放器等工作台；Agent 则调用经过显式暴露和治理的子集。部分能力在人与 Agent 之间共享事实源和结果。
- **例外**：Tool Calling、Agent Skills 和部分 Recall/Knowledge 方法本身以模型为主要调用者；这不改变其他工具的人类主链。
- **不意味着**：某工具拥有 `agentCallable` 不表示它为 Agent 首创；没有 Agent facade 也不表示用户主链不完整。
- **专项交接**：Agent 工具、独特功能、媒体创作和外部执行体与应用协作笔记。

### 三、复杂能力倾向于形成可直接操作的工作台

- **证据类型**：`跨模块归纳` + 多项 `当前结构确认`。
- **模式**：媒体生成、资产、Recall、网页蒸馏、Git、正则、自动化、字幕和播放器通常不只提供后台方法，还配套页面、状态、预览、编辑、历史或管理流程。
- **产品作用**：用户可以观察、编辑、重试、接管或复用结果；AI 能力进入工作台时常作为生成、分析或调用入口，而非替代全部人工操作。
- **例外**：部分基础设施只有调试页，部分第二梯队工具尚未走通完整主链；插件和外部节点的 UI 覆盖也不完整。
- **不意味着**：存在页面不等于体验已运行验证，也不能用页面数量判断产品成熟度。
- **专项交接**：独特功能、媒体创作、Chat UI、生成式输出与运行时笔记。

### 四、本地事实源与外部能力分层

- **证据类型**：`当前结构确认` + 项目文档中的定位说明。
- **模式**：会话、Agent、资产、画布和多种工具配置以本地文件或 SQLite 为事实源；模型推理、媒体服务、网页目标和 VCP 节点通过用户配置连接。
- **产品作用**：用户拥有主要数据和本地工作区，外部模型或服务可以替换；Cloud 不是当前本地主链的所有者。
- **例外**：真实生成、远端节点和网页工作流仍受网络、凭据和第三方行为影响；部分配置包含明文凭据，具体安全边界见专项笔记。
- **不意味着**：本地优先不等于完全离线，也不自动证明本地持久化在所有故障场景下可靠。
- **专项交接**：会话与消息管理、LLM 渠道管理、媒体创作、外部执行体与应用协作笔记。

## 候选基因

### 微创新累积式扩张

- **证据类型**：`候选基因`，主要来自提交历史和当前工具分布。
- **观察**：项目持续把正则预设、文件拖放、窗口分离、媒体元数据、网页配方、字幕合并、播放器覆盖、Token 计量等细粒度构思加入现有工作区；不少能力在常见工具基础上补完预设、回流、分支、持久化或多入口。
- **候选原因**：这种扩张方式跨越多个阶段和模块，已经形成明显产品气质。
- **尚缺证据**：作者尚未在已定位文档中把“微创新累积”定义为稳定原则；也未调查这些功能的真实使用频率和长期保留率。现阶段不把它写成确认的作者意图。

## 张力、例外与反例

### 当前 AI 宣传重心与产品前史并存

README 的 AI 工作站定位是真实的当前自述，提交历史也真实显示项目从非 Chat 工具起步。准确画像应同时保留两者：AI 已成为重要增强与连接层，但不能据此重写产品起点。

### 统一接入不等于统一成熟度

registry 让工具进入同一 Shell，却不会自动提供相同深度的测试、恢复、权限和跨端支持。独特功能笔记中的第二梯队只确认入口；web-canvas 又有经过深挖后确认的结构性断点。不同调查深度也不能直接转化为模块间或项目间可靠性排名。

### 人类入口与 Agent 入口并非互相替代

部分工作台只有人类 UI，部分服务主要被其他模块消费，部分能力才是 Agent 专用。把它们统一写成“Agent 工具”会抹掉产品表面；反过来，仅按 UI 页面统计也会漏掉后台任务、内部服务和外部节点。

### 复杂工作台与轻量工具长期共存

AIO 没有把全部工具都升级成系统级工作区。代码格式化、颜色选择和配置转换等轻量目标仍有存在价值；“没有隐藏特性”只表示它们未进入独特功能统计，不表示它们不属于产品。

## 来源覆盖缺口与未验证事项

1. **普通人类工具缺少正式类目**：Agent 工具指南只覆盖模型可调用能力，独特功能又只收有辨识度的工作流；普通但完整的 UI 工具目前多停留在入口扫描。
2. **47 个 registry 尚无完整入口矩阵**：本篇只机械统计显式 `agentCallable: true` 文件并列举已调查代表；动态方法、配置开关和方法级覆盖需专项清点。
3. **产品演变只核对关键节点**：尚未按版本完整还原 README 定位、首页信息架构和用户群变化。
4. **作者观点来源**：本次讨论中的作者说明为用户转述，除已由 Git 历史印证的部分外，仍应寻找公开 issue、文档或提交说明作为稳定引用。
5. **移动端与插件分发**：移动端产品表面、桌面 Companion 实际链路和插件安装/分发生命周期没有在本篇走通。
