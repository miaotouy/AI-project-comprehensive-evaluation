# 已调查能力汇总目录指南

本目录按项目汇总已有调查笔记。汇总用于回答：这个项目已经调查过什么、目前能确认什么、详细依据在哪里。

本类目不做新的源码调查，不承担跨项目评分或排名。通用写作、证据和元数据要求见 [`../AGENTS.md`](../AGENTS.md)；来源笔记已经使用的证据状态沿用原类目定义，不在汇总中重新发明一套状态。

## 基本原则

### 基于来源

汇总只整理已有调查结论。需要澄清来源笔记时可以回读正文，但不能在汇总中补做源码调查、擅自升级证据或加入没有来源的新判断。

### 可以独立阅读

读者不打开源码和详细笔记，也应能大致知道项目是什么、主要产品表面或调用方式、已经调查的主要能力、重要边界以及各结论的来源。

### 服从项目自身形态

不同项目可以是桌面应用、Web 工作区、CLI/TUI、IM 机器人、服务端、协议网关、后台运行时或多种形态的组合。标题、分组、篇幅和叙述中心应随项目改变，不要求各项目拥有相同章节、能力数量或叙述比例。

项目已有“产品结构与设计基因”笔记时，可以用它帮助说明产品演变、表面和能力组织；没有该类笔记时，不要求补造同样的叙事。

### 不做横向裁判

汇总不比较项目强弱，不填写其他项目的“不支持”或 `N/A`，不评分、不排序。某项目调查更深、记录问题更多，不表示它比调查较浅的项目更脆弱。

### 证据不越级

静态源码贯通可以确认实现结构和主链存在，但不能代替构建、测试运行、真实 UI、端到端流程、性能、安全性或外部环境验证。来源只支持子系统结论时，不外推成项目级工程评价。

## 文件与元数据

每个项目一个文件，命名为 `<项目>-已调查能力汇总.md`。

一级标题后使用下列元数据引用块。字段无法确认时填写“未确认”；来源类目过多时可以概括，并在文末列出完整索引。

```md
> 汇总对象：`<项目名称或远端链接>`
>
> 汇总更新日期：YYYY-MM-DD
>
> 依据：<来源笔记或类目范围>
>
> 汇总方法：<如何选择、合并和组织来源结论>
>
> 汇总范围：<覆盖内容与明确遗漏>
>
> 文档定位：按项目检索已调查能力摘要，不作为横向比较或整改依据
```

## 最低内容要求

汇总至少应包含以下信息，但不强制使用同名标题，也不限制排列顺序。

### 项目概览

用足以识别项目的篇幅说明当前产品形态、主要用户或调用者、核心工作面和重要外部依赖。产品起点、历史演变、数据所有权或扩展方式只有在确实影响理解时才展开。

项目概览应有来源。不要仅凭代码量、目录名、最复杂模块或常见产品套路推断整个项目的中心。

### 已调查能力

按最适合该项目的主题组织能力。来自多个类目的同一能力应合并，避免按来源目录重复抄写。

每项能力应让读者看懂：

- 能做什么或解决什么问题；
- 当前证据能确认到什么程度；
- 影响能力成立的关键边界；
- 详细结论来自哪篇笔记。

入口、触发者、数据对象、Agent 接入、持久化或执行位置等信息，只在它们有助于理解该能力时保留，不要求每项填写统一字段。

### 证据边界与遗漏

说明未运行验证、外部依赖、暂缓项、声明与实现差异，以及来源笔记尚未覆盖的重要产品面。区分：

- 项目确认没有该能力；
- 本轮没有调查；
- 当前证据无法确认。

局部接口未提供时，应说明它影响哪一个入口或调用者，不自动否定其他已经确认的产品主链。

### 来源索引

列出纳入汇总的来源笔记。正文已经链接的来源仍可在文末集中列出，方便继续调查。

## 结构与篇幅自由

汇总可以根据项目需要使用或省略下列内容：

- 产品演变或结构图；
- 产品表面、入口或参与者地图；
- 完成度、证据状态或覆盖范围速览；
- 工程与基础设施专节；
- 独特功能专节；
- 表格、流程图或较长的代表性能力说明。

使用这些结构的前提是它们确实帮助理解当前项目。不要因为另一项目使用了某张表、某个标题或某组统计，就机械复制。

特色能力可以比普通能力写得更长；简单项目也可以只用少量小节。工程结论可以单列，也可以在相关能力附近说明。篇幅由产品复杂度和来源覆盖决定，不追求项目间表面对称。

以下仅为短小示例，不是固定模板：

```md
# <项目> 已调查能力汇总

> （元数据引用块）

## 项目概览
## <按项目自身结构组织的能力小节>
## 已知边界与未覆盖事项
## 来源笔记索引
```

## 证据与统计

- 保留来源笔记的证据状态和限定条件，不把 `入口确认` 改写为完整主链，也不把“未运行”写成能力不存在。
- `主链确认`表示来源已贯通该能力的主要产品链路；其具体含义以来源类目指南为准，不自动等同生产可靠性。
- 默认关闭、依赖用户配置、依赖外部服务或只适用于特定平台等边界，应在不淹没主体结论的前提下保留。
- 声明不符应说明不一致发生在哪个承诺、接口或子项，避免让局部差异替代整个能力结论。
- 数量统计是可选项。使用时写清分母，并把能力状态、局部异常、未调查项和暂缓项分开，避免将非互斥数字相加。
- 测试文件存在、测试实际运行、黑盒验证和线上使用证据是不同层级，不能互相替代。

## 压缩与可读性

- 先保留产品结论，再选择少量必要机制解释其成立原因；完整状态清单、源码符号和路径索引留在来源笔记。
- 同一事实只写一次。多个来源共同支撑时，在一条能力后合并链接。
- 压缩不能抹掉项目辨识度。若删去某段后只剩通用产品套话，应恢复足以识别该项目的对象、工作流或设计差异。
- 问题和限制应注明作用范围；正面机制与负面边界采用相同证据标准。
- 汇总文件本身通常不新增源码定位，需要复查时链接来源笔记的相应章节。

## 维护规则

- 单项目来源笔记实质更新后，检查对应汇总的能力结论、证据状态、范围和链接。
- 新增或删除类目后，只在确实影响项目画像或能力清单时调整汇总结构。
- 汇总未纳入某篇来源笔记时，在元数据或范围说明中交代原因。
- 代码快照、详细调查日期和完整源码依据以来源笔记为准；汇总只保留理解当前证据所需的信息。
