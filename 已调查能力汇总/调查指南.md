# 已调查能力汇总目录指南

本目录用于按项目汇总已有调查笔记中的能力摘要。本类目**不做新的源码调查，不做跨项目横向比较**；它的作用是提供一个按项目检索的入口：每个项目已经调查过哪些能力、各自结论是什么、详细依据在哪里。

通用写作、证据和元数据要求见 [`../AGENTS.md`](../AGENTS.md)。涉及“独特功能”类目证据状态（`主链确认`、`入口确认`、`介绍候选`、`归并已有类目`、`暂缓`）时，沿用 [`../独特功能/调查指南.md`](../独特功能/调查指南.md) 的定义，不在本类目重新定义。本目录补充产品主链与 Agent 接入面的区分，不能把 Agent 接口覆盖率当作项目整体完成度。

## 类目目标

- 按项目整理已调查能力，每条能力给出简短摘要和指向详细笔记的链接。
- 全部类目纳入：功能能力为主体，`仓库分布`、`应用界面基础设施` 等工程/基建向类目单列小节，不与功能能力混排。
- 不做横向对比：不比较项目强弱、不填写其他项目的 `不支持`/`N/A` 空格、不评分、不排序。
- 汇总直接采信来源笔记的结论，不重新下判断，也不在本类目补做源码验证。

## 读者定位与能力口径

汇总文件应当能够脱离详细调查笔记独立阅读。读者首先需要知道项目是什么、主要面向谁、主要产品表面是什么、有哪些完整的用户或调用者工作流和产品特色，其次才需要知道这些能力是否接入 Agent、依赖哪些外部服务以及哪些边界尚未验证。因此，本目录不是 Agent 工具注册表，也不是源码符号索引。

项目的主要产品表面不预设为桌面 UI。它可以是聊天工作台、CLI/TUI、IM 事件流水线、服务端 API、协议前端、后台任务系统或这些表面的组合。Agent、自动化进程或远端事件在某些项目中就是主要调用者；在另一些项目中，它们只是人类工作台的可选接入面。汇总时应依据来源笔记确认的项目定位和主入口判断，不能把任何一种产品表面默认为所有项目的中心。

能力状态采用两个相互独立的维度：

- **产品主链状态**：按该能力的主要产品入口或入口集合判断“入口 → 状态或事实对象 → 执行 → 调用者可见结果 → 持久化或后续动作”是否已由来源笔记确认。入口可以是人类 UI、CLI/TUI、模型、IM 事件、服务端请求、后台任务、远端事件或其他模块；面向人的工具不要求存在 Agent 接口，Agent/服务端项目也不要求额外存在人类 GUI。
- **Agent 接入面**：仅在对理解能力有帮助时补充“已提供、部分提供、未提供、不适用或未调查”。Agent 是项目的主要入口时，应直接纳入产品主链，而不是把它降格为旁注；Agent 只是可选接入面时，接口未提供不能单独把已经可用的主体功能降级为 `入口确认` 或 `声明不符`。

推荐写法是先给产品结论，再给接口说明。例如，桌面工具可以写：“Git 工作台已确认用户侧主链；Agent 接入：未提供（该工具以人类 UI 工作流为主）。”服务型项目则可以写：“IM 事件接入、调度和消息投递构成产品主链；Web 管理台是运维表面。”如果 Agent 调用本身就是能力目标的一部分，则直接说明其 Agent 主链，不用其他表面的状态替代。

`声明不符` 应主要用于用户可见产品能力、公开文档承诺或明确的接口契约与当前实现不一致的情况。某个可选 Agent 方法未暴露、某个工具没有 Agent facade，通常应作为局部边界记录，不应替代该工具的人类产品主链状态。

## 文件粒度

- 每个项目一个文件，命名 `<项目>-已调查能力汇总.md`，例如 `AIO-Hub-已调查能力汇总.md`。
- 项目名以来源笔记文件名为准；同一项目在多个类目中的笔记都要纳入。
- 汇总文件独立阅读时即可了解该项目已调查能力全貌，不必先打开类目笔记。

## 元数据模板

在一级标题后立即写入元数据引用块，字段名、顺序和标点必须与下列模板一致；每个字段单独占一行，使用全角冒号，并在相邻字段之间插入一行空引用标记 `>`。信息无法确认时保留字段并填写“未确认”。

```md
> 汇总对象：`<项目名称或本地路径>`
>
> 汇总更新日期：YYYY-MM-DD
>
> 依据：<来源笔记清单，可列代表性条目并说明未覆盖类目>
>
> 汇总方法：<阅读各来源笔记的结论摘要与关键章节，合并重复能力，保留证据状态并链接来源>
>
> 汇总范围：<本次汇总覆盖的类目与明确排除项>
>
> 文档定位：按项目检索已调查能力摘要，不作为横向比较或整改依据
```

## 推荐结构

```md
# <项目> 已调查能力汇总

> （元数据引用块）

## 项目概览
## 完成度速览
## 功能能力摘要
### <按功能主题聚类的小节，例如 角色与上下文 / 会话与消息 / 生成与创作 / Agent 运行时与外部协作 / 渠道与调度 / 独特与差异化能力>
## 工程与基础设施摘要
## 已知边界与待验证事项
## 来源笔记索引
```

## 写作要求

### 摘要的组织

- “项目概览”先给出产品画像：主要用户、核心工作面、持久化与外部依赖，以及 Agent 在整体产品中的位置。对于同时包含人类工作台和 Agent 工具的项目，明确说明二者是互补面，不默认以后者解释前者。注明是推测还是来自于自身说明。
- 先读各来源笔记的“结论摘要”章节，以它为准建立能力清单；需要补读正文以澄清合并或删减时再下钻。
- 功能能力按**功能主题**聚类，不机械按类目目录排列。同一能力被多个类目覆盖时合并为一条，不逐类目复制标题。
- 每条能力写成独立列表项或小节：**能力名称 + 面向用户的能力结论 + 产品主链证据状态 + 必要时的 Agent 接入说明 + 来源笔记相对链接**。摘要以一至三句说清用户目标、主要结果和关键边界；项目特色或人类工作台可以保留足够细节，不能为了统一字数删掉识别产品所必需的信息。详细实现机制、完整状态清单和源码定位留在原笔记。
- 涉及“独特功能”类目时保留其能力卡标题和证据状态；`归并已有类目` 项只记“已归并到某类目”一行，不重复写能力内容。
- 纯工程类结论（`仓库分布`、`应用界面基础设施`）放入“工程与基础设施摘要”小节，按主题概括，不逐条展开。

### 完成度速览与“未运行验证”口径

每个汇总文件在“项目概览”之后必须写“完成度速览”小节。第一组数字统计**能力条目的产品主链状态**，不能因为某个 Agent 方法未提供就重复计算或降级；第二组可选数字统计 Agent 接入覆盖、局部接口差异、未调查类目和暂缓事项。若一张表同时列出两组数字，必须明确分母，避免把能力条目数与异常子项相加后误读为同一组互斥分布。先给数字再展开细节，让读者在进入正文前建立项目整体画像和证据边界。

同时在该小节写一段口径说明，语义完整、表述可微调：**本汇总所有“主链确认/静态源码确认”均基于对当前代码快照的源码贯通，在编译型桌面应用或完整本地主链中视为完成交付态；“未运行验证”仅指未进行黑盒运行、UI 或端到端操作，不否定代码完备性。**

### 异常项剥离与措辞基调

- 未调查的能力、尚未走通主要产品生命周期的候选，以及确实影响能力成立的 `声明不符`，集中放在文档末尾的“已知边界与待验证事项”小节。它们不应被写成用户已经无法使用的功能，除非来源笔记明确得出该结论。
- 能力存在局部接口差异时，正文先保留产品主链结论，再用一句话说明边界，例如“人类工作台主链已确认，Agent 接口未提供”；完整差异、接口依据和影响范围移入末尾小节。面向人的工具没有 Agent facade 时，不要自动标记为“未闭合”。
- 每条能力摘要先陈述“能做什么/已确认的事实”，再补边界条件，不把“未实现”“未验证”作为条目的开头定语。

### 证据与边界

- 保留来源笔记的产品主链证据状态（`主链确认`、`入口确认`、`介绍候选`、`归并已有类目`、`暂缓`、`声明不符` 等），不擅自升级或降级；如果来源同时记录 Agent 接入状态，应作为独立说明保留。`暂缓`、影响主链成立的 `声明不符` 等异常标记主要出现在“已知边界与待验证事项”小节，正文只保留必要指认。
- 区分“项目没有该能力”“笔记未调查”“无法确认”三种情况，措辞沿用来源笔记的表述。
- 区分“产品能力没有接入 Agent”“该工具明确面向人类、不适用 Agent”“Agent 接入尚未调查”三种情况，不能把它们合并为“功能未实现”。
- 来源笔记明确写出的关键边界（默认关闭、依赖外部服务、依赖用户配置）应体现在摘要中。
- 汇总文件本身不新增源码定位；需要定位时引用来源笔记的文件与章节即可。

### 篇幅与密度

- 篇幅由项目覆盖范围决定，不设统一字数；机械套用小节制造表面对称没有价值。
- 一个自然段或列表项主要回答一个问题；高密度的符号、状态值清单不要堆进摘要句子，留在来源笔记。
- 链接写法：`[Agent 工具调查笔记](../Agent工具/<文件>.md)`，路径相对汇总文件所在目录。

## 维护规则

- 单项目笔记实质更新后，应同步检查对应汇总文件的能力清单、证据状态和链接。
- 新建或删除类目后，检查受影响项目的汇总文件是否需要增删条目。
- 汇总文件不承担版本快照信息；代码快照、调查日期等以来源笔记为准。
